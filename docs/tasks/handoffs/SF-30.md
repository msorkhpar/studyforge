## Decisions

1. ⛔ **The join is the row's `id`, not a new published attribute, and the
   container row was brought up to the index's shape rather than the index down
   to the container's.** The root index already carried `id="<unit key>"` as its
   deep-link anchor and `index.entries.Item`'s own docstring calls it *"the unit
   key every surface joins on"*. ⭐ So a container row now carries the same
   thing, which also gives a container page deep links it never had. ⚠️ **The
   alternative — publishing `data-unit` in `SURFACE_HOOKS` and emitting it from
   all three renderers — would have moved all seven goldens AND obliged
   `chrome.css` to carry a rule reaching a unit's address**, because
   `test_chrome.py::test_every_non_class_hook_is_reached_by_a_rule_in_this_part`
   holds every non-class hook to one. ⛔ Painting a token only so a published
   hook can be called painted is `QA-03/2` committed on purpose, and `SF-34`
   ruled against it by name. **This is the decision I would most like reviewed.**
2. ⛔ **`data-marked` IS published and `data-unit` is NOT**, and the split is the
   same argument read in both directions: `SURFACE_HOOKS` is *what the
   stylesheet targets*. The state is drawn by `chrome.css`, so it is published.
   The key is read only by a script, so it is not. ⭐ `render/page/mark.py`
   carries that reasoning where a reader who wonders will be standing.
3. ⛔ **The container row's key is derived from the container's address and the
   row's POSITION, not from a field on `Item`.** `listing.render`'s own docstring
   already states the invariant — *"the container reader has already refused any
   map whose ordinals are not contiguous from 1, so the declared order is the
   ordinal order"* — and a per-row copy of the address would be a second place
   for it to disagree with the ordinal the row was listed under. ⚠️ Nothing in
   `src/` builds a container `Item` today, so an optional `key` field would have
   been `""` on every real site and the badge would never have lit.
4. ⛔ **The region ships `hidden` and the script unhides it; it is not built by
   the script.** `copy-code.js` creates its button because the words on it are
   one word; this region carries two labels and a three-clause sentence about
   where the reader's data lives, and putting product text in a `.js` string is
   R13 with the file extension changed. ⭐ So the words are markup, and with
   scripting off — or with site data blocked — the reader sees **nothing**
   rather than a control that cannot work. Measured: `control hidden, scripts
   off : True`, `buttons a reader can reach : 0`.
5. ⛔ **The consumer does NOT guard the store's existence.** This is the one
   place I deliberately wrote less defensive code, and the epic's own warning is
   why: the extraction source's guard is what made a load-order bug silent.
   ⭐ The part is **last** in `SCRIPT_PARTS` so its own throw reaches nothing
   else, and `test_the_consumer_is_last_so_its_own_failure_reaches_nothing_else`
   pins that.
6. ⚠️ **The display-preferences record has no writer on the floor today, and it
   is shipped anyway.** The epic rules *"two versioned keys, never one record"*,
   and the property is the **independence** — a preference that fails to parse
   must not be able to take every mark with it. ⛔ Inventing a preference toggle
   to give it a consumer would have been unrequested scope; `SF-18`'s transport
   (a speed, a volume) is the expected first caller, and the store says so.
7. ⛔ **The key's grammar is not re-spelled in JavaScript.** The store validates
   only what it needs to know — *can the control display this* — as a length
   bound plus a refusal of whitespace, controls and DEL. ⚠️ Written as a loop
   over code points rather than as a character class, because a character class
   is where this went wrong once already (see *Surprises*).
8. ⛔ **`mark` is not promoted onto `render.page.__all__`.** Only
   `page.document` calls it, exactly as `page.section` is not promoted; a name
   on the package contract that no peer imports is the Ruling 101 row 1 reach
   `render/page/test_init.py`'s sweep fails by name.

   the prediction is why it was visible.**
2. ⚠️ **Plant B did not fail the cross-golden join test**, and the reason is
   structural rather than a defect: that test reads the **committed** goldens, so
   a renderer change is invisible to it until the goldens are regenerated. ⭐ The
   chain that closes the gap is two links, both pinned: `render == golden`
   (`test_every_container_renders_against_its_golden_file`) **and** the goldens'
   keys agree. Recorded as `SF-30/6` so nobody reads the join test as doing more
   than it does.
3. ⚠️ **Plant I was caught, but not by the node I predicted.** Renaming the
   control's attribute in one golden left the *other* unit golden still naming a
   key, so the subset assertion stayed green; the per-page count assertion went
   red instead. ⛔ The non-vacuity guard is per-population, not per-page, and
   saying so is cheaper than pretending otherwise.
4. ⛔ **A character class nearly shipped a NUL byte into an asset.** The first
   draft of the key check was `!/[\s -]/.test(value)`, which reached disk as a
   regex containing a literal NUL and `\x1f`. ⚠️ Either spelling is wrong for the
   same underlying reason — **a hyphen inside a character class is a range
   operator or a literal depending on where it sits, and every slug this
   framework mints is hyphenated**, so the intended class would have discarded
   every key there is while reporting nothing. ⭐ It is now a loop over code
   points with no class at all, and the NUL plant above shows the repository
   would have caught the byte even if I had not caught the logic.
5. ⭐ **`localStorage` works on `file://` in Chrome 149.** I expected to have to
   report this clause Blocked on the browser. It is the one assumption the whole
   task rests on and it was measurable in ten minutes, so it was measured first.
6. ⚠️ **`docker/dev/check` cannot restore a plant**: the container's view of the
   git common directory is mounted **read-only**, so `git checkout --` inside it
   fails with *"Unable to create … index.lock: Read-only file system"* — and my
   first plant run reported four restores that had not happened, so plants C and
   D accumulated onto A and B. ⛔ Caught by reading the output rather than the
   exit code. **Every plant in the table above was applied and restored on the
   HOST, with the container used only to run `pytest`.** ⭐ And the reason the
   accumulation was recoverable at all is that I had not yet committed: the
   lesson I took is the opposite one — **commit before planting**, so `git
   checkout --` can reach a new file too. Two of the four files were untracked,
   and `git checkout --` cannot restore those; I reverted them by hand and
   re-ran the whole suite to prove the tree was back.
