## What landed

- ⭐ `FLOODING` calls `signal.pthread_sigmask(SIG_BLOCK, {SIGINT})` first. It floods
  `stderr`, prints its listening line, then waits in `signal.sigwait({SIGINT})` and prints
  `stopped`. It has no Python handler and does not call `signal.pause()`.
- ⭐ If `FLOODING` gets a second argument, it holds after listening until one byte arrives
  on `stdin`. Only the two new tests use this, to put a signal BEFORE the wait with no
  timing involved.
- ⭐ The 60 s `rest` bound in `served` now has a comment saying what it measures: the time a
  child gets to END once it is told to. It is a backstop, not a wait for work.

## Decisions

- ⭐ **The cause was the stand-in, not the bound, so the fix is the stand-in.** The old
  stand-in installed a Python `SIGINT` handler and then called `signal.pause()`. CPython's C
  handler only sets a flag, and the Python handler runs at the next check in the eval loop.
  A signal that lands after the last check and before `pause()` enters the kernel sets the
  flag. `pause()` then waits for a second signal that never comes, and `rest(timeout=60)`
  raises. A loaded parallel suite preempts the child in exactly that window. Raising the
  bound would not help, because the child never ends.
- ⭐ **Not moved to the serial group.** After the fix, the reading is GREEN under the
  heaviest parallel load measured below, and a serial slot would cost the suite for nothing.
- ⭐ **`sigwait` over a polling loop.** A blocked signal stays pending until it is taken,
  so it does not matter when it arrives. A `sleep` loop would bring a clock back into a
  reading that `ProcessOutput` keeps clock-free.

## Surprises

- ⚠️ **The old stand-in had a SECOND failure mode, and the host showed it more often than
  the hang.** The parent reads the listening line as soon as its bytes are written. The
  child can still be inside `print` at that point. The handler's own `print` then raises
  `RuntimeError: reentrant call inside <_io.BufferedWriter name='<stdout>'>`, and the child
  exits 1. The new stand-in has no handler, so this cannot happen either.
- ⚠️ **The hang could not be forced with a slow operation that checks for signals.** On
  3.14, a call's return and a big-integer `**` both run pending handlers. The plant that
  proves the mechanism uses `b"x" * n`, a single bytecode that never checks.

## Findings

- `[local]` **`W378/1`** — ⚠️ `W367/4` read the failure as "a timing flake under parallel
  load", and the row asks for the bound to be argued. Neither was the defect: the child lost
  its signal and never ended, so no bound would have held. A future flake that runs out an
  output timeout should be checked for a child that cannot end before any bound is changed.
- `[local]` **`W378/2`** — The pinned image has no `pytest-repeat`, so a repeated reading
  there needs a temporary parametrising module (as above). This is recorded so the next
  office can repeat a reading without looking for the plugin. It is not a request to add it.

## For dependents

- ⛔ **A stand-in child that must stop on a signal does not use a Python handler plus
  `signal.pause()`.** It blocks the signal first and takes it with `sigwait`, as `FLOODING`
  does. `test_an_interrupt_that_lands_before_the_stand_in_waits_for_it_still_stops_it` shows
  the pattern.
