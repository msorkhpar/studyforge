## What landed

⭐ **What the software does now that it did not:** a reader who edits a unit's file can run
`studyforge check <that file>` in their own terminal:

    studyforge check practice/passes/greet.py              # the corpus is found above the file
    studyforge check practice/passes/greet.py --corpus .   # or named

- ⭐ **Resolution.** The verb reads the corpus (`generate.declarations.read_corpus`) and builds
  each unit's generated document the way the content route serves it: `build_unit`, rendered,
  then read back through `unit.served.parse`, which is the trust boundary. Each section's
  `workspace` is read with `exercise.from_document`. The argument is compared, as a path
  relative to the source root, with each record's `main_path`. The comparison is done twice:
  once normalised but with links unresolved, and once with links resolved.
- ⭐ **Graded** (`Exercise.graded`, the grader's presence): the runner is handed
  `[test_command]`. Exit `0` if the run's exit line is `--- exit 0 ---`, `1` otherwise. The run
  is recorded in `studyforge.progress` in `test` mode.
- ⭐ **Ungraded:** the runner is handed `[run_command]`. The program's output is streamed, then
  `NO_TEST`, and the exit is `0`. Nothing is recorded.
- ⛔ **Refused, exit `2`, nothing run:** a path no record names, which is refused by name and
  followed by the files the corpus does check; a path two records name (both are named, and
  neither is run); no `corpus.json` above the file or at `--corpus`; a corpus or unit that
  cannot be read.
- ⭐ **Output:** one header line (`check <main_path>  practice <key>  <state>  mode <mode>`), the
  runner's lines unfiltered, then the verb's verdict line. The runner gates its own lines. The
  verb's own lines, including the argument echoed in a refusal, pass `scrub`.
- ⭐ **Ctrl-C** stops the run's whole tree (`RunHandle.stop`). The stream still ends in
  `--- exit stopped ---`, and a graded run is recorded as `stopped`.

## Decisions

⭐ **The verb is `studyforge check <file>`.** The reader names the file they edited. The
verb finds the one practice whose generated unit document names that file as its
`main_path` (the section's `workspace`), and hands the command that document names to
`studyforge.execute`. The name says what the reader wants to know: does my file hold up.
It is not `test`, because a file with no test is checked too (decision (a)). It is not
`run`, because `run` is already the served execution namespace (`SF-22`) and the name of
the act that never completes a practice.

### (a) A file with no test RUNS ITS PROGRAM, then says there is no test, and exits `0`

⭐ **Decided: the verb runs the record's `run_command`, read from the generated unit
document, streams what the program printed, then says no test checks this file, and exits
`0`.** ⛔ It does not stop at saying there is no test.

The argument:

1. ⭐ **The user's direction asks for it.** The epic quotes it: *"update the file and run
   them by a command which then will be run against that unit test associated with the file
   if there is any."* Running comes first in that sentence, and *"if there is any"* qualifies
   the test only. A command that runs nothing when there is no test answers half of the
   request.
2. ⭐ **§7's ungraded state is work the reader does, not an absence.** Spec §7: ungraded
   exercises *"are presented as work, clearly marked as unchecked, and they never complete
   anything."* §7 also says *"Run executes the reader's program so they can see what it
   printed."* For an ungraded file, seeing what it printed is the only feedback there is. The
   runnable fixture's unit 3 tells its reader exactly this: *"run it and read it."*
3. ⭐ **The record exists so the file can be run.** `W357` put `run_command` in the ungraded
   record on purpose (its handoff, *Smaller decisions*: *"A record exists so that a file can
   be resolved and run"*). If the terminal command never ran it, the only consumer of that
   field would be the page's Run button, which a reader in a terminal does not have.
4. ⛔ **It opens no new way for input to become a command** (§8.3, rule 3). `run_command`
   comes from the same generated document as `test_command`. The argument selects a file and
   nothing else, in both cases.
5. ⛔ **The exit code stays `0` whatever the program does** (C5, §7's three states). The
   exit code answers one question: did a test fail? With no test, the answer is no.
   Returning the program's status would make a shell, a script or an editor's task read an
   ungraded file as a failed one, and C5 says it is not a failure. ⭐ **The program's own
   status is still shown**: the runner's stream ends with its exit line
   (`--- exit <status> ---`), and the reader reads it there.

⚠️ **The cost, stated.** `studyforge check hello.py && …` continues even when `hello.py`
crashes. That is intended: `&&` asks the grader's question, and there is no grader. A reader
who wants the program's own status reads the exit line.

### (b) A passing test run RECORDS A PRACTICE PASS, through the one store

⭐ **Decided: every finished test run of a graded file is recorded in the corpus's progress
store (`studyforge.progress`, `SF-21`) under that practice's key, in `test` mode.** So a
passing run sets `first_passed_at` the same way a passing Submit on the page does. ⛔ A run of
an ungraded file's program is never recorded, and nothing but a passing grader run can pass.

The argument:

1. ⭐ **§8.5 defines a pass by how it was established, not by who asked for it.** *"A
   practice pass is a fact established by a grader run … the record is written where the fact
   was established."* The terminal command's grader run goes through the same runner
   (`SF-20`), in the same mode, with the same argv read from the same document as the page's
   Submit. The epic says that is *"why they agree"*. A fact established the same way is the
   same fact. If it went unrecorded, the same passing grader run would count on the page and
   not count in the terminal.
2. ⛔ **It is not a client's claim.** §8.5 rejects a pass held in the browser because it is
   *"a claim by a client that the server cannot check"*. This verb is not a client of anything.
   It runs the grader in its own process and reads the verdict from the runner's exit line.
   The store's own contract expects writers from outside a server: `studyforge.progress`
   says *"`SK-06` and `OPS-04` write it from outside any server."*
3. ⭐ **The page reads the pass back with no new mechanism.** The store is keyed by
   `progress.practice_key` (`SF-21/4`), built from the unit's `Address`, its ordinal and the
   section key. The verb composes no key itself. The page and the terminal therefore join on
   one string, and a pass earned in the terminal lights the page's badge.
4. ⭐ **Only the completion rule decides a pass.** The verb records a run only when the
   practice is graded, which it reads from the grader's presence (`Exercise.graded`, never
   `workspace` being non-null, `W357/1`). Mode is always `test`. `progress.is_pass` then
   passes only exit `0` in `test` mode, the same rule as
   `exercise.completes_practice(GRADED, TEST, passed=True)`. A failing run, a timeout and a
   stop are recorded as what they were, and none of them passes. That is the store's contract
   (*"record each finished run"*), so the store's `last` is never stale about a run the
   reader just watched fail.
5. ⚠️ **A store that cannot be written does not change the verdict.** The test ran and its
   exit code stands. The verb says, gated, that the run was not recorded, and exits with the
   test's verdict. A test verdict is not something the store can overrule.

⚠️ **The cost, stated.** A terminal run now writes one git-ignored file under the corpus's
generated root, which is where the server already writes it. It writes nothing else, and never
into the reader's material (R3).

### Smaller decisions, made while writing the code

- ⭐ **A graded file is handed its `test_command` alone, not `[run_command, test_command]`.**
  The epic says the verb hands *"the command that document names"* and that *"a file with an
  associated test runs that test"*. `SF-22`'s Submit hands *"the one command that mode names"*.
  One command each way keeps the terminal and the page's Submit byte for byte alike. ⚠️ The
  compile-first guarantee is kept by the test command: the fixture's non-compiling unit 4 fails
  at the test's import (exit `2`), and the verb exits `1`.
- ⭐ **The exit codes are `0` / `1` / `2`, never the test's own status.** A test runner's own
  `2` (pytest's collection error, measured on unit 4) would otherwise be indistinguishable
  from *"nothing ran"*. The exact status is in the stream's exit line. `0` and `1` are
  `validate.report`'s `OK` and `INVALID` imported, as `serve` imports them.
- ⭐ **The corpus is the nearest `corpus.json` above the file**, or `--corpus`. The source
  root the runner is given is that corpus root, which is where `main_path` is relative to.
- ⭐ **Two practices naming one file are refused, naming both.** Running either would record a
  pass against a practice the reader may not have meant.
- ⭐ **The header names the mode** (`host` or `container`), as the runner's probe answers it,
  so a reader sees where their code ran.
- ⭐ **The recorded `commands` is `shlex.join(argv)`**, the spelling `SF-22` records. It
  reads back to the argv, which a test asserts with an argument holding a space. This line
  first said *joined by single spaces*, and the register asked for the change before merge.
  See `SF-44/1`.

## Surprises

- ⚠️ **There is no generated `unit.json` on disk.** `unit/builder/document.py` says so: *"Nothing
  under `src/` writes a `unit.json`"*. The content route builds each unit's document on
  request. So the verb does the same, through the same calls and the same trust boundary,
  rather than reading a file a build never wrote.
- ⚠️ **The non-compiling unit's test exits `2`** (pytest's collection error), which is the same
  number as the framework's `UNUSABLE`. That is why the verb maps verdicts to `0` / `1`
  rather than passing the status through.
- ⚠️ **The package contract counted its verbs in prose** (*"Five of the six verbs above"*), and
  so did the dispatch test's comment. Both became false the moment a verb was added. Both now
  name the verbs and give no count.

## For dependents

- ⭐ **`SF-22` (Run and Submit):** see `SF-44/1`. This verb records test runs through
  `Progress.record_run(address, ordinal, section, mode="test", exit_code=<status or word>,
  commands=[shlex.join(argv)], when=<UTC ISO seconds>)`. `address` is the unit's container
  `Address`, `ordinal` its unit number, and `section` the section key. So a pass earned here
  is read by the page under `progress.practice_key` with no new mechanism.
- ⭐ **Any caller that resolves a reader's file:** `studyforge.cli.check` builds the generated
  unit documents exactly as the content route does. ⚠️ Its resolution helpers are private to
  the verb. A second caller that needs file → practice should ask for them to be lifted onto a
  shared surface rather than copy them.
- ⭐ **Documentation:** the verb's help text and the module docstring are its reference. No
  reader-facing document names the verb yet.
- ⭐ **`SF-29`:** the verb streams unfiltered, as the epic says (the filter is for the page).
  If a terminal filter is ever wanted, it is an option on this verb over `SF-29`'s filter,
  never a change to what the runner yields.
