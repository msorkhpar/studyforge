## Decisions

### 1. ⛔ Not a directory-wide `*`, and this is the one the brief asked me to argue

`progress/` is a directory this framework owns whole, so `*` is right there. ⛔ **`.studyforge/`
is TRACKED and carries the asset bundle a clone must read**, so a `*` would hide the product.
⭐ **So the rules name the cache and its staging file**, and the directory keeps its tracked
contents.

### 2. ⛔ The ignore file hides ITSELF — but only when it carries nothing else

⚠️ **This is the clause that decides whether the fix works at all, and it looks like a detail.**
An ignore file written into an already-onboarded corpus is *itself* an untracked file: without
the self-ignore line the first serve would trade one dirty path for another and
`tools.workspace verify` would still refuse the workspace. ⭐ **A file holding only
machine-local rules is itself machine-local.**

⛔ **The opposite is true the moment the same file also carries the corpus's media policy**: a
clone has to READ those rules or the media it regenerates reads as dirt, so that file is
committed and must not hide itself. ⭐ **So the self-ignore line goes in exactly when the media
rules are absent**, and both directions are asserted.

⚠️ **Why the two rule sets share one file rather than getting one each:** a directory has one
`.gitignore`, and both sets are about `.studyforge/`. Giving the cache its own directory
(`.studyforge/discovery/site.json`, `*` beside it — the shape that mirrors `progress` exactly)
was the alternative I costed: it needs no merge and no self-ignore, but it **moves an R21
contract's location** — the spec table, four golden plans, the authoring guide, the rubric's
quotation and eight test modules — and it strands the `site.json` every existing corpus already
has at the old path, needing a hand `rm` per corpus, which is the R19 hole this row is about.
⛔ **Rejected on those two grounds, not on taste.**

### 3. ⭐ BOTH writers, and the serving one is the load-bearing half

⚠️ **The brief asked me to choose between serve and onboarding. The measured answer is that
neither alone is enough, and they do not conflict:**

- **onboarding** writes it, so a corpus is **born** with the rule and never needs the framework
  to have run — that is the row's clause 1 and R19's shape;
- **`discovery.cache`** ensures it the moment it writes the cache, so a corpus onboarded
  **before** this change is covered the first time somebody serves it — the brief's point that
  the serving process cannot be skipped.

⛔ **They cannot drift**: both compose `placement`'s `cache_ignore_lines()`, so onboarding's
file is a superset of the serve-written one and a later regeneration writes over it rather than
fighting it. ⭐ **And `ensure_ignored` never rewrites a file that is already there** — it may
carry the corpus's media policy, which is not this writer's to change — so a corpus generated
before the rule is **reported** and left exactly as it is, never silently repaired (row clause 3).

### 4. ⛔ The ensure runs on the FRESH path too, and that is not belt and braces

⚠️ **Measured, and it is the trap in this row.** The first corpus's cache is **fresh**: nothing
rewrites it, so an ensure placed only inside `write` would never have run on the one corpus the
row was minted from. ⭐ `assemble` therefore calls `ensure_ignored` on the fresh branch and
`write` calls it on the other — mutually exclusive branches, so no line is reported twice.

### 5. ⛔ The cache stays IN the corpus, and the row's clause 2 is answered NO

⚠️ Clause 2 asks whether the cache belongs in the corpus at all. ⛔ **It does.** Moving it to a
host cache directory buys the same cleanliness and costs an absolute host path in the
framework's own resolution, a collision between two checkouts of one corpus on one disk, and a
generated artifact that `plan` can no longer name. ⭐ Ignoring it where it sits is the cheaper
answer and it holds.

### 6. ⛔ THE ONE AUTHORITY-DOCUMENT CHANGE — the register should read this deliberately

⚠️ **This row cannot be implemented without dating a standing ruling.** Spec §5 says, from
PO round 78 / `W242/1`:

> A build's output is committed too: its pages, the root index, the asset bundle and
> `site.json`.

and `tests/studyforge/corpus/placement/test_profile.py` carried `.studyforge/site.json` in its
`NEVER_IGNORED` population, asked of git. ⛔ **W425 is the opposite instruction**, so one of the
two had to move.

⭐ **The argument I amended it with is structural rather than a preference, and it is why I
believe the row is right:** every other artifact in that list is READ by somebody — a reader
opens the pages and the index, a page loads the bundle — and **nothing reads the cache**.
`corpus.discovery.assemble` scans on every call and returns the scan; there is no branch on
which a cached `Site` is handed back, by that module's own stated contract. ⛔ So a clone
carrying the cache gains **nothing**, while every reader who serves the corpus gets a modified
file for doing the one thing the tool is for.

⭐ The sentence is amended **in place with its ground and its date**, the way R14 was withdrawn
in place, and `site.json` moved from `NEVER_IGNORED` to a new `ALWAYS_IGNORED` population that
is asserted of git in both media policies. ⚠️ **If the register disagrees, this is the single
thing to revert** — the mechanism would then have to become the separate-directory shape costed
in decision 2.

## For dependents

- ⭐ **A corpus is regenerated, not patched.** If a corpus was onboarded before this branch and
  you want it born clean rather than repaired on first serve, re-run onboarding; the generated
  ignore file appears at `.studyforge/.gitignore` and, with media committed, it hides itself, so
  there is **nothing new to commit**.
- ⛔ **Do not add an ignore line to any corpus by hand, and do not use a local git exclude.** If
  a corpus still goes dirty on the cache, the serve report now says which of the three states it
  is in, in its own words — read that line rather than the tree.
- ⭐ **`Profile.ignore_file(media=...)` no longer returns `None`.** A caller that branched on
  `None` still compiles and still behaves, but the branch is dead; `plan.ignore_home` is now
  always set for a corpus that is plannable at all.
- ⛔ **The ISO corpus itself is untouched by this branch.** `tools.workspace verify` will keep
  reading RED on `.studyforge/site.json` until that corpus is served — or regenerated — with
  this branch merged. ⭐ That is one act by whoever owns the corpus, not a per-corpus edit: the
  first serve writes the rule and the tree goes clean, which is exactly what was measured on the
  copy.
