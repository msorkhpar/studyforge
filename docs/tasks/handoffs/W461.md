## What landed

⭐ **What the software does now:**

- **`corpus.json` may carry `onboarding_doc`** under **`corpus_api: 6`**
  (`KEY_VERSIONS[(None, "onboarding_doc")] = 6`, `CORPUS_API = 6`, known set `1`–`6`).
  The value is a corpus-relative path ending `.md` (no leading `/`, no `.` or `..`
  segment, no glob character), or `false` for no reader document. A refusal never
  quotes the value (R7). `Manifest.onboarding_doc` is `ONBOARDING_DOC` (the root reader document) when the key is
  absent (`studyforge.corpus.manifest.ONBOARDING_DOC`, now on the package surface) and
  `None` for `false`. So every corpus onboarded before the key is onboarded exactly as
  it was.
- **Onboarding places the document where the manifest says** (clause 1). The file, its
  `not_material` glob (`artifacts.own_not_material(reader)`), `artifacts.paths(reader=)`
  and the generated pin check's pointer (`pin.pin_test(skills, reader)`) all follow it.
  With `false`, no document is written and the pin check says how to install in its own
  words instead of naming a file. `artifacts.placed` refuses, by name and before
  anything is planned, a place another writer owns: a path onboarding or the scaffold
  already writes, or anything under `.studyforge/` or the archive directory
  (`ISO-32/5`'s trap).
- **A regenerate that moves the document drops the old glob.** The entry whose `why` is
  `artifacts.WHY_READER` is recognised as this skill's wherever an earlier run put it,
  so it is re-derived instead of being kept as a person's glob that classifies nothing.
- **A generated file MOVED by hand is recognised, not refused.** `refuse_unrecorded`
  (`W353`) exempts a file at a newly generated path whose bytes have the digest the
  record holds for a generated path that is **now empty**. This is the corpus's case:
  `docs/archive/ONBOARDING.md` is the root file moved with `git mv`. ⛔ Only the digest
  of a MISSING entry counts, so a file of yours, or a copy of a generated file that is
  still in place, is refused as before.
- **`hand_edited` reports a generated file missing from its recorded place** (clause 2).
  The paths whose bytes differ come first, as before. Then there is one sentence per
  missing file (`record.gone`):
  *"`<where>` is missing: .studyforge/installed.json records it as generated there and
  nothing is there now. Moving or deleting a generated file is an edit to it (R19):
  regenerate to write it back, or, to keep it somewhere else, say where in corpus.json
  and regenerate"*. The person's module is never reported.
  ⛔ **An ignore file that hides itself is not reported** (`record.machine_local`). It is
  one machine's own (`W425`), so every fresh clone lacks it. See *Surprises*.
- The spec's §4 key table, [`corpus.md`](../../authoring/corpus.md) (a row and an
  `onboarding_doc` section) and the onboarding skill's [`SKILL.md`](../../../src/studyforge/skills/onboarding/SKILL.md) document all of this.

## Decisions

- **A manifest key rather than "stop writing one".** The row allowed either. ⭐ A key
  does both: `false` stops writing it, and a path places it. Absent keeps every existing
  corpus byte-identical, so the default is unchanged. Named `onboarding_doc` because it
  is onboarding's document and the manifest is read by every stage.
- **`.md` is required**, because the path doubles as its own `not_material` glob, and
  because the document is Markdown. Glob characters are refused for the same reason.
- **The version rises only when the key is used**, which is `narration`'s rule. `settle`
  carries the rise with it (`W460/2`'s mechanism, unchanged).
- **The moved-file exemption is keyed to a MISSING entry's digest.** The first draft
  accepted any recorded digest. It was narrowed before commit, because a copy of a
  generated file that is still in place is not a move. The test
  `test_a_copy_of_a_generated_file_still_in_place_is_not_taken_as_moved` holds that line.
- **`hand_edited` keeps its `list[str]` shape.** A missing file is a sentence and an
  edited file is a path, so `[]` stays the proof (the onboarding skill's procedure, the authoring guides) and
  no caller changes.

## Findings

- `[structural]` **`W461/1`, `skills/onboarding` `write(regenerate=True)`: a generated file the new file
  set no longer writes is orphaned.** Suppose a corpus sets `onboarding_doc` while
  the reader document still sits at the root. The regenerate writes the new place and
  rewrites `installed.json` without the root entry. The root file then stays on disk,
  and nothing records it, so `hand_edited` cannot see it and `uninstall` will not remove
  it. The row's R10 clause holds, because nothing is WRITTEN at the root. But the stale
  copy is nobody's. Either removing a previously recorded, unedited generated path or
  refusing by name would close it. It was not done here, because deleting on regenerate
  is an R3 argument of its own.
- `[local]` **`W461/2`, the corpus: its reader document's placement lands only when it re-onboards.**
  The corpus's `corpus.json` still says nothing, and its record still lists the root. So
  on this build, `hand_edited('.')` in the corpus prints the root reader document's gap
  sentence until the integration office runs the settle shown above. That is the
  intended reading, and the corpus's next row, but it is a behaviour change the corpus
  will see.
- `[local]` **`W461/3`, `ISO-32/4` stands**: the generated pin check still needs `pytest`, and the
  reader document's install prose does not say so. This is outside this row.

## For dependents

- ⭐ **To place or drop the reader document on an onboarded corpus:**
  `reonboard('.', settle={"onboarding_doc": "<path>.md"})` or
  `settle={"onboarding_doc": False}`, then `.write('.', regenerate=True)`, then
  `hand_edited('.')`, which should print `[]`. A copy already moved by hand, unchanged, is
  rewritten in place.
- ⛔ **`hand_edited` may now return sentences as well as paths.** A caller that treats
  every element as a path is wrong. No caller in `src/` does.
- ⛔ **`corpus_api` is 6.** A test that pins the known set, or the version one above the
  top, moves with it (`test_document`, `test_errors`, `test_version`), as it did for `W460`.
