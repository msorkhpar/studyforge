## Decisions

### ⛔ 1. The destination is `manifest/errors.py`, and the argument is not "somewhere else"

Ruling 135 says it answers *"how does this path leave the root"*, **which is
neither package's subject**. Three homes satisfy that; here is why this one.

| candidate | why not / why |
|---|---|
| stay in `content`, exported | ⛔ **the ruling forbids it** — a surface grows by accident |
| move to `edits` | ⛔ **impossible**: `edits` imports `content`, so `content` importing `edits` is a cycle |
| a new `manifest/paths.py` | ⚠️ defensible. Rejected: one 13-line private function does not need a namespace of its own, and it would add a member to two repository sweeps for no claim |
| ⭐ **`manifest/errors.py`** | ⭐ **the module that already states the rule this function implements** |

⭐ **The load-bearing half:** `ManifestError`'s own docstring already carries R7
in full — *"The message names the field … **never the offending value
itself**"*. `_escape` is what a refusal says **instead** of the value. The
module that states the prohibition owns the sanctioned alternative. It also
depends on nothing, and both refusal sites already import it, so the move added
no edge to the package's dependency graph — the direction is unchanged.

### ⛔ 2. It stayed private, and the underscore's scope is stated rather than assumed

⚠️ **The obvious objection, met head-on:** `content` is a package and
`manifest` is another, so `content/parse.py` importing a private name from
`manifest.errors` looks like the defect in a mirror.

⭐ **It is not, and the asymmetry is that `content` is a SUBpackage of
`manifest`.** What `W40/1` found was `edits` reaching **past a declared
surface** — `content/__init__.py` publishes an `__all__` and a test that says
*"what a consumer needs and no more"*, and `edits` went around it. Nothing is
gone around now: `errors` declares no restricted surface, `content.parse`
already imported from it, and both namers live inside `studyforge.corpus.manifest`.
⛔ **The underscore means "internal to `corpus/manifest`", and that claim is
asserted over the whole of `src/` rather than promised** —
`test_only_this_module_and_its_two_callers_name_the_escaping_phrase`.

⛔ **Making it public was the alternative, and it is the one Ruling 135 names as
the failure mode.** Ruling 101's producer half would then put it on
`manifest.__all__`, and a message-fragment helper would be part of the
framework's contract forever.

### 3. Documentation follows the code

`errors.py`'s summary line and a *Why `_escape` lives here* paragraph;
`content/parse.py`'s **Depends on**; `manifest/__init__.py`'s package table row.
⛔ The bridge's comment in `content/__init__.py` went with the bridge.

## Findings

### W59/1 `[local]` — `permitted_edits` accepts a home-relative path that `content` refuses

⛔ **`edits._reject_forbidden_target` tests `startswith("/")` and `".." in
parts`. It does not test `startswith("~")`**, which
`content.parse._reject_absolute` does — so `~/notes.md` is an accepted
`permitted_edits` target, and `_escape`'s `"begins with a tilde"` arm is
unreachable from that call site.

**Measured** (pinned container, at the merge, 2026-09-10):

```text
parse_edits([{"path": "~/notes.md", …}], content)   ->  ACCEPTED  (edit.path == "~/notes.md")
parse_content({"include": ["~/notes.md"]})          ->  ManifestError, "…must be relative to
                                                        the source root and stay inside it; it
                                                        begins with a tilde…"
```

⚠️ **This is R3 and R7 at once**: `OPS-05` reads this declaration to decide what
it may edit, and a tilde path is both outside the source root and the shape a
home directory lives in. ⛔ **Not fixed here.** Ruling 135 is specific that this
row MOVES one function; adding a branch to a refusal is a behaviour change, and
a behaviour change inside a refactor is the thing the byte-identity proof exists
to rule out. **Measured by me; the underlying code is `W19`'s, unchanged since.**

### W59/2 `[local]` — the twin refusal sentences are identical, and one of them could take the other's `where`

⭐ **`W19` unified the middle clause; the sentence around it is still written
twice.** Measured: the two f-strings differ only in that `content` interpolates
`{where}` where `edits` hard-codes `permitted_edits path`. Passing
`where="permitted_edits path"` makes the emitted bytes **identical** — which is
not a prediction, it is what the harness printed at both sites for all three
faults.

⛔ **Not fixed here**, for the same reason as `W59/1`: `errors` now has an
obvious home for a shared `_reject_escaping_path(pattern, where)` and that is a
second, larger move than the one Ruling 135 authorised. ⭐ **The byte pins this
row added are what would make that move provable**, so it is cheaper after this
one than before it. **Measured by me at the merge.**

### W59/3 `[structural]` — Ruling 139's private scratch is inside the tree `test_coverage.py` walks, and that walk does not honour `.gitignore`

⛔ **Taking Ruling 147's own advice — a clean checkout of the ref, to quote a
base number honestly — turns the suite RED, and the failure names files that
are not the author's.** I added a second checkout at `.scratch/tip` (git-ignored,
per Ruling 139) to read `f898dbb` in a clean worktree. Result:

```text
tests/gate_coverage/test_coverage.py::test_no_fourth_tree_of_readers_exists_unnamed   FAILED
    homeless == [] failed with 44 paths, every one of them '.scratch/tip/…'
tests/gate_coverage/test_coverage.py::test_every_named_tree_is_populated…             FAILED
    assert 44 == 88
```

⚠️ **`document_readers(repository_root())` walks the repository root, and
`.gitignore` is not consulted** — so `.scratch/` is a directory the protocol
tells agents to put working material in and the suite treats as source.
Plain scripts are invisible (my `.scratch/emit.py` and `.scratch/sweep.py` sat
there through every green run); ⛔ **anything that decodes a document is not**,
and a nested checkout contains 44 such files.

⭐ **Why this is marked structural:** it will happen again, to whoever next follows Ruling
147 by checking out a ref to measure it — and it presents as **two red tests
about the gate**, which is a long way from *"your scratch directory is on the
walk"*. ⛔ **It is not mine to fix**: `tests/gate_coverage/` is outside this
row's `Owns`, and whether the remedy is a `.gitignore`-aware walk, an explicit
exclusion, or a rule that scratch checkouts live outside the worktree is a CTO
call between two of that office's own rulings. **Measured by me at the merge,
2026-09-10; reproduced by removing the directory and re-running to green
(3857 passed).**
