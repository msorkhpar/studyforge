## The cause

⛔ **Reproduced, then named from what the run recorded.** The stand-in's page reports each
`input` event with a fire-and-forget `fetch`. `ThreadingHTTPServer` answers each request on its
own thread, and the handler assigned `typed` on arrival. So the LAST report to arrive won, not
the last value typed.

⭐ **The instrument:** a temporary copy of the stand-in numbered each report and recorded the
arrival order in the failure message. That copy was restored from a working-tree copy before
the fix (`md5sum -c` OK, exit 0). Every failure it caught read like this:

```text
AssertionError: the stand-in editor never reached the awaited state: focused=2 typed='w44'
  arrivals=[('1', 'w'), ('2', 'w4'), ('4', 'w449'), ('3', 'w44')]
```

`'w449'` reached the server, and an older report landed after it. ⭐ **All 9 failures in that
loop were this shape:** 6 settled on `'w44'` and 3 on `'w4'`, and each one's arrivals show
report 4 ahead of an earlier one. `W456/6`'s message (*"the stand-in editor never reached the
awaited state"*) is this wait.

⭐ **Why this is not a product race:** the textarea received all four keys. The report of the
fourth reached the stand-in's server, and focus was on the frame (the assertion before the
typing had passed). The defect is in how the stand-in's own server recorded what it was told.
`practice-editor.js` plays no part in the order of the frame's requests to its own origin.

## Decisions

- ⭐ **Number the reports, and do not serialise them.** Chaining each `fetch` behind the last
  would also order them, but it would slow the reports and make the stand-in's timing differ
  from a workbench's. A number costs nothing and makes arrival order irrelevant.
- ⭐ **"At rest" is counted in painted frames, not milliseconds.** A glide moves the page on
  every frame it paints, so a gliding page is never at rest. A loaded machine paints fewer
  frames, and the wait lengthens with it. 20 frames spans the page's 100 ms `activeElement`
  watch about three times at 60 fps. Plant P3 shows the watch is inside that window.
- ⭐ **The anchor check's reset of `focused` is unchanged.** It writes under `editor.lock`,
  and `changed` is built on that same lock.

## Surprises

- ⚠️ **My first load was a full `-n auto` suite looped in parallel, and it filled the per-user
  `/tmp` quota** (about 2 GB per suite run), which also broke other offices' shells and the
  register's merge gate. The register asked me to stop, and I did. The suite loop was killed,
  its basetemp deleted, and all later load was CPU spinners plus one bounded 64 MB writer, with
  scratch kept under 500 MB. The full-suite loop's iterations after the quota filled
  failed with `OSError: [Errno 122] Disk quota exceeded`, and none of them is counted above.
  Killing that suite orphaned one `studyforge serve --port 0` child from its fixtures, serving
  a basetemp I had deleted. I found it by its path in my own scratch and stopped it. It was
  not `:8770`.
- ⚠️ **A pure CPU hog did not reproduce the flake** in 42 runs. The race needs the
  stand-in's server threads to be scheduled unevenly, and disk contention was what did it here.
