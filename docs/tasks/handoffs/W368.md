## What landed

- ⭐ `RailUnit` takes a `key`. A unit row handed one emits `data-unit="<key>"`, escaped as an
  attribute value. A row handed none emits nothing. A container row never carries one.
- ⭐ `generate.navigation` hands each rail unit its contents key, so every rail row on a built
  page is keyed.
- ⭐ `progress-view.js` finds `nav[aria-label="Containers"] li[data-unit]` and sets
  `data-marked="true"` on each row whose key the store holds. It removes the attribute from each
  row whose key the store does not hold. It does this on load and again after each press of the
  read-mark control, so marking or unmarking the page being read shows in its own rail at once.
- ⭐ `chrome.css` draws a tick at the end of a marked rail row, in `--done`, the colour the
  listings' read box uses.

## Decisions

- ⭐ **`data-unit`, not `id`.** The rail's docstring gives the reason: a container page already
  keys its own listing by `id`, and two elements under one id would split `read-mark.js`'s
  `getElementById`. `data-unit` is the attribute the read-mark control already carries. It is a
  script hook, so it is spelled locally and not published in `SURFACE_HOOKS`
  (`render/page/mark.py` explains why).
- ⭐ **Painted in `progress-view.js`, not `read-mark.js`.** `read-mark.js` is outside the surface,
  and `progress-view.js` already reads the store on every page. The repaint after a press waits
  one turn, for the reason the file already gives for its scroll-into-view: `read-mark.js`'s
  listener runs after this one.
- ⭐ **No store, no marks.** With no working store the rail shows no marks, rather than guessing.
- ⭐ **The visual suite marks by pressing the page's own control.** It never writes the store's
  record itself, because that would be a second spelling of the store's format.

## Surprises

- ⚠️ The row's surface (`rail.py`, `progress-view.js`) cannot settle clause 1 by itself. The
  caller that builds the rail has to hand over the key, and a stylesheet rule has to draw the
  mark. See `W368/1`.

## Findings

- `[local]` **W368/1** (surface): the row named `rail.py` and `progress-view.js`, but *"a marked
  unit shows marked in the rail"* also needs `generate/navigation.py` to pass the key (one
  keyword) and `chrome.css` to draw the mark (one rule). Neither file belongs to another row in
  this wave (`W366`, `W370` and `W371` name other files), so I made both edits at their smallest
  and declared them above. The register may rule otherwise.
- `[local]` **W368/2** (recorded, not acted on): the rail's tick is decorative CSS `content`, the
  same as the listings' read box, so a screen reader is not told a rail row is read. The listings
  have the same gap. Closing it would need a visually-hidden word in markup, and that is a
  product-string decision for both regions together.

## For dependents

- ⭐ Any caller that builds a `RailUnit` should pass `key=`. A row without one can never show a
  mark, and the unit tests treat that as the declared default.
- ⭐ `data-marked` on a rail row is set only at read time. A built page is byte-identical whoever
  opens it (R10).
