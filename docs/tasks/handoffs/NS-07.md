## Surprises

⛔ **The fixture's own justification was false, and that is the row's result.**
`tests/support.py` said it builds MPEG-1 at 44.1 kHz *"because that is what the
engine emits"*. The pinned engine emits **MPEG-2 Layer III, 24 kHz, mono**.

⛔ **The consequence was the real defect.** `_read_header` has two arms — MPEG-1
uses `_BITRATES_V1_L3` and 1152 samples per frame, MPEG-2 uses
`_BITRATES_V2_L3` and 576 — and **every frame the suite built took the MPEG-1
arm while every frame the deployment sees takes the MPEG-2 one.** The only arm
that runs in production had never executed against a byte, real or synthetic,
in a suite of five hundred tests. ⭐ **It is correct** — the duration and the
byte count both close exactly, at two different lengths — **but it was correct
untested, which is luck and not evidence.** ⚠️ This is precisely the class of
defect a fake-engine suite is structurally unable to find, and it is the
argument for having run the row at all.

⚠️ **`README.md`'s "recorded measurement" pointed at nothing**, as the row
suspected. What did exist was an *unlabelled* example manifest in `docs/api.md`
carrying real figures — 47276 bytes, 2.952 s, 24000 Hz. ⭐ **My run reproduced
all three exactly**, which is what identifies them as a real reading somebody
took and never labelled, rather than as illustrative numbers.

⚠️ **The suite is 532 tests at `main`@`c4dcb82`, not the "~377" the wave brief
states**, and `kokoro-tts-nvidia` — the container the brief was most emphatic
about not touching — **does not exist on this host any more**, along with the
whole `codesignal` compose project. That constraint was moot rather than obeyed

## For dependents

⛔ **There is no `filename` anywhere in this service's output** — not in the
`/v1/jobs` manifest, not in the stored `.json` record. A join whose right-hand
side is `clips.<speech id>.filename` has nothing to join to until somebody
computes it.

⭐ **The filename is DERIVED: `f"{artifact_id}.{format}"`.** On disk, verified
by listing the named volume inside the container, each artifact is
`<artifact_id>.mp3` beside `<artifact_id>.json` — 64 hex characters plus the
extension, with no segment id in the name.

⭐ **So a position→filename map has three legs, not two:** position → speech id
(the renderer's key) → `artifact_id` (from the manifest, whose `segments[].id`
echoes what you submitted, in the order you submitted it) → filename. ⛔ **Join
on the speech id, never on the position** — order is preserved as a courtesy,
not as the key.

⚠️ **Two more that will bite a consumer:**

- `sample_rate` is **24000**, not 44100, and the audio is mono.
- A `cached` segment carries the same `artifact_id` and status `cached` rather
  than `synthesised`. ⛔ **A map that reads a missing byte count as a coverage
  gap reports a false finding on every re-run** — exactly the "silent success"
  inversion the row was told not to paper over.

⭐ **The artifacts volume `narrate-service_artifacts` was left in place**,
holding the four artifacts this run made. ⚠️ Nothing is lost by removing it —
the reading is in the document and audio is not byte-reproducible — so
`docker volume rm narrate-service_artifacts` whenever somebody decides.
