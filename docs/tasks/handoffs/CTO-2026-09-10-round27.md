## ⛔ The two things `SF-09`'s worked example does NOT carry, and both are traps

⚠️ **The PO is right that `SF-09` is the worked example — mint the key, add it to
`CONTRACT_FIELDS`, assert it in one test — but it is the worked example for a
*document*, and this is a *cache*.** ⭐ **The mechanics transfer; the failure
behaviour does not, and a builder copying `SF-09` faithfully would get it
wrong.**

### 1. ⛔ An unsupported or absent `site_api` does not raise

⛔ **It means the cache is not read: the scan runs, and the cache is rewritten at
the current version.**

⭐ **That IS R9's refusal.** R9 forbids *migration* — reading a document written
at an old version and carrying its content forward under a new one. ⛔ **Nothing
here is carried forward.** The old document is discarded whole and the authority
— the scan — produces a new one. ⚠️ **Raising instead would be the wrong
reading twice over:** it contradicts §5's *"a stale cache is detected and the
scan wins"*, and it converts a git-ignored, derived, rebuildable artifact into a
hard failure — ⛔ **the same defect `Ruling 96` is decided against one section
below, arriving in a different module on the same day.**

⭐ **The instrument already exists and its docstring already names this caller.**
`version.is_supported` is documented as *"the predicate, for a caller that
reports rather than refuses"*. ⛔ **`SF-04` uses `is_supported`, not `check`.**

⛔ **And it is REPORTED, never silent (R6):** the path, the declared version, and
what this build speaks. ⚠️ **A cache that silently re-scans is a cache whose
version key bought nothing** — the whole reason the row was escalated is that a
misread is invisible, and a silent discard is invisible in the same way.

### 2. ⛔ `site_api` is NOT the staleness mechanism

⛔ **It answers *"is this the shape of cache I speak?"* and nothing else.**

⚠️ **The trap is specific and I expect it:** `SF-04`'s acceptance says *"a stale
cache is detected and the scan wins"*, and a builder holding a fresh version key
will reach for it as the staleness token — bump it per scan, compare, re-scan on
mismatch. ⛔ **That makes a contract version into mutable data**, and
`CONTRACT_FIELDS` is a tuple every other contract reads: a member of it whose
value changes per run breaks R9's meaning for all of them.

⭐ **Two signals, two tests.** Schema staleness is `site_api`. Content staleness —
*the tree moved since this cache was written* — is `SF-04`'s own, and it is
`tools/knowledge/index.py`'s problem in a different tree, which is worth reading
before inventing a third answer.
