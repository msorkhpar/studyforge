## Decisions

- ⭐ **The served root is ONE corpus's subtree**, not the whole harness tree. The static mount
  exposes the generated dot-directory at the served root or beside a `corpus.json`, and this
  harness writes one subtree per fixture corpus with no manifest in it — ⚠️ **measured first:
  serving the whole tree answered `404` for every stylesheet and script on the page.** It is
  also the shape `studyforge serve --site` has.
- ⭐ **`client=` is `routes.run.CLIENT_PATH`**, the framework's one spelling, so the tag the
  static mount inserts and the path the namespace answers cannot come apart in this harness any
  more than they can in a real instance.
- ⭐ **`Browser` gained a `profile_root` ARGUMENT rather than the fixture gaining a lock.** A
  lock would have serialised every office's launches to fix a test's own bookkeeping; one
  caller naming its own directory cannot reach another caller at all.
- ⭐ **The transport's controls are joined to the trail on POSITION, never on a label**
  (`W105`'s form): two of them are a single typographic character and the speed control's text
  is its whole option list, so a label join would have read *"the keyboard reaches one of
  four"* about a transport it reaches all of — a defect reported against the page instead of
  against the join.
- ⭐ **The index's scriptless resolution is NARROWED to the pages this harness wrote**, and the
  narrowing is stated in the check. `site` writes one unit page per fixture corpus, so most of
  a contents tree points at units nobody built here; whole-site resolution is
  `tests/studyforge/cli/test_serve_floor.py`'s over a real `studyforge build`.
- ⭐ **The accessibility record is THIS DOCUMENT** (below), not a new file. `QA-02` owns the
  record and this repository has no records directory; ⛔ minting a convention for one file was
  not this office's to decide, and the brief's instruction was to mint nothing.

## Surprises

- ⛔ **The first browser reading of the panel found a REAL keyboard defect in it, which is
  exactly what `W417` was minted to make possible.** `practice.js` argued — in a comment — that
  focus follows the control that goes away, and it was right for the end of a run and wrong for
  Stop: the handler disabled Stop *before* asking whether the panel held focus, a disabled
  element drops focus to the document at once, and the run then settled with focus already on
  `<body>`. ⭐ A keyboard reader who pressed Stop was returned to the top of the page. Fixed
  here (`QA-02/1`), and the check that finds it is a browser reading rather than a grep.
- ⚠️ **`W419`'s defect was in TWO fixtures, not one.** The row names
  `tests/visual/test_browser.py`; `tests/visual/test_page_lifetime.py`'s `launch_under` is the
  same five lines with a different name, globbing the same way. ⛔ Fixing one and not the other
  would have closed the row and left the hazard.
- ⚠️ **An element with no layout box answers `innerText` with its WHOLE text**, hidden children
  included — ⛔ the same blindness `SF-24/3` names, arriving in a TEXT reading rather than a
  geometry one. **Measured** on the narration transport's `role="status"` region, whose computed
  `display` is `none` at rest: its three mutually exclusive state sentences came back
  concatenated. `QA-02/5`.
- ⭐ **`run-client.js` needs nothing but an `http:` origin** — `available()` reads
  `location.protocol`, `fetch` and `TextDecoder` — so the panel's whole behaviour is reachable
  without a container, a runner or a corpus. That is why this row cost a harness module and not
  a toolchain.
