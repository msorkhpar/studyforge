## Decisions

1. ⛔ **`execute/editor.py` and one method of `serve/routes/runs.py` changed, and the brief allowed
   `execute/` only for a name.** ⭐ **The acceptance cannot be met without it.** `editor_from` refused
   any editor holding two binds inside the corpus (*"two mounts … name no one folder"*), so an editor
   binding the sources AND `practice/` answered NO editor, and every frame went dark. The alternative
   was to bind `practice/` alone, but that drops the reading-floor sources the row says stay where they
   are. ⭐ The change is the smallest that keeps both: the index still publishes one folder (the first
   bind by base), and a practice opens through the bind that holds its file. The settings are written
   on that bind's host side, and a path no bind holds is still `None`. ⭐ The `serve/` change owed a HOST
   reading of `tests/studyforge/cli/test_serve_process.py`, which was taken (Gates).
2. ⭐ **The practice bind is `<editor.workspace.container_path>/<PRACTICE_DIRNAME>`.** The directory is
   read from the one constant `exercise.bundle.Places.workspace` and the adapter share. The container
   path is composed from the contract's own workspace root. The contract has no slot for a second
   per-corpus bind (`W445/3`). The bind is refused if the contract already mounts something there, and
   omitted when the sources' root already holds the practice workspaces.
3. ⭐ **The tag lives in `.studyforge/execution/runner.env`, which the command names with
   `--env-file`.** `generate` stays pure, because the tag is a function of the prime on disk and exists
   only after `write`. ⚠️ **`EDITOR_IMAGE` is still the reader's to export, as before.** Recording it the
   same way was not asked for, and the corpus's running editor is the unprimed build while
   `EXECUTION.md` prints `--prime` for both.
4. ⭐ **The skill still imports nothing that can start a process.** `test_init.py` asserts this over
   every module, so `record_runner` takes the one process as `ask`. It decides the argv, the checkout,
   the validation and the bytes. The component's `--print-tag` hashes files and starts no Docker, as
   measured.
5. ⭐ **The runner's uid is the editor block's `runs_as.compose_value`.** The runner block's `run_value`
   is shell syntax (`$(id -u):$(id -g)`) that compose cannot evaluate (`W445/2`).

## Surprises

- ⛔ **The end-to-end proof cannot run beside the user's session under the corpus's own `source`.**
  Both container names derive from `source`, and serve looks them up by those names. With the user's
  editor and runner up, a copy under the same `source` would collide with them or be probed as theirs.
  ⭐ **So the scratch clone's `corpus.json` `source` was renamed** (`iso-8583-jpos-tutorial-w445`, in the
  scratch copy only). Every container, volume and project name was then its own. The editor's host port
  came from a compose override file (`ports: !override`), which is the only non-generated input. It is
  needed because the contract's host port is a literal (`SK-09/4`) and the user's editor holds it.
- ⭐ **The recorded tag equals the corpus's hand-scripted record**: `record_runner` over the scratch clone
  wrote the same tag as `docs/studyforge/runner.json` at `fe6ac31`, and that image was already built.
- ⚠️ The state namespace answered no `practices` for the renamed scratch copy, whose pages still carry
  the old `data-corpus`. ⭐ The breakdown was read where the page reads it: the Submit's own stream,
  whose `--- case … ---` lines are `AX-02`'s per-case verdicts.

### ⛔ The integration office — regenerate the first corpus and bring it up

From the corpus checkout, with the framework at this branch's merge and the sibling at its pin:

1. **Regenerate and record**, in one Python call from the corpus root. The sibling path is relative
   to the corpus:

   ```python
   import subprocess
   from pathlib import Path
   from studyforge.corpus.manifest import parse
   from studyforge.skills.execution import generate, record_runner, write

   root, toolchain, narration = Path("."), Path("../code-server-toolchain"), Path("../narrate-service")


   def ask(argv, cwd):
       done = subprocess.run(
           argv, cwd=cwd, stdin=subprocess.DEVNULL, capture_output=True, text=True, timeout=60
       )
       return done.returncode, done.stdout


   made = generate(
       parse((root / "corpus.json").read_text(encoding="utf-8")),
       editor_text=(toolchain / "consuming.json").read_text(encoding="utf-8"),
       narration_text=(narration / "consuming.json").read_text(encoding="utf-8"),
       root=root,
   )
   write(made, root)
   record_runner(made, root.resolve(), toolchain.resolve(), ask=ask)
   ```

   ⭐ The diff to expect: `compose.yaml` gains `../../practice:<workspace>/practice` on the editor and a
   `runner` service; `EXECUTION.md` gains the runner build, the record step and the one command;
   `.studyforge/execution/runner.env` is new and holds the same tag as the hand-scripted
   `docs/studyforge/runner.json`. ⭐ **That hand-scripted file is now redundant.** Retiring it is the
   corpus's call; nothing generated reads it.
2. **Bring it up** with the command `EXECUTION.md` prints, `EDITOR_IMAGE` exported as before:
   `docker compose --env-file .studyforge/execution/runner.env -f .studyforge/execution/compose.yaml up -d --wait`.
   ⛔ **The user's session already runs `studyforge-iso-8583-jpos-tutorial-editor-1` and
   `studyforge-runner-iso-8583-jpos-tutorial`, which were started by hand.** The command claims both
   names. Replacing them is the user's session's call and not the office's.
3. **Submit through `serve`** on a pilot practice, with the reference in place and then the starter.
