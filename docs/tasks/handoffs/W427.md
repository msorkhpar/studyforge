## Decisions

⭐ **`frame-src` is asked PER RESPONSE, not fixed at bind.** An editor comes up and goes away
while this process serves, so a policy decided once would be wrong for the rest of the run.
The fork cost is bounded by `EditorProbe`'s own TTL cache, not by how often the policy asks.

⭐ **The origins come off the run namespace's own `Runs`, carried on the registered route.**
Building a second `Runs` to ask would have given the policy a second probe and a second cache
per corpus. Reading it back out of the namespaces mapping is what makes the replaceable
`--site` seam (`W386`) behave correctly: a seam that registers no run namespace returns
`None`, and the policy stays `'none'`.

⭐ **An origin is re-validated before it reaches the header.** `Runs.origins()` reads from
`docker inspect`, so it is input. `frame_origin` refuses anything carrying a space, a comma,
a `;`, a quote, a `*`, a `@` or a backslash — a space or `;` is how a second directive would
be forged into the header — and refuses any host `ALLOWED_HOSTS` does not name.

⛔ **The client was not touched.** `render/assets/practice.js` already builds the frame
correctly; the page was never the defect.

### ⛔ The host trap, and the design call it forced

⚠️ **An editor authenticates with a `SameSite=Lax` session cookie. A PORT is not part of a
site but a HOSTNAME is.** So a page reached as `localhost:<page>` framing an editor at
`127.0.0.1:<editor>` is CROSS-site: the cookie is withheld, the frame shows a login form that
never succeeds even with the right password, and ⛔ **nothing in the browser says why.** Our
`ALLOWED_HOSTS` accepts `127.0.0.1`, `localhost`, `::1` and `[::1]`, so a reader could reach
that state by typing a different spelling of the same machine.

⭐ **Chosen: the editor is admitted only to a page reached by the editor's OWN host, and an
editor withheld from a host is SAID ONCE in the server's log**, naming the origin, the host
the reader used, and the host to use instead. `framable` decides; `response_headers` says it.

⛔ **Rejected: narrowing the `Host` allow-list while an editor is configured.** It is the
remedy the extraction source used, and the reason it is wrong here is that our editor is
DISCOVERED rather than configured: the allow-list would then narrow because a CONTAINER came
up, so a reader's whole site would start answering `403` to a spelling that worked five
minutes earlier, with no act of theirs in between. ⭐ **Only the frame is withheld, the rest
of the site is served unchanged, and the log carries the remedy** — asserted by
`test_the_site_itself_is_still_served_to_a_host_the_editor_is_withheld_from`.

⭐ **Host EQUALITY subsumes the literal rule and is strictly better.** Requiring the origin's
host to be `127.0.0.1` would refuse a `localhost` page framing a `localhost` editor, which is
genuinely same-site and would have worked. Equality refuses exactly the mismatches.

⛔ **`connect-src` stays `'self'`** — the framed workbench talks to its own origin over its own
websockets and needs nothing of ours. Asserted in the composed policy.

⭐ **No drift guard is needed and none was added, and that is a property of the design rather
than an omission.** The policy is COMPOSED from `POLICY_HEAD`, one `frame-src` and
`POLICY_TAIL`; it is never patched by replacing a literal, so the failure a drift guard exists
to catch — a replacement that silently matches nothing — cannot occur.
`test_the_composed_policy_carries_exactly_one_frame_src_and_one_frame_ancestors` is the canary
that keeps it that way.

- `[structural]` — ⛔ **The frame will now LOAD, and what it loads is a PASSWORD PROMPT.**
  Measured on the wire: `GET http://127.0.0.1:8443/?folder=…` answers `302` to
  `./login?folder=…`, and the running editor container is configured `--auth=password`. ⭐ So
  after this fix the practice panel shows code-server's login form inside the slot rather than
  the editor. ⭐ **The same-site half of this is now handled here** — see the host trap under
  Decisions — so a reader on `127.0.0.1` can at least log in; ⚠️ **but a reader should not have
  to**, and a browser that blocks third-party cookies outright may still refuse the session.
  ⛔ **This is the toolchain's question, not the framework's**: how
  the editor container is started belongs to `code-server-toolchain` (`E12`), and the
