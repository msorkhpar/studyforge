### 2. The reader chooses the theme (stage 2)

⭐ **A three-state control in the masthead of every page kind**, written once in
the shared skeleton. *System* is a stored value AND what an absent record means,
so the two can never disagree; a two-state control could only record "dark" or
"not dark", which freezes the page for a reader whose machine turns dark at
sunset.

⭐ **The store is `study-progress.js`'s DISPLAY record**, whose own docstring
declared it independent of the read marks and named a later consumer. This is
its first. Nothing else touches `localStorage`.

⛔ **The flash is prevented in the head, not in the bundle.** Every part of
`page.js` is deferred and runs after the first paint, so a stored dark choice
applied there would show the light page for a frame on every navigation. The
skeleton carries a synchronous boot in `<head>`, which is why a rendered page
now has two `<script>` tags and one of them is inline. ⚠️ The boot spells the
store's key, field and version a second time because it must run before any
bundle exists; `test_theme` reads BOTH spellings out of their own files and
holds them equal, refuted by each of the three changed by one character.

⭐ **`theme-color` stays honest.** The skeleton ships one per system scheme. A
reader who has chosen has made those media queries wrong, so the chosen one
widens to `all` and the other becomes `not all`; choosing *system* restores both
exactly as the skeleton wrote them.

### 3. The page uses the window (stage 3)

⛔ **The defect, measured rather than described.** `chrome.css`'s wide shape
carried `max-width: var(--page-max)` — `110rem`, 1760px — together with
`margin-left: 0`. ⭐ Below 1760px that is invisible; above it the whole grid
stops growing and stays against the left edge. ⚠️ At 2560px the rail, the 1172px
reading column and the 256px aside filled the left two thirds and the last 820px
of the screen was blank, which is what the user was looking at.

⭐ **The repair, and it is a MOVE rather than a bigger number.** A larger ceiling
on `body` reproduces the same dead strip one display along, so the bound came
off the page and went onto the thing it was written to protect:

- `body:has(rail)` in the wide shape declares `max-width: none`. ⛔ **Written
  out, not omitted** — the narrow shape bounds the same element at
  `calc(var(--measure) + 4 * var(--gutter))`, and with the line simply deleted
  the wide page laid out at that constant on a 3840px window. Measured.
- `body:has(rail) > main` takes `max-width: var(--page-max)`, and `--page-max`
  moved to `180rem`. That is 2880px: past the widest window this row measures,
  so the reading column takes all the slack at 1280, 1440, 1920 and 2560, and a
  4K display still cannot stretch one line of code across itself.

### 4. One shape that works on every display (stage 4)

⛔ **The shell is BOUNDED AND CENTRED, and that is one shape rather than a rule
per display.** `chrome.css`'s wide rule gives `body` `max-width: var(--page-max)`
together with `margin-left: max(0px, (100% - var(--page-max)) / 2)`. Below the
ceiling the inset floors at nothing and the page fills the window exactly as
stage 3's did; above it the shell holds the ceiling with EQUAL margins either
side. ⭐ **Equal is the whole clause** — a dead band is spare room that is all on
one side, so a shape whose margins are equal at every width cannot have one. The
rail, the reading column and the outline are all inside the shell, so the
reader's menu centres with the reading instead of clinging to the glass.

⛔ **The bound on `> main` is GONE, and that is a removal rather than an
oversight.** With the shell held at `--page-max` the surface is always the shell
less the rail, the aside and three gutters, so a second declaration of the same
token could never bite — and a ceiling that cannot bite is a second place a
reader would go to move it. One ceiling, in one place, asserted as such.

⛔ **`--page-max`: `180rem` → `110rem` (1760px), argued FROM BOTH SIDES.** The
shell holds the rail (17rem), three gutters and the aside (16rem), so the reading
surface is the shell less 588px — 1172px at this ceiling.

- ⭐ **From below, the first corpus's own code blocks.** The ISO build ships
  **218** of them; the width each needs before it scrolls horizontally was read
  in a browser, and the share that would scroll at each candidate is: a 1012px
  surface (`100rem`) **20.2%**, 1172px (`110rem`) **8.7%**, 1252px (`115rem`)
  **4.6%**, 1332px (`120rem`) **3.2%**. ⛔ The first 160px of ceiling buys 11.5

  at `120rem` it is 452px, nearly two. ⚠️ That space growing without limit is

⛔ **The page with no rail takes the SAME inset** (`W333`). Its own bound is the

## Decisions

- ⭐ **The bands are per ink, not one band for all three.** One band wide enough
  to hold a body ink and a faint ink is too wide to hold either: stage 1's
  4.5–9.0 admitted 5:1 body text, which is what shipped and what was rejected.
  Each band is centred on the corresponding ink of the user's own page.
- ⭐ **`RULE_CHROMA` moved from 0.12 to 0.20, and it is not a loosening.** Stage
  1's figure was measured against a warm grey. The slate scale is a TINTED
  neutral whose blue channel leads by about a seventh, so 0.12 would refuse the
  reference's own hairlines. The rules gained a SECOND bound instead — the
  warmth bound — and a red hairline is caught by that one at any chroma.
- ⭐ **The control is inside `<header>`, not an eleventh child of `<body>`.**
  `chrome.css` spans the rail over the body's ten top-level positions and the
  unit mirror reads that number back; a sibling would have moved the rail.
- ⭐ **Its rules live in `notes.css`, not `chrome.css`.** `chrome.css` reached
  409 lines against R11's 400. The seam is the four parts' own: `notes.css` is
  what the page tells the reader and what it offers them, and it already holds
  the read control. ⛔ A split at a named seam, never a trim (Ruling 261).
- ⭐ **The control is NOT gated on storage working**, where `read-mark.js` is. A
  mark that is not kept is a lie; a theme that is not kept is still a theme for
  as long as the reader is on the page.
- ⭐ **No per-language inks, and that is a refusal rather than an omission.** The
  brief asked for the route planner's java/python/kotlin inks on code fences and
  language chips. ⛔ Painting them means a fixed list of language names in a
  framework stylesheet, which is R1 — and `code-highlight.css` says in its own
  docstring that the framework ships no corpus's languages. The energy the inks
  were for is carried by the amber accent and a saturated pen case instead. See
  `W388/9`.
- ⭐ **The display face is unchanged.** The brief offered Overpass; the second
  reference uses a plain UI sans and this row's settling clauses are the palette
  and the control. See `W388/8` for what was measured, so the next row need not
  re-derive it.
- ⭐ **(Stage 3) The ceiling moved instead of growing.** Raising `--page-max` on
  `body` would have made every named width green and left the identical defect
  at 3840px. ⛔ A bound that reproduces the defect one display along is not a
  repair, so the page is unbounded in the wide shape and `main` carries the
  bound. The token keeps its name because the palette already declares it and a
  reader still moves the ceiling by changing one number in one file.
- ⭐ **(Stage 3) The prose cap stayed at `76ch`, and the argument is the
  measurement.** The brief asked for a cap argued from characters per line
  rather than inherited; the count says the inherited number is already the
  widest one inside the row's own 75–100 band. ⛔ Widening it to `77ch` would
  ship a 102-character line, and moving the band to admit that is moving the
  goalposts of the clause the cap exists to satisfy.
- ⭐ **(Stage 3) A paragraph does NOT fill the reading column at 1920 and
  above**, and that is the cap doing its job rather than a defect left behind.
  Filling the 1972px column at 2560 would mean about 230 characters to a line.
  ⚠️ What the user asked for — *the width is used* — is answered by the rail on
  the left edge, the aside on the right edge and the scanned blocks (code,
  tables, figures) spanning the surface; the running text keeps a measure. ⛔ If
  the user wants the paragraph itself wider than 100 characters, that is a
  decision about reading, not a defect, and it is theirs.
- ⭐ **(Stage 3) The new readings went in a module of their own.**
  `test_reading_room.py` was at 531 lines against R11's 600 and every clause in
  it is taken at ONE wide viewport — which is precisely why it could not have
  caught this. The seam is *is this readable* against *does it use the window*
  (Ruling 261).

- ⭐ **(Stage 4) ONE SHAPE, not a rule per display.** The alternative on the
  table was a breakpoint — fill the window below some width, switch to a fixed
  column above it — and it was refused because it is two layouts a reader can
  see the join between. ⛔ `max-width` with a centring inset is one declaration
  pair whose behaviour below the ceiling and above it differs by arithmetic
  rather than by a second rule, and `min(window, ceiling)` is the whole of what
  the tests assert.
- ⭐ **(Stage 4) The inset is WRITTEN OUT rather than left to `margin-inline:
  auto`, and `W333` is the reason.** Centring is what `auto` does, but `auto`
  says nothing a second rule could agree with — and the page with NO rail is
  bounded by the measure rather than by the ceiling, so centring THAT one puts
  it somewhere else entirely. ⛔ Both shapes take the same expression, and
  `W333`'s own clause holds the two EQUAL rather than each to a typed value.
- ⭐ **(Stage 4) The ceiling came back to the shell and `> main`'s bound went
  away.** Keeping both would have been two ceilings for one question, and the
  inner one could never bite. ⛔ A declaration that cannot bite is worse than
  none: it is a second place a reader would go to move the ceiling, and moving
  it there would do nothing.
- ⭐ **(Stage 4) `110rem` is argued from a CURVE, not from a preference.** The
  share of the first corpus's 218 code blocks that would scroll falls 20.2 →
  8.7 → 4.6 → 3.2 across `100`/`110`/`115`/`120rem`. ⛔ Past the knee each extra
  pixel of ceiling buys a diminishing share of one corpus's code and costs a
  pixel of open room beside every paragraph of it — which is the thing the user
  rejected.
- ⭐ **(Stage 4) The cap was settled on the CORPUS, because the fixture
  saturates.** Above `80ch` the fixture paragraph's line breaks stop moving and
  every wider cap reads the same count, so a cap chosen there would have been
  chosen against a plateau. ⛔ The reading that decided is the worst paragraph of
  each of the first corpus's 41 unit and section pages, scaled by the measured
  2.8% difference in how the two environments resolve `ch`.
- ⭐ **(Stage 4) `LONGEST_LINE` moved from 100 to 110 BEFORE the cap was chosen,
  and that order is the argument.** A bound moved after the fact to admit a cap
  is not a bound. ⚠️ `W388/13` named these two numbers as ones that move
  together or not at all, and the user's fourth reading is the ruling it asked
  for.

## Surprises

- ⚠️ **Stage 1's own handoff quoted a figure that its files do not carry.** It
  said the palette that shipped read "15.3:1 in dark", and `15.3` was planted in
  two checks as the refutation. Recomputed from `W362`'s actual file values,
  that pair reads **11.60:1** — inside the new bands. The reading that really
  breaks the ceiling is `W362`'s LIGHT pair, 14.36:1, and that is what the
  refutation now uses. ⛔ The `15.3` was a browser reading of the highlighted
  passage, not of body text on the ground.
- ⚠️ **The rail on the index stopped overlapping the list**, because the masthead
  grew by the control's line and the index's rail is only as tall as the courses
  it names. Stage 1's reading compared the rail with `main` alone and passed on
  the height of a heading; it now compares it with the content COLUMN — masthead
  through list — and asserts the rail starts level with the masthead.
- ⚠️ **`innerText` respects `hidden`**, so the masthead reading in
  `test_no_script` saw the control with scripts on and not with them off, and
  reported the masthead as script-dependent on all eight pages. The control is
  excluded by its hook, not by its words.
- ⚠️ **(Stage 3) Deleting a `max-width` is not releasing it.** The wide shape
  refines `body`, which the narrow shape has already bounded at
  `calc(var(--measure) + 4 * var(--gutter))`. With the declaration simply
  removed, the "spanning" page laid out at that constant on a 3840px window —
  narrower than the defect it was meant to cure. `none` is written out, and
  asserted as `none`.
- ⚠️ **(Stage 3) THE HOST AND THE PINNED IMAGE DISAGREE ABOUT LINE LENGTH BY ONE
  STEP.** The same cap on the same page lays out 96 characters on this host's
  browser and 100 in the image, at every width above 1280. ⛔ A cap chosen on a
  host reading — `78ch`, which reads 100 on the host — ships a 102-character
  line in the environment that decides, and the pinned gate caught exactly that
  before this branch was committed. ⭐ Every figure recorded for the cap is the
  image's.

- ⚠️ **(Stage 4) `W333`'s clause and stage 4's shape were in direct conflict,
  and the clause was the thing that had to be restated.** `test_page_start.py`
  asserted that the page with NO rail *does not move when the window widens* —
  which was a PROXY for that row's real settling clause (*the page without a
  rail starts where the page with one starts*) and was equivalent to it only
  while the page with a rail was pinned to the window's left edge. ⛔ With the
  shell centred, BOTH kinds move; the restated clause compares the two kinds at
  three widths and is strictly stronger, because it cannot be satisfied by a
  page that simply never moves. See `W388/14`.
- ⚠️ **(Stage 4) THE TWO ENVIRONMENTS DISAGREE ABOUT `ch` ITSELF, and that is
  the mechanism behind stage 3's "one step" surprise.** `76ch` resolves to 813px
  on this host and 836px in the pinned image — 2.8% — so the same cap lays out
  about three more characters in the image on a line of this length. ⛔ Stage 3
  recorded the symptom; this stage measured the cause, which is what let a HOST
  reading of the corpus be scaled into an image figure rather than discarded.
- ⚠️ **(Stage 4) A CORPUS CANNOT BE READ IN THE PINNED IMAGE**, because only the
  checkout is mounted there. ⭐ So the instrument that actually settled the cap —
  41 real pages rather than one fixture paragraph — is a host instrument, and
  the gate that guards it afterwards is a fixture one. ⛔ A gate that only ever
  sees the fixture cannot see a real corpus's worst paragraph; that gap is named
  in `W388/15` rather than papered over.

## For dependents
