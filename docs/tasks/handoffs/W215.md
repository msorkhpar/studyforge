## What landed

### The seam, in the order Ruling 99 requires

1. **The plan declares the directory.** `attachments` is a fifth unit media kind, so
   `studyforge plan` claims `…/unit-NN/attachments/` for every declared unit, `plan`'s `media
   units` line lists it, and each profile's ignore rules cover it — all of them from
   `UNIT_MEDIA_DIRNAMES`, which every one of those readers already asked rather than retyped.
2. **The renderer emits the link.** A served section carries the archive's own `attachments`
   entries, and `render.page.section` renders one `<li><a href=… download>` per entry, after the
   section's material and outside its `<section>`.
3. **The media pass copies it.** `generate.media.references` yields each attachment, so the copy
   lands at `UnitLocations.media_dir("attachments") / <basename>` — the same call the href is
   built from, which is why the file is beside the link by construction rather than by two
   modules agreeing.

⭐ **The live witness is closed.** `depth1`'s unit 2 declared `media/small-graph.ttl` and nothing
read it. The built page now carries `<a href="attachments/small-graph.ttl" download>`, the build
writes the file there, and the plan's golden claims the directory it lands in.

### `assets` are NOT linked, and that is the row's "say which, and why"

⛔ **Only `attachments`.** The two lists share one entry vocabulary and differ in what they are
for: an **asset** is a file a *block* already names — `depth1`'s `media/diagram.svg` is the
`image` block's own `src` — so the page reaches it through that block and the media pass has
copied it since `SF-37`. Listing assets as downloads too would offer the reader the diagram they
are already looking at, and would put a second href on the page for a file that already has one.
⭐ An **attachment** is a companion file no block names, which is precisely why nothing read it.

⚠️ **An asset no block names is unreachable today and stays unreachable** — it is not copied
(nothing emits a reference to it) and not linked. ⭐ The remedy is in the archive document: such
a file is an attachment, and [`docs/authoring/archive.md`](../../authoring/archive.md) now says so where an adapter author
reads it. ⛔ Not enforced in `src/`: the framework would have to walk the assets against the
blocks to notice, and `studyforge validate` is where a corpus-shaped check belongs — recorded as
`W215/3`.

### The rider — `OPS-05/5`

⛔ **These files do NOT join R3's third category, and `content.include` is unchanged.** The
`content` policy classifies **the source material** — whether a file's prose is read *into* the
archive — and an asset or an attachment is already *in* the archive, written by the adapter. Its
placed copy is the build's own output, which R3 tells from a reader's material by path
(`generate.Footprint`, W202 answer 2). So no `reads_as_content` predicate, no manifest parser and
no `validate.nondestructive` clause changed, and none needed to. The sentence is in
[`docs/authoring/archive.md`](../../authoring/archive.md), in the new section where the fields are defined.

### `unit.json` is `api` 2

⛔ **Bumped rather than widened** (R9). `unit.served` refuses a shape it does not know, and the
two answers it must not conflate are *"this document was written before sections carried
attachments"* and *"this unit has no companion files"* — the argument that module already makes
about `video`. ⭐ Nothing under `src/` writes a `unit.json`, so what the bump refuses is a
document some other tool wrote; it is refused, never migrated.

## Decisions

- ⭐ **`attachments` is a fifth media KIND, not a new mechanism.** It gets a directory, an
  ignore rule, a plan line and a weight in the footprint because it is generated media that
  lands beside a page. Everything that already walked `UNIT_MEDIA_DIRNAMES` picked it up with no
  edit — the plan's claims, both profiles' ignore lines, `validate.paths`, and
  `corpus.media.measure`. ⛔ That last one is deliberate: an attachment is bytes in the
  repository, so a limit that did not weigh it would be a limit cleared by not looking.
- ⭐ **One word from the archive field to the directory name.** The archive's key, the served
  section's key, the placed directory and the plan's line are all `attachments`. A fifth spelling
  would have been a fifth thing to keep in step.
- ⭐ **`UnitLocations.directories` now asks `media_dir` per kind** instead of listing its own
  fields. The footprint weighs exactly that tuple and the ignore rules cover exactly those names;
  a kind that reached one list and not the other is the failure `corpus.media.footprint` says its
  verdict rests on not happening.
- ⛔ **The region is per SECTION, not per unit.** The archive files attachments against the
  document they came from, exactly as it files a `video`, and a unit may hold several documents.
  Collapsing them per unit would drop the later ones or invent an order.
- ⛔ **A malformed entry is REFUSED, by both halves.** `local` goes through the same gate every
  file reference on a page passes (`sourcepath`), so an absolute path, a path leaving the source
  root, and a name that is empty are refused — by the renderer as a `PageError` and by the copy
  pass as a `BuildError`. ⚠️ The alternative, dropping the link quietly, would tell a reader
  nothing about a dataset the archive says it fetched. ⛔ A remote `src` on a *block* is the
  different case and still skipped: there the page offers a link the reader chooses to follow,
  and there is nothing on disk to place.
- ⭐ **The region's prose is one word, `Files`, and it is in a template** (R13). The link's text
  is the corpus's own filename and nothing this framework wrote (R1).
- ⭐ **No new class name.** The region uses `data-section="attachments"`, the shape
  `pending-practices.html` and `narration-gap.html` already use, so the published class contract
  is untouched and no stylesheet owes it a rule.
- ⭐ **A SPLIT AT A SEAM, named** (R11, Ruling 261). `tests/studyforge/generate/test_media.py`
  reached 620 of the 600-line test ceiling when this row's cases landed in it. ⛔ The line taken
  is the one `generate.media`'s own docstring draws — *"`references(document)` when only what a
  page will reach for is wanted"* — so what the PASS does to a disk stays in `test_media.py` and
  what a page will reach for, which opens no file, is `test_references.py`. ⚠️ `FIGURE` and
  `image()` moved to `corpora.py` rather than being spelled in both.

## Surprises

- ⚠️ **The plan, the ignore rules, the footprint and `validate`'s declared-path enumeration all
  picked the new kind up with no edit**, because each had already been written to ask placement's
  tuple. ⛔ What did have to change was prose that had counted the kinds — two module docstrings,
  two test comments and one test's own name — and one test that typed the four names instead of
  asking for them. ⭐ Each is now written so a sixth kind changes nothing.
- ⛔ **`tests/studyforge/generate/test_media.py` rewrites one fixture document per case**, and
  five of those cases are about *block* references on the unit that also declares the attachment.
  They now clear it explicitly (`rewritten(..., attachments=[])`) rather than assert around a
  file they are not about.
- ⭐ **`test_site.py`'s existing sweep was already the end-to-end witness.** *"Every `src` and
  `href` a built page emits resolves to a file the build wrote"* covers `<a href>` too, so the new
  link was asserted by an existing clause the moment it existed.

## For dependents

- ⭐ **`unit.json` is `api` 2**, and a served section carries a seventh key, `attachments`, always
  written and `[]` when the archive declared none. A consumer that pins `api == 1`, or that
  compares a section's keys against a list of its own, needs the new value.
- ⭐ **`studyforge plan` claims one more directory per unit**: `…/unit-NN/attachments/`, `claim`
  until a build copies a file into it. Any consumer that counted a plan's paths per unit counts
  one more.
- ⭐ **`ATTACHMENTS_DIRNAME` is on `studyforge.corpus.placement`'s surface**, and
  `UnitLocations.attachments` is a field. ⛔ **`UnitLocations` takes six positional fields now**
  — anything constructing one directly (rather than asking a profile) must pass it.
- ⚠️ **An adapter needs no change.** The archive format is unchanged: `attachments` was already a
  required key and its entries already had this shape. What changed is that something finally
  reads them. ⛔ **`W214` is still open on its own half** — where an adapter is told to *write*
  a unit's media — and nothing here answers it.
- ⭐ **[`docs/authoring/archive.md`](../../authoring/archive.md) now defines both lists**, including which one a file belongs
  in and why neither is a `content` declaration. That is the page to cite rather than re-deriving
  the distinction.
