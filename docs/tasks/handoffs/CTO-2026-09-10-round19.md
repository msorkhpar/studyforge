# ⛔ Ruling 60 — finding 61 (`PO-…-round18/1`): `validate` corroborates `exercises` **against the archive**

## The defect, reproduced with a control that was run negatively

⛔ **I did not take this on the PO's word.** Run pinned, in the image:

```
baseline exercises=False
CONTROL A — unmodified fixture (must be clean on BOTH):
   validate ok=True  findings=0  []
   fixture_checks violations=[]

poisoned exercises=True, practices on disk = 0
CONTROL B — the flag lies (the defect):
   validate ok=True  findings=0  []                    ⛔ validate is SILENT
   fixture_checks violations=['exercises-flag']        ⭐ the fixture checker is LOUD
```

⭐ **Control A is what makes B evidence**: the clean corpus is clean on both
instruments, so B's single hit is the poison and not the fixture. ⛔ **A corpus
that declares `exercises: true` and holds no practice anywhere passes
`studyforge validate` today.**

⚠️ **W7's shape, in the front door.** `validate` is the adapter's definition of
done (R2) and is the tool an integrator is told to trust; the fixture checker is
not shipped. ⛔ **The gate an outsider meets is the weaker of the two.**

⭐ **And it is confirmed from outside the framework.** PO-Integration reached the
same hole independently as `Q22`, on ISO rather than on a fixture — ⚠️ **and it
fails in the flattering direction**, which is why nobody found it by being
surprised.

## The ruling, in five parts

**1. Where.** A corpus-level `check_exercises_flag(walk)` in
`src/studyforge/validate/structure.py`, appended to `structure.CHECKS`. ⛔ **Not
a new module** — it is one comparison over the walk, and `structure.py` already
owns every corpus-shape check including `check_practice_counts`.

**2. Rule id.** `RULE_EXERCISES_FLAG = "exercises-flag"` — ⛔ **the same spelling
the fixture checker already uses.** A third vocabulary for one rule is the defect
`FND-09` was opened against; do not mint one here.

**3. Both directions, symmetric.** `bool(manifest.exercises) != (practices > 0)`.
⛔ **`false` with practices present is not the harmless half** — it silently
discards graded material the adapter went to the trouble of emitting. ⚠️ **And
`validate` must never be weaker than the unshipped fixture checker**, which is
symmetric today.

**4. ⛔ The counting source is the ARCHIVE, not the declaration — and this is the
part the PO and the fixture checker have differently.**

⚠️ **`tests/fixture_checks/__init__.py:140` sums *declared* counts**
(`unit.get("practices")`). ⛔ **Corroborating one claim of the adapter's with
another claim of the same adapter's is not corroboration** — it is the manifest
agreeing with itself, and R2 makes this the gate rather than a lint. **`validate`
counts what is on disk:**

```python
sum(1 for unit in walk.units if unit.document.get("kind") == "practice")
```

⭐ **This is strictly stronger and it does not lean on `check_practice_counts`
holding.**

**5. ⛔ The `Unchecked` asymmetry, which is what makes it honest.** A refused
document makes the archive count a **lower bound**:

- `exercises: false` + archive holds ≥1 practice → **`Finding`** regardless. A
  lower bound above zero is still above zero.
- `exercises: true` + archive holds 0 **and any document was refused** →
  **`Unchecked`**, not `Finding`: *"documents were refused above, so whether this
  corpus holds any practice could not be determined."*

⭐ **That mirrors `check_practice_counts`'s existing discipline exactly** — *"a
refused document is not an absent practice"* — rather than inventing a second
one.

## ⛔ And the duplication, which is the trap in this ruling

⚠️ **§1a of my own rubric refuses two implementations of one rule**, and after
this lands there are two `exercises-flag` checks. ⛔ **But the resolution is NOT
to make the fixture checker import `validate`.** `tests/fixture_checks/` is the
oracle that `SF-25`'s acceptance leans on — *"each invalid corpus violates
exactly the one rule its directory names"* — and an oracle that calls the code
under test agrees with its bugs.

⭐ **The real defect is finer: one rule id naming two different subjects.** The
fixture checker counts declarations; `validate` will count the archive. ⛔ **Same
name, different question, and that is the collision.**

⭐ **So: the fixture checker changes its counting source to the archive too.**
Same id, same subject, two independent implementations of a one-line boolean —
⚠️ **which is not §1a's case.** §1a's was a **four-pattern regex list** re-typed
and drifting; a shared `bool(x) != (n > 0)` cannot drift without one of them
being simply wrong, and each has its own tests. **Independence preserved, id kept
honest, R1 clean** — `exercises` and `kind` are the framework's own schema, so
nothing here learns about a source.

**§8a outcome: ruled.** Artifacts: **`E07`'s `JS-01` Acceptance** (already
carries the clause on this branch, correctly) and a **new task owning
`validate/structure.py`**, which the PO places and numbers. ⛔ **Owed before
`JS-01` starts** — `E07` already says so, and that clause is what makes it
falsifiable.

⚠️ **`tests/fixture_checks/__init__.py`'s docstring is a separate finding — see
`CTO-19-4`.**

# ⛔ Ruling 64 — `F26`: a `validate` rule id **is** a public interface, and it is versioned by the report, not frozen

**PO-Integration's `F26`, raised because `W27` moves one.** ⛔ **Their round-4
census was `grep -oE '\[[a-z-]+\]'`, so a corpus-side regression check would go
green for the wrong reason after `W27` lands** — the id changes and the grep
still matches *something*.

⭐ **This is R21 arriving on the report: a contract that is written and not
located.**

**The ruling:**

1. ⭐ **A rule id is an interface.** It is what an integrator greps, files and
   counts, and R2 makes `validate` the seam. ⛔ **So it may not change silently.**
2. ⛔ **But it is NOT frozen**, and freezing it would be the wrong answer —
   `W27`'s move is a **correction** (an R7 leak filed under `RULE_MANIFEST`
   instead of `RULE_PERSONAL_DATA`), and a frozen id would have preserved the
   defect to protect a grep.
3. ⭐ **`RULES` is already the register** — `validate/run.py`'s docstring says
   *"every rule id the tool can emit appears in `RULES`"* and a test asserts it.
   ⛔ **What is missing is that `RULES` is not versioned and not published as a
   contract.** **It gets the same treatment as every other contract in this tree:
   a `*_API` constant beside it.**
4. ⛔ **And the corpus-side check `F26` really needs is not a frozen id — it is
   an assertion that the id it greps for is *in* `RULES`.** ⭐ **That check
   cannot go green for the wrong reason**, which is the property their grep
