## Decisions

1. ⭐ **`consuming.json` is at the component ROOT, and the epic's `TC/consuming.json` is what that
   means.** `TC/` is the component; `narrate-service`'s own `consuming.json` sits at its root, and
   the framework's existing reader (`skills.buildserve.narration.CONTRACT`) names the file by that
   path. One shape for both components is worth more than a directory preference.
2. ⛔ **The reference fragment is NOT under `docker/editor/`, and that is a measured reason, not a
   taste.** `editor_plan.OWN_INPUTS` hashes every file under `docker/editor/` into the image's tag.
   A document placed there would move every consumer's tag on a typo fix, which is exactly what R10
   says a tag must not do. It lives in `docs/` beside the prose it belongs to.
3. ⭐ **The renderer lives in the COMPONENT, not in the framework.** R18: a consumer pins this
   component and reads its data, never its code. So `consuming/consuming.py` exists to DEMONSTRATE
   that the JSON is sufficient — the framework's own generator reads the same JSON and imports
   nothing from here.
4. ⭐ **Per-project values arrive as compose interpolations with defaults** (`${HOST_UID:-1000}`,
   `${EDITOR_IMAGE:?…}`), so the rendered file is complete with no argument and still adapts. That
   is how "sufficient with no other input" and "the mount list must differ per project" are both
   true at once.
5. ⭐ **The image has no registry, and the contract says so in `editor.image.registry: null`.** This
   component has no remote. A consumer builds the image from the pinned checkout and pins the tag
   the build prints. ⚠️ What a tag PROMISES is deliberately absent and named in `not_yet_declared`:
   it is `TC-06`'s.
6. ⭐ **The health check runs code-server's own node**, because a set without `python` has no
   `python3` and a set without `node` has none on `PATH` (`TC-02`'s handoff said so; the contract now
   carries the reason in `editor.healthcheck.why_this_interpreter`).
7. ⭐ **The workspace root is a `tmpfs`.** The extraction source reached this the hard way and its
   compose file records why: the directory is not in the image, so docker creates it root-owned, and
   a named volume there is root-owned for the same reason. The source binds sit inside the tmpfs.
8. ⛔ **`--bind-addr=0.0.0.0:8080` stays in the command, and the contract says in
   `editor.command_notes.bind_addr` why that is not a contradiction**: it is the container's own
   interface. The loopback restriction is the host publish and nothing else. A test asserts the
   published binding is loopback in a live container.

## Surprises

⛔ **THE IMAGE COULD NOT START AS ANY UID BUT ITS OWN, AND RULING 3 IS UNASSERTABLE WITHOUT THAT.**
Measured before anything was written: `docker run --user <not 1000>` with the editor's real
entrypoint exits before code-server starts. The base image's `fixuid` — which repairs the passwd
record and the ownership of the image's own home directory for whatever uid the container was
given — runs inside
`/usr/bin/entrypoint.sh`, which the editor's own entrypoint `exec`s at the END. Until then the uid
has no passwd entry, `HOME` is `/`, and the seed step tries `//.local` and is refused.

⭐ **The fix is one line in `docker/editor/entrypoint.sh`: `eval "$(fixuid -q)"` before the seed.**
It is the same command the base runs, it is idempotent, and both halves are measured in containers —
a stranger uid starts and owns its home; the same image with that one line removed from its
entrypoint (bind-mounted over, so no rebuild) exits with a permission error.

⚠️ **This is inside the declared surface** (`docker/editor/`, the compose and contract files) **and
it is the mechanism of a ruling this task must ASSERT, not a defect noticed next door.** It moves the
editor's tag, which is why the two editor image modules that exercise the entrypoint were re-run.

⚠️ **A smaller one:** the extraction source's compose file publishes the editor on
`127.0.0.1:8443:8080` and mounts six source paths individually. Spec §8.1 says `TC-05` *fixes rather
than copies* the loopback binding — it turned out to be the one thing the source already had right
for this service; what it did NOT have was any machine-readable form, which is the whole of the
`consuming.json` half.
