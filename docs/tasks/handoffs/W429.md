### ⭐ The four things the row said would settle it

1. ⭐ **A FILE can be addressed, not only a folder.** `Editor` gained `base` — the part of the
   source root the editor actually mounts, ⛔ **relative and never the host directory**, because
   the host directory is a home (R7) and this record is read by the serving process. `main_path`
   and `test_path` are relative to the SOURCE ROOT and the editor mounts a directory INSIDE it,
   so the two do not compose without it. The index publishes the endpoint that addresses one
   practice; `POST /api/v1/run/<corpus>/editor/<practice>` answers it.
2. ⭐ **The framework writes the practice's workspace settings**, computed from that practice's
   own `main_path` and `test_path`, into the folder the window opens.
3. ⭐ **Two tabs over two frames**, the second built on the first click of its tab.
4. ⭐ **A quiz renders no panel at all** — no file, no frame, no Run, no Submit.

### ⛔ The window's own URL is the only discriminator, and that is a property

⭐ **An extension cannot read its own window's query string, and both windows share ONE workspace
settings file** — so anything an extension opened, it would open in BOTH. ⛔ There is therefore
nothing else that can point two windows of one code-server at two different files, and the whole
shape below follows from that one fact rather than from a preference.

    <origin>/?folder=<folder>&payload=[["openFile","vscode-remote://<authority><absolute path>"]]

⭐ **The SERVER composes the whole URL, and the page composes no part of it.** ⚠️ **A deviation
from `W416`, stated rather than slipped in:** that row ruled *"the client builds no URL: it hands
back an origin and a folder and the panel decides."* The panel still decides nothing about where
the editor is — but the `vscode-remote` authority is the editor's own host and port and the path
is absolute inside somebody else's container, and a built page may name neither (R8). ⭐ **So the
seam moved one notch and got STRONGER: the page now names no origin, no port, no query key and no
path at all**, which `tests/studyforge/render/page/test_practice.py` asserts as an absence.

⚠️ **A path the editor does not hold is answered as NOTHING, never as a URL.** A code-server URL
naming an unmounted file opens an **empty, dirty buffer titled with the file's own name**, and
the workbench offers to save it — it looks exactly like a corrupted file and is not one.

### ⛔ Read-only is the editor's job, and the test is left read-only on purpose

    "files.readonlyInclude": {"**/*": true}
    "files.readonlyExclude": {"<the practice's own source>": true}

⛔ **The test is DELIBERATELY not excluded.** It is the statement of what *done* means, and a
reader who can edit it can make it say anything. ⛔ **The page neither claims read-only nor
attempts to enforce it** — a guard in the page would be a second, weaker copy of a rule the
editor already keeps, and `test_the_panel_never_claims_or_enforces_read_only` asserts the page
carries no such word.

⛔ **`files.hotExit` is `off`.** Editor-restore state is per WORKSPACE and not per window, so with
it on each window reopens what the other last had and **both end up showing both files** — the
two-window design undone by a default. ⭐ **Which makes `files.autoSave` a CORRECTNESS rule:** Run
and Submit execute against the file ON DISK, so an unsaved edit is one the reader will watch
their own tests ignore, and they will believe the tests.

⛔ **Nothing here is a security boundary and no docstring says it is.** An iframe of an IDE with a
shell is exactly as powerful as the process behind it; the boundary is the container, the
loopback bind and one exact origin. `test_nothing_here_claims_to_be_a_security_boundary` reads the
module's own prose for both halves of that sentence.

## Decisions

- ⭐ **The endpoint is `POST <corpus>/editor/<practice>` — `editor` standing where a MODE
  stands.** It selects exactly what a run selects, so it reuses the one parse; it is not in
  `MODES` and starts nothing; and it is a POST because it WRITES — it prepares that practice's
  workspace. ⛔ A GET with that side effect would have been a lie in the method.
- ⭐ **The settings are rewritten on EVERY ask, not once.** The exclusion names THIS practice's
  own source, so a reader who moved to another practice must not still be able to edit the last
  one's file. ⚠️ That rewrite is also the one signal inside the editor that the practice moved,
  which is what the lockdown extension watches for.
- ⭐ **`base` is kept SERVER-SIDE and the published index is unchanged.** `editors()` still
  answers `{origin, folder}` exactly as `W416` shaped it. ⛔ Publishing the host mount source
  would have put a home directory on a served document (R7); publishing `base` would have been a
  field nothing reads.
- ⭐ **`studyforge.run.editor(corpus)` is KEPT although the panel no longer calls it.** It is a
  published entry point of a client a built site may be served by, and it still answers a real
  question — *is an editor up for this corpus* — which the new call answers only per practice.
  ⚠️ **Named rather than quietly left**: if nothing ever calls it again it is a retirement, and
  a retirement is a row somebody else mints.
- ⭐ **A quiz renders NO PANEL, rather than a panel with its controls removed.** That is the rule
  the module already had for a reading-only unit — *a section with no work gets no affordance, not
  a disabled one* — and it was already written in its docstring while the code did not do it.
  ⚠️ **Before this, a quiz rendered a panel saying `Your file for this practice is` followed by
  nothing, with a Run button under it.**
- ⭐ **The Tests TAB is emitted by the builder and the Tests FRAME by the page.** The built page
  knows whether the material names a test (it is in the workspace) and can honestly offer the
  tab; only a served origin knows where the file is. ⛔ The tablist ships hidden and is shown only
  where there are two windows to choose between — one tab is no choice.
- ⭐ **The test frame is built LAZILY, on the first click of its tab.** A second workbench is a
  second language server, and a reader who never opens the tests should never pay for one.
- ⭐ **The marker that says a settings file is ours is looked for as TEXT.** See the RED reading
  above: it keeps this module out of `W7`'s reader population and it survives a settings file
  with comments in it, which is a legal one.
- ⭐ **A settings file this framework did not write is REFUSED, not replaced**, and the route
  answers `409` with its own constant sentence — ⛔ the refusal's own message names a file and an
  errno and never reaches the wire (R7).

## Findings

`[structural]` **`W429/1` — a corpus repository gains an untracked `practice/.vscode/settings.json`
the first time a reader opens a practice with an editor up, and nothing in any corpus ignores it.**
The file is this framework's, it is additive, it is never written over anything this framework did
not write, and it is only written where a reader has deliberately started an editor over that
corpus. ⛔ **But no corpus manifest declares it and no `.gitignore` covers it**, so `git status` in
a consumer repository will show it after the first practice is opened. ⚠️ Seen and NOT fixed: a
corpus's own files are the integration side's surface (`E07`, `E08`), and R3's declaration
mechanism (`OPS-05`) is where an exception belongs if one is wanted. ⛔ **Nothing was minted.**
