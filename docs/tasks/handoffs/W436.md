## The channel, and why

⭐ **THE CHOICE: a BUILD ROLE IN THE BUNDLE.** A bundle may list build files under `build` in
`bundle.json` and hold them under `build/`. The gate record digests each as `build:<path>`, and
`emit` lays each into the reader's workspace at the same path, beside the starter and the tests.
The exercise's command names the build file by a workspace-relative path
(`mvn -o -q -f practice/…/pom.xml test`). The dependencies the file names come from the runner
image's prime (`W390`): Maven and Gradle read their seed with no flag.

Argued against the four constraints the row names:

| constraint | how the build role meets it |
|---|---|
| `AX-03/1`: no run report may ever be committable | ⭐ The closed set gains ONE directory, and the reason for closing it is kept by a sharper rule. **Every run's output lands in `target/` inside the workspace** (`RUN_OUTPUT_DIRNAME`). A bundle's report path is refused anywhere else, and `unpermitted` refuses a bundle file under any `target` directory under EVERY role, `build/` included. A run never runs in a bundle, and the one directory a run writes is one a bundle may not hold |
| R1: the channel is DATA, with no branch on a language or library | ⭐ `emit` copies the build role's files as **bytes** and never parses one. No module learned the word `maven`, `pom` or `jpos`. `tests/studyforge/exercise/bundle/test_emit.py` copies a binary build file byte for byte to show it is never interpreted |
| R2: the adapter seam is on disk | ⭐ The build role is a file in the bundle, `bundle.json` declares it, and `validate` re-digests it (`RULE_BUNDLE_DIGEST` names `build/pom.xml` when it drifts) |
| §8.3: the Docker socket never reaches the serving process | ⭐ **No change on that path at all.** `execute/` and `serve/` are untouched: the runner still `docker exec`s the record's argv verbatim, and the prime is baked into the image the reader starts |

⚠️ **The two alternatives, and why each was not chosen:**

- **A corpus-level build declaration the runner reads.** ⛔ A command may not name a path outside
  its workspace (`emit._arguments`), so the runner would have to compose an argument. That is the
  first line of a shell parser on the path to `exec`. It would also put a gate-record input
  outside the bundle, where `drifted` cannot re-digest it, so a changed build would silently
  invalidate every exercise's gates.
- **A launcher the runner image provides.** ⛔ That is the sibling's surface and not this row's.
  It would also be a per-language program in the image, which is a branch on a language made at
  the component instead of the framework.

⭐ **Why it composes with `W390` and adds nothing to it:** the primed image already sets
`MAVEN_ARGS` and `GRADLE_USER_HOME` to its seed. A workspace holding a build file is therefore all
a graded run needs. ⭐ **The two halves are held in agreement by the gates, not by a new check:**
the authoring skill stages the build role into every gate run in the pinned runner, so an exercise
whose build names something the prime did not warm fails `G1` and never ships.

## Decisions

1. ⭐ **`target` is the run-output directory.** It is where Maven writes with no configuration, it
   is already in `skills.execution.prime.SKIPPED` (the prime never takes a specimen from a run's
   output), and any other tool is told it in its own build file or flag
   (`--junit-xml practice/…/target/report.xml`). ⚠️ It is a name the framework fixes, not a
   branch: nothing reads which tool wrote there.
2. ⭐ **`build` is optional and the document's version did not move.** A bundle with no build
   role reads and writes exactly as before. An old reader refuses the new key by name (unknown
   keys are refused) rather than misreading it, which the module's own rule says does not bump
   `BUNDLE_API`.
3. ⭐ **Build files are declared by name, not discovered by walking `build/`.** The gate record
   and `emit` read the same list, and an undeclared file in `build/` is not laid into a workspace.
4. ⭐ **A build role is copied as bytes.** It is not archive text, so it is not required to be
   UTF-8, and nothing here parses it.
