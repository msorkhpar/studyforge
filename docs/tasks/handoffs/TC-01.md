## What landed

⭐ **A proposal, and nothing the software does has changed yet.** Once built, the component gains a

### 1. What is carried from the extraction source

⭐ Each of these is a property of `CodeSignal`'s `docker/code-server/`, restated here in my own words
with what went wrong without it (R20: carried, never cited). Every one keeps its comment in the new
image.

| property | what goes wrong without it |
|---|---|
| **Extensions are installed at build time into a directory in the image** (`/opt/code-server/extensions`, passed as `--extensions-dir`), not onto a volume | An extension on a volume outlives the image. After an upgrade the reader runs the old extensions against the new toolchain. |
| **The build checks the installed extension list and fails when an id is missing** | A marketplace that stops serving an id gives you an image with no language support, and it still builds and starts. |
| **`PATH` is set twice: by `ENV` and by a `profile.d` script** | `ENV` reaches `docker exec` and non-login shells. A login shell rebuilds `PATH` from `/etc/profile` and drops `/opt`, so a tool works under `docker exec` and gives *command not found* in the terminal. ⭐ **Re-measured today on the base on this host** (`codercom/code-server`, code-server 4.135.0, Debian 13.6): its `/etc/profile` assigns `PATH` outright on both of its branches. |
| **Named-volume mount points are created in the image, owned by the runtime uid** (the `coder` user's `.config` and `.local`, and one per toolchain cache) | Docker creates a missing mount point owned by root, and code-server then cannot write its own config (`EACCES` on `.config`). |
| **`ENTRYPOINT` and `CMD` are both re-declared** | The base bakes `--bind-addr 0.0.0.0:8080 .` into its `ENTRYPOINT` (re-read today with `docker image inspect`), so a compose `command:` gets appended after those arguments instead of replacing them. |
| **The entrypoint seeds user settings only when absent, then `exec`s the base's own entrypoint** | If the seed overwrites, the reader's edits are lost on every start. If it bypasses `/usr/bin/entrypoint.sh`, it loses the base's `fixuid`, `DOCKER_USER` handling and `dumb-init`. |
| **The JDK is a whole tree at `/opt/java/openjdk` with `JAVA_HOME` at its root**, and the editor's Java settings name that path | The language server picks up some other JDK, or none. |
| **An architecture outside the recorded set fails the build** | Otherwise an unverified download on an unexpected platform. |

⛔ **Renamed off the source:** the entrypoint's log prefix and the `profile.d` file name carry
`codesignal`, which R1 forbids. They become `editor`.

### 2. What the source gets wrong for THIS framework, and how the editor reads `pins.json`

⛔ **What the source does wrong:** it uses floating tags (`codercom/code-server:latest`, `eclipse-temurin:26-jdk`,
`ghcr.io/astral-sh/uv:latest`). It fetches each checksum from the same host as its archive at build
time, which only proves that host agrees with itself. It picks its own versions (`ARG` defaults for Gradle,
Kotlin and Node). And `npm install -g typescript`, `uv pip install pytest` and every extension id are unpinned.
⚠️ **Its versions also disagree with the pins already chosen.** Measured: JDK 26 vs `pins.json`'s 25, Kotlin
`2.4.10` vs `2.4.20`, Node `24.20.0` vs `24.21.0`. Carrying its `ARG`s would put a second version
of each into the component.

⭐ **The proposal: the editor chooses NO runtime version, and gets every runtime from the runner.**

- ⭐ **`docker/editor/build.py` builds the runner first**, for the editor's set, by its deterministic tag
  (`docker/minimal/build.py`, unchanged). The editor's `Dockerfile` then takes
  `FROM ${RUNNER_IMAGE} AS toolchain` and `COPY --from=toolchain` the trees it needs:
  `/opt/java/openjdk`, `/opt/gradle`, `/opt/kotlinc`, `/opt/node`, and for `python`, the `/usr/local`
  that the runner's python base carries with the hash-pinned pytest. ⭐ **So every runtime has exactly
  one way of arriving (the runner's) and one version (`pins.json`'s).** The runner already checks each
  version at build time, and the editor runs the same `checks` from `pins.json` again on its own image.
- ⭐ **Why not rebuild the stages inside `docker/editor/`:** that would be a second copy of every
  fetch-and-verify step. ⛔ **Why this is not the "building FROM a local image" that `TC-00` refused:**
  the runner is rebuilt from `pins.json` in the same invocation. The editor's tag also digests the
  runner's inputs, so anybody can recompute the chain. `CodeSignal`'s image had floating inputs and
  belonged to another repository.
- ⚠️ **The editor's own pins are not runtimes** (the code-server base, the extensions, TypeScript).
  They go into `pins.json` under a new top-level `editor` block, so every chosen version stays in
  one file. ⚠️ **The cost is `TC-01/4`:** today that file is one of the runner's tag inputs.
- ⭐ **The seam to `TC-02`:** in `TC-01` the editor's set is a constant in `docker/editor/build.py`.
  It is `CodeSignal`'s five: `java`, `gradle`, `kotlin`, `node`, `python`. ⛔ **Turning that constant
  into a per-corpus `--runtimes` argument, adding `maven`, and deriving the extension set from the
  selection is `TC-02`'s work, and `TC-01` does not build it.** The constant goes through the runner's
  own refusal, so a name `pins.json` does not pin is already refused.

### 3. How each input ARRIVES, pinned

⭐ **The rule is `TC-00`'s:** a checksum counts as a pin when it is recorded in the repository and the build
checks against that recorded value, with no checksum fetched at build time. Its provenance is taken once,
at pin time, and written into `sources`.

| input | arrives as | pinned by |
|---|---|---|
| code-server base | `codercom/code-server:<version>` | the multi-arch **index digest** in `pins.json`'s `editor.base` (question `Q1`) |
| runtimes | `COPY --from` the runner (answer 2) | `pins.json`'s `runtimes`, unchanged |
| `libreadline8` (for `python`) | Debian's package from `snapshot.debian.org` at the timestamp `pins.json` already uses for `sqlite` | snapshot timestamp + exact version (`TC-01/7`, `Q5`) |
| TypeScript | the npm registry tarball, `npm install -g ./typescript-<v>.tgz` offline | recorded sha256 + the registry's published `integrity` (`Q4`) |
| each extension | the `.vsix` by `ADD --checksum=sha256:<recorded>`, per platform where the publisher builds per platform | id, version and sha256 per platform in `editor.extensions`, with its source (`Q2`, `Q3`) |

- ⭐ **Extensions are installed from the pinned files with the install step at `RUN --network=none`.**
  If an extension declares a dependency that is not pinned, the build fails right there and nothing
  is quietly fetched from a marketplace. That makes the dependency closure part of the pins (`Q3`).
- ⭐ **Verification is an EXACT set comparison.** `code-server --list-extensions --show-versions` must
  equal `editor.extensions` as `id@version`. A missing id fails the build, and so does an extra one
  (an unpinned dependency that got in some other way).
- ⭐ **What fails the build when an id is removed** (the epic's acceptance). The expected set comes from
  `pins.json` and the installed set comes from the files the install step received. Remove one file or
  one install line in a temp copy and the build fails, naming the id. Remove the pin entry itself and
  `build.py` refuses before Docker starts, because the editor's set requires that id. ⚠️ Under `TC-02`
  that requirement moves to the runtime selection. In `TC-01` it is the fixed list.
- ⚠️ **The source's automatic fallback (`fwcd.kotlin`, else `mathiasfrohlich.Kotlin`) becomes a
  documented fallback and stops being a branch in the build.** An image whose contents depend on what a
  marketplace served that day is not reproducible (R10). With the `.vsix` pinned by checksum, a host
  that stops serving it fails the build loudly. Switching to the fallback is then a pin change, a
  recorded decision, which spec §8.1's *"documented fallback"* allows.

### 4. Where it lives

⭐ **`docker/editor/` in `code-server-toolchain`, beside `docker/minimal/`.** It holds `Dockerfile`,
`entrypoint.sh`, `seed/settings.json` and `build.py`, and `tests/test_editor_plan.py` and
`tests/test_editor_image.py` go beside the runner's tests. ⭐ **Build entry:**
`python3 docker/editor/build.py [--print-tag] [--platform …]`, standard library only, the only way the
Dockerfile gets built. ⭐ **Tag:** `code-server-toolchain/editor:<set>-<arch>-<12 hex>`. The digest
covers `pins.json`, `docker/editor/` and `docker/minimal/` (the runner is an input), using the naming the
runner already uses.

- ⭐ **Why not the component root, as the epic's `Owns` line reads:** the root belongs to the component
  and `TC-00` created it. `TC-01` should own what it adds, which is exactly how [`W253`](../rows/W253.md)
  settles, and that epic edit is `W253`'s to make (`TC-01/11`).
- ⚠️ **The build script reuses the runner's plan** (`load`, the refusal, `inputs_digest`, the tag). As
  that code stands, its input roots and repository name are module constants for the runner only, so
  stage 2 needs a small change to `docker/minimal/plan.py` (`TC-01/2`).

## Questions that need a fetch (stage 2, under the user's pinned-pulls ruling)

- **`Q1`** — the code-server base. The version to pin and its **multi-arch index digest**. The local image
  reports code-server 4.135.0 with a `RepoDigest` that cannot be told apart from a single-platform
  manifest offline, so it is not a pin yet.
- **`Q2`** — each extension (`ms-python.python`, `ms-python.debugpy`, `redhat.java`,
  `vscjava.vscode-java-debug`, `vscjava.vscode-java-test`, `vscjava.vscode-gradle`, `fwcd.kotlin`): a
  version whose `engines.vscode` admits Code 1.135, its `.vsix` URL on Open VSX, its variants per
  platform (`linux-x64`, `linux-arm64`) where the publisher builds per platform, the sha256 of each,
  and a second source (the publisher's own release, or Open VSX's signature). Failing that,
  `single_source: true` with its reason, as `TC-00`'s ruling 3 admitted.
- **`Q3`** — the dependency closure: every `extensionDependencies` and `extensionPack` member of each pinned
  version, each pinned in turn. The `--network=none` install enforces this.
- **`Q4`** — TypeScript: its version, the registry tarball URL and published `integrity`, and a sha256 recorded
  from the file.
- **`Q5`** — `libreadline8` at the `sqlite` snapshot timestamp, per architecture.
- **`Q6`** — whether `fwcd.kotlin` is still served. If it is not, the documented fallback's pin is taken instead.

⭐ **Measurable on this host without a fetch, at stage 2:** whether the base's `/usr/local` collides with
the runner's; whether `code-server --install-extension <file>.vsix` completes under `--network=none`;
and what argv the integrated terminal's shell actually gets.

## Decisions

- ⭐ **Runtimes come FROM the runner, not rebuilt** (answer 2). This is the one decision the register
  should rule on before stage 2. The alternative is a second fetch path per runtime, reading the same pins.
- ⭐ **The editor's pins go in `pins.json`'s `editor` block**, and not in a second file, so one file
  holds every chosen version. The cost is `TC-01/4`.
- ⭐ **The fallback becomes a documented pin change, not an automatic build branch** (answer 3).
- ⭐ **`TC-01`'s set is `CodeSignal`'s five, as a constant**, and the argument for it is `TC-02`'s.

## Surprises

- ⭐ **The base still behaves as the source measured it.** `/etc/profile` assigns `PATH` outright,
  and the `ENTRYPOINT` still bakes arguments. Both were read on the image already on this host.
- ⚠️ **Python cannot just be copied across.** The pinned python image (its local `RepoDigest` equals
  `pins.json`'s digest) links `libreadline.so.8` from `lib-dynload`, and the code-server base lacks
  it. Every other library that list needs is already present.
