## ⛔ THE CAUSE — workspace trust, and a flag the contract had and the image did not

⭐ **`studyforge.practice-focus` was installed, listed, in `extensions.json`, parsing,
inside its engine range — and DISABLED.** A corpus's sources arrive as a **bind mount**,
which the workbench has never been told to trust, and a workbench in **Restricted Mode
disables every extension that does not declare untrusted-workspace support**, ⛔ **with
no error and no log line.**

⚠️ **Why the mint's own comparison could not see it.** The extensions that *did* activate
on `onStartupFinished` in those sessions — `vscode.debug-auto-launch`,
`vscode.merge-conflict` — **declare** support, and `redhat.java` declares `limited`.
⛔ **It was never a like-for-like comparison.** `vscjava.vscode-java-debug`,
`vscjava.vscode-java-test` and `vscode.git` were disabled in exactly the same sessions:
⚠️ **the reader's Java tooling was crippled by the same cause and nothing said so.**

⛔ **And the gap that shipped it.** `consuming.json`'s `editor.command` and the generated
`docs/compose.reference.yaml` BOTH carried `--disable-workspace-trust`. ⛔ **The editor
image's own `CMD` did not.** The reader's container carries no compose labels — it was
started on the image's own command line — so it got the one path where the flag was
absent. ⭐ **The contract was right and the image was not, and nothing compared them.**

⭐ **The three candidates the mint named, each ruled out rather than assumed:**
`extensionKind` was undeclared but is **not** the cause (a build that declares it is
still disabled in Restricted Mode); the `.vsix` `lockdown.py` packs installs and loads
correctly; the `vscode.lock` `EEXIST` appears, is found stale and the lock is acquired —
⛔ **normal, exactly as [`W429`](W429.md) says.**

## ⭐ THE FIX — two halves, and each was measured to suffice ALONE

| half | where | what it covers |
|---|---|---|
| `--disable-workspace-trust` in the image's `CMD` | `docker/editor/Dockerfile` | a consumer who keeps the image's command line — ⛔ **which is how the reader's own editor was started** |
| `capabilities.untrustedWorkspaces.supported: true` and a stated `extensionKind` | `lockdown/package.json` | a consumer who replaces the command line |

⭐ **`lockdown.py` now REFUSES a manifest missing either**, before it packs anything: a
manifest that a workbench would silently disable never becomes a `.vsix`.

⚠️ **The framework's half is a BELT and it is labelled one.**
[`execute/workbench.py`](../../../src/studyforge/execute/workbench.py) adds
`workbench.secondarySideBar.defaultVisibility: hidden` — the chat pane. ⛔ **The Explorer
is the PRIMARY side bar and no setting names its visibility at all** (checked against the
shipped workbench bundle: `workbench.secondarySideBar.defaultVisibility` exists,
`workbench.sideBar.defaultVisibility` does not). ⛔ **It does not discharge clause 1 and
the test says so.**

## ⛔ THE DURABLE HALF — a check that reads installation cannot see activation

⭐ `TC-04`'s guarantee was *"an image whose lockdown did not load is not tagged"*, and the
check that carried it read `code-server --list-extensions`. ⛔ **It passed, in every
round, on an image whose lockdown never loaded — structurally, because the extension IS
installed.**

⭐ **Replaced, in the SIBLING** — `docker/editor/activation.py` and
`tests/test_lockdown_activation.py`, at the commit
[`workspace.json`](../../../workspace.json) pins (⛔ **R20: a path inside another
repository is named, never linked**):

1. `build.py` builds to an **image ID**, not a tag — it passes `--iidfile` and no `-t`;
2. the probe starts a container from it **with the image's OWN command line** (only
   `--auth=none` is added, so the probe owns no secret), against a **bind-mounted,
   untrusted** folder;
3. a **headless browser** opens the workbench at the same
   `?folder=…&payload=[["openFile",…]]` URL a study page builds;
4. the tag is applied only once the container's own logs carry **BOTH**
   `ExtensionService#_doActivateExtension studyforge.practice-focus` **and** the
   extension's own record naming the commands it closed.
5. ⛔ **A host with no browser REFUSES the build.** A gate that can be absent is not a
   gate, and this one exists because the previous one passed.

⚠️ **Why the extension's record is a FILE and not `console.log`.** Measured: an
extension's console reaches the **browser's** devtools and **no file on the server**, so
a gate could never read it. It is written into the log directory the workbench hands the
extension (`context.logUri`), beside `vscode.git/Git.log`.

## Decisions

⭐ **The gate needs a real browser, and that is a cost taken on purpose.** ⛔ **The
alternative was a check that models the workbench's activation decision from the
manifest — which is a better installed-list check and still not an observation.** This
row exists because a model passed while the product was broken, so the gate opens a real
session. ⚠️ A host with no browser **refuses** the build rather than skipping the proof.

⭐ **The extension's record is a FILE, not `console.log`.** Measured, and it is the only
reason the design is shaped this way.

⭐ **Both halves of the fix, although either was measured to suffice.** ⛔ **A consumer
who replaces the image's command line loses the flag, and a consumer who does not is not
reading the manifest** — the two failures are disjoint, so the two declarations are.

⛔ **The reader's container was NOT swapped.** The dispatch said not to, and a swap is
the register's.

## Surprises

⚠️ **The mint's strongest suspicion — an inferred `extensionKind` — was wrong**, and it
was wrong in a way that would have cost a whole round to find by reasoning: declaring
`extensionKind: ["workspace"]` changes nothing while the workspace is untrusted. ⛔ **The
discriminator was a single user setting, and it took one reload to find.**

⚠️ **The brief's third candidate is a live trap for the next office.** An `extensionKind`
or `.vsix` theory can be "confirmed" by editing the INSTALLED manifest in place and
reloading — ⛔ **and the answer is wrong**, because the workbench serves a cached
extension description to a reloaded session. ⭐ **Every manifest reading in this row was
re-taken on a freshly built image and a fresh container.** It is the one methodological
trap this row contains.

⚠️ **The contract already said the right thing.** ⛔ **The flag had been written down,
correctly, in `consuming.json` and in the generated compose template, for as long as
those have existed** — and the image it describes did not carry it. ⭐ **Nothing in this
component compared a contract's `command` with the image's `CMD`**, and `W432/2` is that
gap as a finding.
