## Decisions

- ⭐ **Clause 2 — REFUSE, never adopt. Argued:**
  1. **The record is complete for the run that wrote it.** `render` lists every file the
     onboarding wrote and `write_files` writes all or none, so a path an existing record does not
     list was not put there by that onboarding. Nothing in the corpus can say who did.
  2. **Adopting is exactly `W345/2`'s defect.** It overwrites the file and records it as
     generated in one step; from then on `hand_edited` and the generated R3 check both trust the
     record, so the loss is invisible to every instrument this framework has. That is the
     "silent" the row forbids.
  3. **Refusing costs one move per path, once per framework release that adds a path**, loud,
     by name, with nothing written — and a free path (the ordinary case) is gained with no
     refusal at all.
  4. ⚠️ **Rejected: adopting when the bytes already equal the framework's.** It loses nothing
     today, but clause 1 reads "refuses … any generated path that exists", and equal bytes still
     do not say whose file it is; a person who had copied the framework's text and meant to extend
     it would find it claimed. The carve-out would buy almost nothing and make the rule two rules.
  5. ⚠️ **Rejected: adopt and report.** The report arrives after the overwrite; the only loud
     form that loses nothing is the refusal.
  6. ⭐ **A missing record is the same case at its limit** — it predates every path — so it
     claims nothing, and a regenerate over generated files with no record is refused naming them.
- ⭐ **`W345/3` is NOT reached by this guard, and that is stated rather than forced.** See `W353/1`.
- ⭐ **A listed generated file a person edited is still rewritten**, as before: that is R19
  (a hand-edit to a generated artifact is a finding, and regenerating is the fix), which
  `test_onboard.py` already asserts. This row is about paths the record never claimed.
