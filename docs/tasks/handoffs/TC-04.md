### Acceptance readings ([`E12`](../E12-toolchain-image.md) § `TC-04`)

Taken on the sibling's branch, host Docker, `linux/amd64`.

1. ⭐ **"The extension loads in a running container — verified from the installed list, not from the
   file being present."** In a container started from the default-set image with `--network none`,
   `code-server --list-extensions --show-versions` names `studyforge.practice-focus@1.0.0`, and the
   workbench's own `extensions.json` in the extensions directory carries that identifier. ⭐ **And
   the other way, which is why it is packaged at all:** the installed extension's folder was COPIED
   beside itself under another publisher and name in a running container, and the installed list
   does not name the copy — the workbench reads `extensions.json` and never scans. ⭐ The build
   itself takes the same reading before it tags: the id is in `EXPECTED_EXTENSIONS`, so an image
   whose lockdown did not load is not tagged, and a build whose install step skips the packed file
   fails naming `studyforge.practice-focus@1.0.0 is pinned but not installed`.
2. ⭐ **"Renaming the identifier breaks no consumer that pins the documented id."** The identifier is
   written in ONE place, `lockdown/package.json`, and everything else derives from it: the `.vsix`
   file name, the `Identity` element inside the zip, the build's expected-extension list and the
   README's documented id. No source file in the component writes it out by hand (asserted over
   `editor_plan.py`, `build.py`, the `Dockerfile`, `extension.js` and `lockdown.py`). Renaming it in
   its one home moves the file name, the expected id and the install check together, and the packer
   refuses a target file name its own manifest does not give — so a plan and a file can never
   disagree about what a consumer pinned. The documented id is `studyforge.practice-focus`, and the
   settings a study server writes are `studyforge.practice.main` and `studyforge.practice.test`.
3. ⭐ **"The workbench lockdown behaves as it does in CodeSignal today."** Read by running the ported
   `extension.js` under `node` against a stub `vscode` module with the timers replaced, so the
   schedule is read exactly rather than waited out. On activation it executes
   `workbench.action.closeOtherEditors`, `closeSidebar`, `closePanel` and `closeAuxiliaryBar`, in
   that order — `closeOtherEditors` first, because the window's own URL payload has already made the
   addressed file active and nothing else must move focus before it. It schedules the same decaying
   retries at 250, 750, 2000, 6000 and 12000 ms, and each fired retry runs the same list. A
   configuration change is asked about exactly one section, the one its manifest contributes under;
   a change that does not affect it closes nothing, and one that does re-runs the whole list.
   Disposing the context cancels every pending retry and the listener. A command a workbench does
   not have does not stop the rest. ⚠️ **What changed and what did not:** the identifier, the
   configuration namespace and the packaging are this repository's; the command list, their order,
   the retry schedule, the activation event and the "reads no setting, opens no file" design are the
   source's, unchanged.
4. ⭐ **"Installed for EVERY declared set."** It serves no runtime, so it is not an
   `editor-pins.json` entry with a `for`: `plan()` appends it to `EXPECTED_EXTENSIONS`
   unconditionally, and the selection tests assert it for every set the editor builds. The image
   tests read it off the `java,maven` and `python` images as well as the default five.

## What landed

- ⭐ **`lockdown/` is the extension, as an artifact of this repository.** `package.json` and
  `extension.js`: plain CommonJS against the workbench's `vscode` module, no build step, no
  dependencies and nothing fetched. Its publisher is this framework's and its two contributed
  settings sit under the same word, so it belongs to no consumer and names none (R1).
- ⭐ **`lockdown/lockdown.py` is the identity and the packer**, the standard library only and never a
  marketplace tool. It writes a zip holding `extension/` (the manifest and every script beside it),
  `extension.vsixmanifest` generated from the identity, and `[Content_Types].xml`. Every entry gets
  a fixed timestamp, so the same inputs give the same bytes and the install layer does not move for
  nothing. ⛔ It imports NOTHING else in the component, because the image's pack stage holds
  `lockdown/` alone; `editor_plan.lockdown_identity()` is the one place its refusal becomes the
  component's own.
- ⭐ **The manifest's rules are POSITIVE and name no source.** The publisher must be this
  framework's, every contributed setting must sit under it, the contributed keys must share one
  section, and the activation event is `onStartupFinished`. An identifier belonging to some
  consumer fails all of them without this component knowing that consumer exists.
- ⭐ **The image packs it in its own stage and installs it with the pinned extensions.** A stage on
  the pinned Python image (the build tool the fetch stage already uses, present for every set) runs
  the packer with no network into `/packed`; the install step mounts that stage beside the fetched
  files and installs both. The id is in `EXPECTED_EXTENSIONS`, so the existing installed-list check
  is what verifies it — the build reads the list, never the directory.
- ⭐ **`lockdown/` is an editor input.** It is in `OWN_INPUTS`, so a change to the extension moves
  the editor's tag and no runner's.

## Decisions

- ⭐ **The publisher is the framework, not a product.** `studyforge` is what this component already
  labels its images with (`org.studyforge.editor.*`), and using it for the extension keeps R1: the
  framework's own name is not a source's.
- ⭐ **The configuration namespace moved with the identifier.** The two keys a study server writes
  are `studyforge.practice.main` and `studyforge.practice.test`. Nothing consumed the old spelling
  in this workspace — the serving half is not written yet — so no consumer had to move.
- ⭐ **Generated, not kept.** The source keeps a `.vsixmanifest` beside the manifest; here it is
  generated from the identity at pack time, so there is no second place to rename.
- ⭐ **The packer refuses a target name its manifest does not give.** That is what makes clause 2
  structural rather than a convention: the plan computes the name, the packer checks it, and the
  installed-list check reads the id — three readings of one fact.
- ⭐ **Every `.js` beside the manifest is packed, not only `main`.** A helper left out would install
  with exit 0 and fail the moment it activated, which is the same class of silence as the copied
  folder.
- ⭐ **The version stays `1.0.0`.** The behaviour is the source's; only the identity and the
  packaging are new, and this is the first release of the artifact from this repository.

## Surprises

- ⚠️ **The pack stage cannot import from `docker/`.** The stage holds `lockdown/` alone, so the
  obvious `from plan import Refused` would have worked on the host and failed inside the build.
  `lockdown.py` therefore carries its own refusal class, and `editor_plan` translates it — the one
  seam where the two meet.
- ⚠️ **`--list-extensions` agrees with `extensions.json`, not with the directory.** The copied-folder
  reading in `tests/test_editor_image.py` is the measurement, taken in a running container rather
  than inherited from the source's comment.
