## ⛔ THE MEASUREMENT THE ROW ASKED FOR FIRST — and it is the bad answer

⭐ **The row said to assume it in neither direction. It is an INTEGRITY defect,
and the row's priority changes.**

`files.readonlyExclude` is an **object** setting, and VS Code **merges** object
settings across scopes, so a USER-scope entry is merged INTO the workspace value
the study server writes rather than being shadowed by it. ⛔ **Measured inside a
real session** (code-server 4.137.0, the reader's own pinned editor image
`java-maven-amd64-26eda7f6f804`, a practice-shaped folder carrying exactly what
[`execute/workbench.py`](../../../src/studyforge/execute/workbench.py)'s
`settings()` writes), by the extension host itself:

| reading | value |
|---|---|
| effective `files.readonlyExclude` before | `{"Main.java": true}` |
| `inspect()` before | workspace `{"Main.java": true}`, global unset |
| `update(..., ConfigurationTarget.Global)` | ⛔ **ACCEPTED** |
| effective `files.readonlyExclude` after | ⛔ **`{"MainTest.java": true, "Main.java": true}`** |
| `inspect()` after | global `{"MainTest.java": true}`, workspace `{"Main.java": true}` |
| the editor's own `User/settings.json` on disk | ⛔ carried the new key |

⛔ **So every plant the register set against [`W429`](../rows/W429.md) is
defeatable from inside the product by a reader who reaches the settings editor**

## ⛔ THE SECOND MEASUREMENT, and it decided the whole shape of the fix

⭐ **A user keybindings file written DURING a session does nothing.** Measured
three ways: written mid-session by `docker cp` — no effect; written mid-session
from inside the container by a real process — no effect; present before the
session started — ⭐ **every chord dead.** The workbench reads
`<user data dir>/User/keybindings.json` when a **session starts**.

⛔ **So the extension cannot apply the confinement, only report on it**, and the
removals are SEEDED by the image's entrypoint before any session exists. A
design that had the extension write the file at activation would have been
correct on disk, green in every file check, and completely ineffective — which
is [`W432`](../rows/W432.md)'s failure mode again.

## ⭐ THE FIX — an allow-list, derived, in two halves

| half | where | what it covers |
|---|---|---|
| **keybindings** | `lockdown/allowed.js` → a generated seed the entrypoint writes on every start | every way a reader's KEYBOARD reaches a command |
| **tabs** | `lockdown/extension.js` | every way anything ELSE opens an editor — the context menu, another extension, a future command |

⛔ **What is written down is the ALLOW-LIST** — the caret family, the editor's
own actions, notifications, completion, parameter hints, code actions, rename,
snippets, the editor's own find, and ONE workbench command (`Ctrl+S`). ⭐ **Every
other default keybinding's removal is DERIVED from it against the workbench's
own default keybinding document**, read at run time from
`vscode://defaultsettings/keybindings.json` — which opens no tab, and is the
only place that list exists.

⛔ **A deny-list is the wrong shape and the row said so:** it is wrong the next
time the workbench gains a command, and nothing would say so. ⭐ **Something
says so here:** the extension derives the removals from THIS session's
keybindings and reports `missing=<n>` for the ones the session did not load; the
image's gate refuses the tag on `missing != 0`, and on `extra != 0`, which is
the opposite direction — the seed taking away a keybinding the allow-list now
permits.

⭐ **The tab guard is an allow-list of exactly one thing**: the file this
window's URL opened, learned from the workbench after `closeOtherEditors` has
run. Every other tab is closed, whatever opened it. ⛔ **No surface is named in
the source** — a test asserts `extension.js` contains neither
`"Keyboard Shortcuts"` nor `openSettings` nor `quickOpen` — and a window whose
active editor is unknown closes **nothing**, because a guard that does not know
what to keep must not start closing.

⛔ **A removal carries NO `when` clause**, and that is measured rather than
tidy: VS Code's resolver treats a removal without one as matching every `when`
the default carries, so one entry per key+command removes all of them.

## Decisions

⭐ **An allow-list expressed as three FAMILIES plus about sixty exact ids**,
rather than six hundred ids. ⛔ The property the row asked for is *"a new
command is denied by default"*, and prefixes keep that while staying readable:
`cursor`, `editor.action.` and `notifications.` are whole namespaces that act
inside the one open editor. ⚠️ Some of them navigate (`revealDefinition`) — that
lands as a TAB, and the tab guard closes it.

⭐ **The seed is a UNION, not a replacement, and that is a measurement rather
than caution.** The workbench's default keybinding document is NOT the same in
two sessions of one image: a part that has never been created contributes no
keybinding, so a session that opened the Output panel lists
`workbench.actions.workbench.panel.output.clearFilterText` and one that did not
does not. ⛔ **Three entries differed between two sessions of the same image**,
and a regeneration that replaced would oscillate and drop what another session
found. ⭐ A removal for a key this workbench does not bind costs nothing, so the
union is monotonic — except for a command the allow-list is later widened to
permit, which is the one entry the filter drops.

⭐ **`extra` was REDEFINED after the first build refused on it.** It was *"a
removal this session did not derive"*, which the session variance above makes
pure noise; it is now *"a removal whose command the allow-list ALLOWS"*, which
is the only way the seed can take something away from a practice.

⭐ **The keybindings seed is written on EVERY start** — the opposite rule from
`settings.json`, which is written only when absent. ⛔ `settings.json` is the
READER's file; the keybindings are the lockdown's, a reader confined by them has
no command with which to write one, and a user-data volume from an earlier image
would otherwise keep a keybinding the allow-list no longer permits.

⛔ **The framework's half is a DOCSTRING and a pin, and that is the honest
shape.** No key `settings()` writes can stop a user-scope merge; the fix is the
image's. ⭐ A test asserts the module SAYS so, so the next reader does not take
the lock for stronger than it is.

⛔ **The reader's container was NOT swapped.** The dispatch said not to, and a
swap is the register's.
