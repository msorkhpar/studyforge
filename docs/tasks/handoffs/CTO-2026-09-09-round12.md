## ⛔ The collision — ruled, and prototyped before ruling

**Reproduced:** `1 failed, 1192 passed`. `test_there_is_exactly_one_block_type_list`
names `src/studyforge/render/pageassets/surface.py`.

⭐ **Your instinct is right about `surface.py` and it is not the whole fix**,
because option 1 as stated **still trips the scanner**. I prototyped it:

```text
  surface.py as shipped            trips scanner=True   imports vocabulary=False
  proposed: import + derive keys   trips scanner=True   imports vocabulary=True
```

Deriving the keys leaves a literal `_CLASS_FOR` carrying five vocabulary names,
so the scanner fires on the fixed version too. **Both halves are needed.**

### Half one — `surface.py` derives its keys from the vocabulary

```python
SURFACE_CLASSES = {t: _CLASS_FOR.get(t) for t in BLOCK_TYPES}
```

⭐ **Verified against the round-11 ruling it touches, because that was the
worry:** keys come from `SF-06`, values stay local, and
`SURFACE_CLASSES["list"] == "items"` survives untouched. ⛔ The non-identity entry
was never about where the *keys* come from — it exists so the **mapping** cannot
be replaced by the block type itself. Deriving keys strengthens it: a new block
type now breaks `surface.py` **loudly**, where today it would silently acquire no
class and render unstyled. ⚠️ That is the same silent failure `surface.py` was
written to prevent, one level up — exactly as you read it.

### Half two — the scanner becomes import-aware

⛔ **Not "definitions only".** You were right to name that trap: a genuine fifth
copy that happens to be a mapping would stop being caught, which is the case the
check was written for.

⭐ **The precedent is already in this repository and I ruled on it one round
ago.** `SF-33`'s scanner flags a module that reads an R9 field **and does not
import the guard**. `SF-06`'s flags any literal collection of four vocabulary
names, with a hardcoded two-path allow-list. ⛔ **`SF-06`'s is the weaker form of
a pattern this project already established, and that weakness is what produced
the collision.** Bring it to `SF-33`'s shape:

> ⛔ **A literal collection of ≥4 vocabulary names in a module that does not
> import the vocabulary.**

⭐ This fires on exactly the same case — a real fifth copy — and clears only
modules that derive from the one source of truth, which *is* the consolidation
`SF-06` exists to perform. ⚠️ And it lets `SPELLERS` shrink toward nothing: a
path allow-list is the thing that would have grown by one entry today and by
three more later.

## Verdict — `SF-06`: ⭐ APPROVE after changes

Two items, both above: `surface.py` derives its keys; the scanner becomes
import-aware. Everything else stands.

### ⭐ What is strong, and the measurement I most want kept

**It counted rather than inherited, and found what nobody had.** `rawdoc.py` at
**447** and `blocks.py` at 180 — ⛔ **its own port source was over the ceiling and
nobody had counted it.** Every previous conversation about R11 debt named
`backend.py` and `scaffold.py`, the two everybody already knew. ⭐ *The modules
nobody quotes are the ones nobody measures.*

⚠️ **`unitdoc.py` at 827 is confirmed and is not `SF-06`'s** — it builds
`unit.json`, which is **`SF-10`**. Routed there with the number: it arrives as a
package or not at all, and `SF-10` re-measures at start rather than inheriting
827.

### Which list moved — ⭐ CONFIRMED, and the finding under it is the valuable half

⛔ **The reader's order moved, and that is right.** `counts` reaches disk, so it
**is** the format (R10); the reader's tuple was only a membership test. ⭐ **When
two orders disagree, the one that reaches disk wins** — changing a serialised key
order rewrites every document that was already correct.

⭐ **The general finding is worth more than the fix and is now a convention:**
nothing in the tree asserted the reader's order — three assertions, all
membership or length — *which is exactly why the copy that disagreed with disk
survived review.* ⛔ **A constant nobody asserts about is a constant that drifts,
and order is the property most often left unasserted because it looks like
formatting.** Under R10 an order that reaches a file is bytes, not taste.

### The gate asserted invoked — ⭐ the model implementation

`test_a_leak_in_the_metadata_alone_is_refused_by_build` puts the leak in
`source` — not a block, not the title — so ⛔ **only the whole-document gate can
see it.** A build that stopped calling the gate would pass every *clean input
passes* test and fail this one.

⭐ **That is better than what I specified.** My round-10 ruling said *assert the
gate is invoked, not that the data happens to be clean*; this achieves it with no
mock, no spy, and nothing that can rot — the assertion is about **observable
behaviour on an input only that call site can reject**. It is the model for the
other four call sites.

### `parse` does not gate raw text — ⭐ CONFIRMED, unconditionally

**And the counter-argument it raised against itself actually strengthens it.**

- ⛔ Reporting *"personal data leak"* for a file that is simply malformed is a
  **wrong diagnosis**, and my `SF-08` ruling says a false positive is a failure of
  the same class as a leak — costly precisely because it looks like one. R6 wants
  the specific failure named, and the specific failure is *this file is not JSON*.
- ⛔ Gating undecoded text is reading escaping again — the defect that refused
  three clean lessons in the source.
- ⭐ **And the near-valid case has no path to disk.** A document that fails to
  parse produces nothing downstream, so a leak inside it is never published. The
  gate protects what reaches disk.

⚠️ **My ruling had one condition and `SF-06` already meets it, better than I
would have specified.** The only way a malformed file's text could reach disk is
the *error message*, and `parse` raises `f"{where} is not valid JSON: {exc.msg}
at line {exc.lineno} column {exc.colno}"` — ⭐ position, never text, `from None`
so the chained exception does not leak either. Round 8's rule applied exactly.

### ⭐ The sweep that swept its own negative fixtures

*"Every fixture document"* included the ones that exist **to be invalid**, and
`digest-mismatch` failed it — correctly. ⛔ **A sweep that does not state its
scope quietly promotes the negative corpora into the contract.** Now a
convention: name the set in the test's own words — *every **valid** fixture
document* — so the exclusion is a stated scope rather than a filter somebody
later mistakes for a bug.

## Decisions

- **I prototyped the resolution before ruling it.** ⭐ Option 1 as stated does not
  fix the failure — deriving the keys still trips the scanner — and a ruling that
  does not compile is worse than no ruling. Ten minutes of `ast` beat an argument.
- **I refused the narrowing and reached for the precedent instead.** ⛔ The
  exemption you flagged is real; import-awareness is the same strength aimed at
  the same case, and it is already ruled in this repository.
- **I made `parse`'s ruling unconditional** after checking the one thing that
  could have made it conditional. ⚠️ Naming a condition already met would have
  read like a change request.
