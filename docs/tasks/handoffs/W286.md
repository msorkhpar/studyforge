### ⛔ THE DESIGN DECISION, stated first (settling clause 1)

⭐ **The pin looks for the framework beside the corpus's MAIN checkout.** When the corpus root
is the top level of a **linked worktree**, git names the main checkout itself:
`git rev-parse --git-common-dir` answers the main checkout's `.git`, and its parent is the main
checkout. The framework is the sibling named `studyforge` beside that. In every other case the
anchor is the corpus root, exactly as before `W286`:

| the corpus root is | the pin looks beside |
|---|---|
| a main checkout's top level | the root (unchanged) |
| a linked worktree's top level | ⭐ its main checkout |
| not a checkout's top level (an export, a plain copy, a directory inside some other repository) | the root (unchanged) |
| a worktree whose common directory is not named `.git` (a bare repository, `--separate-git-dir`) | the root (unchanged). ⚠️ Read from the code, not tested |
| anywhere, with no `git` on the path | the root, then `check_held` refuses by name because `git` is missing |

⛔ **Why this is not a second workspace resolver (`W127`).** It answers a question about the
**corpus's own repository**: which checkout is its main one. It does not answer where the
workspace is. It names no component, reads no `workspace.json`, imports nothing from `tools/`,
and knows no corpus name (R1). The only I/O it adds is two local `git rev-parse` questions, run
under the same `GIT_LOCAL_ONLY` environment `check_held` already uses. Nothing is fetched and
nothing is written (R2).

⭐ **One copy of the rule.** `main_checkout` is self-contained on purpose. The generated
`test_framework_pin.py` carries **its own source**, emitted by `inspect.getsource`, so the pin
and the check the corpus runs cannot come to disagree.

⭐ **Where no framework is found, the refusal says where it looked**, as a description with no
path (R7): *"a sibling named 'studyforge' beside the corpus's main checkout (the corpus root
itself unless it is a linked worktree)"*. The generated test says the same.

## What landed

- `pin.main_checkout(root)` returns the checkout the framework stands beside, as the table
  above describes. It resolves `root` first, because `Path(".").parent` is `.` itself.
  - It asks `git rev-parse --show-toplevel` and uses git's answer **only when that is `root`
    itself**. So a directory inside somebody else's repository is never taken for that
    repository.
  - Then `git rev-parse --git-common-dir`. When the resolved answer is named `.git`, its parent
    is the main checkout.
- `pin.framework_of(root)` is `main_checkout(root).parent / FRAMEWORK`. `onboard.write` already
  calls it before writing anything, so a regenerate in a linked worktree now finds the
  framework without an edit to `onboard.py`.
- The generated `test_the_framework_beside_this_corpus_holds_the_pinned_commit` asks
  `main_checkout(_root())` instead of `_root().parent`.

## Decisions

1. **Anchor on the main checkout, not on an ordered list of places to try.** A list, such as
   "beside the root, then beside the main checkout", would give two answers wherever both
   exist. It would also keep reading a symlink like ISO's workaround ahead of the real sibling.
   One anchor gives one answer, and it equals the old answer in every case that is not a linked
   worktree.
2. **Git is asked about the corpus, never about the framework's workspace.** `tools/workspace`
   answers a different question for a different repository (which components sit beside
   *studyforge*), and framework source may not import it. Re-deriving that function here would
   have been `W127`'s defect. `main_checkout` shares only one git fact with it.
3. **The top-level guard is part of the rule.** Without it, a corpus exported into a directory
   inside any git repository would silently anchor on that repository's main checkout. P2 shows
   the guard is exercised.
4. **The generated test carries the function's source, rather than a second hand-written
   copy.** A generated check that re-states the rule is a copy that ages. `inspect.getsource`
   runs when the file is generated, and the framework is always a source checkout there.
5. **`onboard.py` is not touched.** It already reaches the rule through `framework_of`, so the
   file at the 400-line ceiling needed no split.

## Surprises

- ⚠️ `corpora.material` always makes the synthetic framework beside the root it is given. A
  worktree fixture built with it would have had a framework beside the worktree, and would have
  passed without the fix. It gained `framework=False`, and the worktree tests assert that nothing
  is beside the worktree.
- ⚠️ Every existing `test_pin.py` test passed unedited against the new rule. That is expected:
  none of their roots is a checkout, so each still anchors on the root.

## For dependents

- **Any writer of a pin:** call `check_held(commit, framework_of(root))`, as before. A linked
  worktree now anchors on its main checkout without any help from the caller.
- **A corpus in a linked worktree:** regenerate to receive the check. The generated
  `test_framework_pin.py` needs `git` wherever the corpus's suite runs (as `W270/3` said), and
  it now also asks two local `rev-parse` questions.
- ⭐ `pin.main_checkout` is public in `pin.py`. It is not added to the package's `__init__`
  exports, which are outside this surface.
