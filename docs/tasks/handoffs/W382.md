## What landed

- ⭐ **The cause, measured before the change.** With xdist importable, one arm was RED on the
  host: `test_a_SERIAL_directory_runs_on_ONE_worker_under_a_bare_n`. Its child repository holds
  `tests/visual/`, so the copied root conftest's `_forward_visual` imports `tests.visual`. That
  resolves to this checkout's package, which imports `studyforge`. The child has no ini of its
  own, so the only path it had was the one the test set: the repository root and nothing else.
  The pinned image never saw this because its editable install already points at the mounted
  checkout's `src/`. The host installs nothing. It was not a worker-only failure: the
  controller's terminal summary raised it too.
- ⭐ **The fix:** `_env` sets `PYTHONPATH` to the checkout's `src` then the root. Both the host
  and the image now import the framework from the checkout, in the ini's order, and never from an
  installed copy.
- ⭐ **A direct test that needs no xdist:**
  `test_a_CHILD_imports_the_framework_from_THIS_CHECKOUT_outside_it` runs a child from a
  directory with no ini and asserts that `studyforge` resolves under this checkout's `src`. So the
  host suite guards clause 1 whether or not xdist is installed.

## Decisions

- ⭐ **The test file, not the conftest.** The row allowed a conftest line only if argued. The
  defect is the test's child environment, so the fix belongs there. Making the root conftest
  put `src` on `sys.path` would change every run in every checkout.
- ⭐ **`src` before the root, as the ini has it,** so the import order matches the parent
  suite's.
- ⚠️ **The caller's own `PYTHONPATH` is still replaced, not extended.** That is the file's
  existing hermetic choice and this row keeps it. It matters for measurement (see `W382/1`).

## Surprises

- ⚠️ **The brief's measuring method cannot reach the children.** The brief says to install xdist
  with `pip install --target` and put it on `PYTHONPATH`. But `_env` replaces `PYTHONPATH`, so a
  child with `-n 2` gets no xdist and fails with a usage error. That failure is an artifact of
  the method, not a reading. ⭐ I measured instead with the same `--target` directory exposed as
  a private **user site** (`PYTHONUSERBASE` pointed at a scratch base). That is the form the
  register's host install will take, and no real user site or system Python was touched.
- Only one of the parallel arms reached `tests/visual/` from a child without an ini. The two
  visual-line arms run from this checkout's root, where the ini already supplies `src`.
