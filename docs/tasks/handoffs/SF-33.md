## Decisions

### 1. The caller names the exception

`corpus.manifest`'s own contract says reading a manifest raises
`ManifestError` **and nothing else** — a promise its `errors.py` docstring
makes at length, including why the one exception to it is not a leak. ⛔ One
implementation of the version *test* does not get to break that. So `check`
takes an `error` type, `VersionError` is only the default, and
`ManifestError` deliberately does **not** inherit from it — tying two packages
together to save a line would also make `except VersionError` catch things
that are not about versions.

⭐ One implementation of the test, one of the message, and each contract keeps
its own front door.

### 2. A wrong value and a wrong type get different sentences

- `corpus.json declares corpus_api 99; this build speaks corpus_api [1]. …`
- `corpus.json declares corpus_api as a bool; this build speaks corpus_api [1]. …`
- `corpus.json declares no corpus_api; …` — for a JSON `null` or a missing key.

⚠️ **Echoing the value would have been worse for the case this module
exists for.** An integrator who wrote `true` and is shown Python's `True` has
to translate; being told they wrote *a bool where an integer was wanted* is
the actual diagnosis. ⭐ And naming the type means an unexpected payload — a
version field holding an object — is **described rather than reproduced** into
a message that lands in a log, which is R7 arriving in a place nobody would
look for it. A test asserts a dict payload carrying a home path is not echoed.

Both branches always name the accepted set, so the acceptance's "both
versions" holds either way.

### 3. `where` is keyword-only and has no default

Same argument as SF-08's gate, and it is the same failure: a refusal that
cannot say which file it read is one nobody can act on (R6). The first reader
of most of these messages is an integrator hand-writing a `corpus.json`.

### 4. The tree test is syntactic, and it is proved in both directions

`test_no_module_reads_a_contract_field_without_importing_the_guard` parses
every module under `src/` and finds `x.get("raw_api")`, `x.pop(...)` and
`x["raw_api"]` for any name in `CONTRACT_FIELDS`. A module that reads one and
does not import `studyforge.version` fails the build.

⛔ **Deliberately syntactic, not a grep.** Four docstrings in the manifest
package correctly explain the `corpus_api` rule in prose, and a source grep
would flag every one of them — the same "a check that fires on correct code
gets switched off" argument FND-06 made about `$HOME`.

Three tests, because a rule with no negative control is a rule that passes
forever:

1. no offenders in the tree today;
2. the scanner really does see today's one caller (**not vacuous**);
3. a synthetic second implementation, written to a temporary tree, **is**
   flagged — a module that reads `raw_api` and rolls its own membership test,
   which is exactly the thing SF-06 was about to be the first opportunity for.

## Surprises

1. ⭐ **The porous form is worth asserting, not just describing.** The test
   opens with `assert True in ONE` — the bug itself, stated as an assertion —
   before asserting `not is_supported(True, ONE)`. A reader who doubts the
   premise is answered by the test rather than by the comment, and if Python
   ever changed the first line would be the one that failed.
2. ⚠️ **`False` where `0` is supported is the same bug and is easy to leave
   open.** A reader told "true is the problem" fixes `True` and stops. No
   contract accepts version 0 today, so it is a test rather than a call site —
   but the guard is general and a contract that starts at 0 is legal.
3. SF-02's existing tests constrained the message more tightly than expected
   (`"corpus_api 99"`, `"never migrated in place"`, the accepted set). ⭐ That
   is the promotion working as intended: the wording was already load-bearing,
   and the extraction had to keep it rather than reinvent it.

## Findings

1. `[local]` **`CONTRACT_FIELDS` is five of R9's six.** The TOC schema version
   has no field name yet — E03 mints it — so the tree test has a known blind
   spot until then. ⭐ The constant's own comment says so, and adding the name
   is a one-line change on the day E03 chooses it. **E03: this is yours.**
2. `[structural]` **The tree test recognises direct reads only.** A module
   that pulls a contract field through a variable, a loop over keys, or a
   constant escapes it. It is a floor, not a proof, and it is aimed at the
   likely shape of the mistake — somebody writing the sixth membership test by
   hand — rather than at an adversary.
3. `[structural]` **`api` is a generic field name.** It is `unit.json`'s
   version field, so it is in `CONTRACT_FIELDS`, and a module reading an `api`
   key for an unrelated reason would be flagged. Zero occurrences today. If
   one appears legitimately, the answer is to narrow the rule to the module,
   not to drop the field.
4. `[local]` FND-06 finding 4 is still open — a `#:` doc-comment with nothing
   under it in `tools/quality/personal_data/shapes.py`, left by my own split.
   Not swept here because this task never opened that file.

⭐ **What you own is the set, not the check.** `KNOWN_<CONTRACT>` lives in your
package because which versions your contract speaks is your business; SF-33 is
explicitly out of scope for deciding it.

test asserts it says so. If a contract ever does need a migration, it is a
separate, explicit, recorded step — never something that happens because
somebody wanted to render a page.
