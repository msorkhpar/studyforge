## Decisions

1. ⭐ **`content_api`, and R9 gains the overlay.** Above.
2. ⭐ **A section key is *derived*; an address is *recorded*. Both are right,
   and the difference is whether the derivation is total and injective.** §6
   forbids deriving an address because the target lives outside this framework
   and its real spelling was **measured to differ from its title 157 times in
   1,290** (finding 3). A section key names something this framework mints,
   from two fields that are already canonical.
3. ⛔ **`require_slug`, never `slugify` — which is the ASCII-collision question
   answered by removing the slugification.** SF-01's finding was that a
   component which slugifies owes itself a collision check the framework cannot
   make. It costs nothing to refuse instead: `corpus.manifest` already validates
   every declared variant as a slug, so deriving `<variant>` is the **identity
   function** and `café`/`cafe` cannot both arrive — neither spelling is a legal
   variant. `test_two_variants_that_would_collide_under_slugification_cannot_both_arrive`
   states it as the property rather than the hope.
4. ⛔ **The overlay's `address` is a list of slugs, and a title is refused
   rather than slugified.** The extraction source let an overlay spell it as
   titles and slugified to compare, which accepts an overlay filed under the
   wrong unit one time in eight. FND-04's fixture had already generalised this
   correctly — see "what moved".
5. ⛔ **`workspace` and `video` are refused in every section.** They are the
   builder's, derived from the archive and the placement profile; an author
   writing one asserts something they are not the author of, and it is either
   silently overwritten or, worse, silently believed.
6. ⭐ **`trust` defaults from `provenance`**, and only `bundled` defaults to
   authoritative. A field an author must fill in to say the obvious is a field
   an author fills in wrongly.
7. ⭐ **`trust.py` is its own module.** A section key answers *what is this
   called*; provenance answers *may this grader claim to be the source's*. Its
   consumer is SF-23 and its rule is R5's. One module for both would file the
   exercise-trust rule under naming.
8. ⭐ **The gate runs over the whole decoded document, before anything else** —
   because the fields this module validates are not the fields a leak turns up
   in.

## For dependents

### For SF-10 (unit document builder) — read this first

- `load(path, depth)` gives you an `Overlay`; `overlay.sections` is the authored
  array **in the author's order**, already validated, with `key` resolved on
  every section. ⛔ Never re-derive that order: two consumers ordering
  differently mint different speech ids for one unit and desynchronise the page
  from its audio.
- For the **derived** shape (no overlay), `derived_section_key(variant,
  archive_kind, index)` — and ⚠️ `index` is the file's position **among its own
  kind**, not its ordinal, so a capture that skips `lesson-2` leaves no hole.
- ⛔ `workspace` and `video` are yours to add and are already refused in the
  overlay, so you can add them without checking whether an author did.
- ⚠️ **The authored path has never had a real input** (finding 1). Your fixture
  is the only instance in existence; treat its shape as a contract, not as
  evidence.

### For SF-23 and E08 (exercises)

`check_test_record(provenance, trust=None)` returns the validated pair.
`PROVENANCE`, `TRUST`, `DEFAULT_TRUST` and `FORBIDDEN` are data, so a test can
assert the rule rather than a message. ⛔ The one forbidden pair is
`("generated", "authoritative")` and R5 is why.

A section key is **stable across a retitle** and is what audio filenames,

key for the same section, you have two answers to "what is this called" — ask
for a field here instead.
