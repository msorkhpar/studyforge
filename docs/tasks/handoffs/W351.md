## What landed

⭐ **What the software does now that it did not:** a survey of a graded corpus
whose material carries `pom.xml` and `ThingTest.java` drafts
`"runtimes": ["java", "maven"]` and `"corpus_api": 4`, and asks whether those
are the runtimes its graders need, quoting the files that evidence each one.
A prose corpus's draft carries no `runtimes` key and no question about one.

- **Evidence is two closed maps.** A build file (`pom.xml` → `maven`,
  `build.gradle`/`build.gradle.kts`/`settings.gradle` → `gradle`,
  `package.json` → `node`, `pyproject.toml`/`setup.py` → `python`) and a source
  suffix (`.java`, `.kt`, `.py`, `.js`/`.mjs`/`.cjs`, `.sh`/`.bash`,
  `.sqlite`/`.sqlite3`). Anything else evidences nothing.
- **`java` goes beside any name in the manifest's `REQUIRES_JAVA`**, read from
  the owner, so a Kotlin or Gradle draft reads back.
- **The key is drafted only beside `exercises: true`**, because `W350`'s reader
  refuses it beside `false`. Where the material evidences a runtime and ships
  no grader, the draft carries no key and asks one question naming the
  evidence. Where graders ship and nothing is evidenced, or only a build no
  runtime names (`Cargo.toml`), it asks which runtimes they need.
- **The draft asks for `corpus_api` 4 itself** whenever it carries the key, so
  `promote`, which keeps the higher of the draft's version and the one it
  works out, writes a manifest that reads back (`W350/1`'s gap is avoided,
  not closed).

## Decisions

- ⭐ **A new module, not more of `proposal.py`.** `proposal.py` stood at 378
  lines at `b9aef83`. The seam is the one `W350` cut in the manifest: one
  drafted key, one module. `proposal.py` gains only the wiring.
- ⭐ **`.sql` evidences nothing.** SQL names a language, not the engine that
  runs it, which is the vocabulary's own reason for spelling `sqlite` as it
  does. A `.sqlite` database file does evidence the engine.
- ⭐ **`build.gradle.kts` evidences `gradle`, not `kotlin`.** The build
  script's language is not the material's; Kotlin source (`.kt`) is what
  evidences `kotlin`.
- ⭐ **`RUNTIMES_API` is re-derived as `4`** because the owner's key-to-version
  map is not on `studyforge.corpus.manifest.__all__` (Ruling 101), the shape
  onboarding's `NOT_MATERIAL_API` already takes. It is pinned behaviourally:
  the mirror parses the draft one version lower and asserts the refusal.
- ⭐ **Test files are evidence too.** A grader written in a language is the
  strongest evidence the runner needs that language.
- ⭐ **The framework's own generated files evidence nothing.** They never reach
  `capability`'s lists (`W329`), so no second rule was needed here, and the
  mirror asserts it both ways.

## Findings

- `[structural]` **`W351/1`: the runnable fixture surveys as ungraded.**
  Surveying `tests/fixtures/runnable` at this branch drafts
  `exercises: false` and no `runtimes`, and asks the new question naming its
  `.py` files as `python` evidence. Its graders are named `check_*.py`, which
  `capability`'s `TEST_NAMES` and `TEST_MARKERS` do not recognise. The
  hand-written manifest says `exercises: true, runtimes: ["python"]`. So a
  re-survey of the one runnable fixture disagrees with it. This is
  `capability.py`'s closed set, outside this row's surface. The new question
  means the disagreement is asked about instead of passing silently.
- `[local]` **`W351/2`: `W350/1` still stands for any draft a person edits.**
  This row avoids it by having the draft ask for version 4. A person who adds
  `runtimes` to a draft by hand and leaves `corpus_api` lower is still refused
  by `promote`'s read-back, which is correct but not helpful. That row is
  minted and is not this one.
