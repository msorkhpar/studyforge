## Decisions

- ⭐ **The address is computed as an ASCENT and never as a relative path.** `os.path.relpath` would
  answer every layout, and for a worktree outside the framework's directory its answer walks back
  down through named directories — which on this workspace's own shape is a home directory in a
  generated file. ⛔ So the code asks `root.relative_to(framework_of(root).parent)` and builds
  `"../" * n + FRAMEWORK` from the part COUNT alone. The only string that can ever be produced is
  ascents and the sibling's name, which is a property rather than a check.
- ⭐ **A root the framework is not above is REFUSED, not approximated.** It is the one shape with no
  safe answer. The refusal is `PinRefused`, the module's existing kind, and it names the two ways
  out (onboard from the main checkout, or place the worktree under the framework's directory).
- ⭐ **The guard lives in `write`, where the root is known**, following `W270`'s precedent exactly:
  `onboard()` stays a function of its arguments, and `write` refuses before anything is on disk.
- ⭐ **`linked_worktree` moved into `corpora.py`.** Two mirrors now need the same fabricated shape;
  a second copy of a fixture is how `W257/2` happened.
- ⚠️ **`PROCEDURE`'s meaning changed** from "the path from the corpus root" to "the path inside the
  framework". It is a module constant of `pin`, used only by `stub`, and nothing outside this
  package reads it (checked by grep across `src/` and `tools/`).

## Surprises

- ⚠️ **`_running`'s own prose was the harder half.** The address was one function; the sentence
  "clone it beside this repository as `../studyforge`" was FALSE for a worktree in a way the fence
  no longer was, and rewording it is the part that could have quietly become the second remedy.
  ⭐ The wording chosen describes the LAYOUT — *"beside this repository's main checkout — this
  repository itself unless it is a linked worktree"* — and never asks the reader to re-base the
  printed address, which is the line the refused remedy would have added.
- ⚠️ **A corpus that is a linked worktree has a `.git` FILE at its root, and `validate`, `plan` and
  `build` all exit 0 there** — measured by executing the fence, not assumed. The enumeration treats
  a gitfile as a store and never enters it.
- ⚠️ **The fabricated worktree fixture needs its second worktree named differently**: `git worktree
  add` refuses a second worktree whose leaf name is already used by another one of the same
  repository. That is why the refusal test's worktree is `two`.

## For dependents

- ⛔ **Pass `root=` to `onboard`.** It was optional for the reading (`W313`) and it is now load-bearing
  for the addressing: without it, a write into a linked worktree is REFUSED by name rather than
  producing a document whose first command detaches the wrong HEAD. ⭐ Step 3's fence in the skill
  already passes `root='.'`, so a procedure followed as written is unaffected.
- ⭐ **`pin.framework_from(root)` is the one place to ask "how do I say where the framework is from
  here".** Any skill that needs to print the framework's location asks it and never composes
  `"../" + FRAMEWORK`. It raises `PinRefused` for a root the framework is not above; it never
  returns a string that is not ascents plus the sibling's name.
- ⭐ **`corpora.linked_worktree(parent, framework=..., main=...)`** is available to every mirror in
  this package for fabricating the worktree shape, with `corpora.git` for the plumbing. Both use
  placeholder identities and no user config.
- ⚠️ **An integration office regenerating a corpus that is a linked worktree** will see four
  generated files change (the reader document and the three stubs) and the install record's digests
  with them. That is the fix arriving, not drift.
