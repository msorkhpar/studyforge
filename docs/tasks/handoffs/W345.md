## What landed

- ⭐ **Derived, never listed.** `bytecode_ignores(paths)` returns `<dir>/.gitignore` for every
  directory a `.py` in `paths` lands in. The adapter scaffold asks it over its own modules
  (`ingest/`, `tests/ingest/` for the default package), and onboarding asks it over its own two
  checks (`tests/`). A module added in a new directory gets its ignore file with nobody editing a
  list.
- ⛔ **Never the root.** A module at the repository root gets no rule at all: the root ignore
  file is a source file (R3) that `W278` forbids `permitted_edits` to name.
- ⭐ **The text names `__pycache__/` and `*.py[co]` and nothing else**, under a comment saying
  it is generated. Nobody writes either by hand.
- ⭐ **In the scaffold, so a standalone `scaffold(...).write(root)` — the adapter
  [`SKILL.md`](../../../src/studyforge/skills/adapter/SKILL.md) step 3 — gets them too**, not
  only an onboarding. Each is built at the earliest step that puts a module in its directory.
- ⭐ **No new glob.** They land in directories the manifest already declares `not_material`
  (`ingest/**`, `tests/ingest/**`, `tests/**`), so a corpus onboarded before this row needs no
  manifest change, and the regenerate's manifest is byte-identical.
- ⛔ **The regenerate guard.** Under `regenerate=True`, an ignore file this run would write that
  already exists and that `.studyforge/installed.json` does not list is a person's, and the whole
  write is refused naming it. ⚠️ Without it, a regenerate would overwrite that file and then
  record it as generated — after which the generated non-destructive check, which trusts the
  record, could never see the overwrite.

## Decisions

- ⭐ **In the scaffold as well as onboarding**, because the adapter skill documents the scaffold
  as a standalone step; a fix only in onboarding would leave that route leaking.
- ⭐ **One ignore file per directory, even though `tests/.gitignore` would also cover
  `tests/ingest/`.** The row says every such directory carries its *own*, and a directory
  removed or moved keeps its rule with it.
- ⚠️ **The regenerate guard is narrow — it reads only files named `.gitignore`.** The general
  form (any newly-generated path already on disk and absent from the record) is `W345/2`: it
  is the right rule, but it could refuse a legitimate regenerate of a corpus whose record predates
  a path, and that is not this row's call.
- ⭐ **`*.py[co]`, not `*.py[cod]`.** A `.pyd` is a compiled extension module a project can
  carry on purpose; nothing an interpreter writes on import ends in it.

## Surprises

- ⚠️ **`validate`'s source walk honours ignore rules** (`repository_ignores`), so once these
  files exist the bytecode is never offered to it at all. `test_walkthrough`'s `W329` control
  (bytecode is `unclassified` under the narrower glob) therefore had to take `tests/.gitignore`
  out too, or it would have been measuring this row rather than `W329`'s glob. Commented there.
- ⭐ **Step 4 also writes `.pytest_cache/` at the corpus root**, and pytest ships it with its own
  `.gitignore`, so it is not a leak; the negative-direction test leaves it out and says why.
- ⚠️ **`W345/4` surfaced as a timing-dependent RED in the full host suite** and not in the
  file run alone: the pre-`W345` fixture first committed its bytecode, which is the exposure
  this row exists to prevent rather than the state the first corpus is in.
- ⚠️ Several tests read *"every file the scaffold writes"* when they meant *"every module"*;
  five needed the narrower reading spelled out.
