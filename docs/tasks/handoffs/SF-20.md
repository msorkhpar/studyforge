## What landed

- ⭐ **One contract, two modes.** Container: `docker exec -w /work/<cwd> -e … <container> sh -c
  'exec "$@" 2>&1' sh <argv…>`.
  Host: `<argv…>` in `<source root>/<cwd>`. ⛔ Nothing ever PARSES the command in either mode
  (the container's `sh` only runs a fixed program that `exec`s its positional arguments): the
  argv reaches `exec` as the generated document wrote it, checked first by `exercise.require_command` — the one
  existing definition of a command, not a second pattern set.
- ⭐ **The probe asks, and only asks.** `docker inspect` answers whether the container runs AND
  mounts this source root at `/work`; anything else — stopped, another checkout, no Docker, a
  hang — is host mode. Cached `MODE_TTL` seconds. ⛔ The runner never starts, stops or builds a
  container (round 112's ruling); a stop ends the RUN's processes, never the container.
- ⭐ **`TC-00/6` closed by construction:** every line is rewritten relative to the source root
  in its own mode (`/work/…` in the container, the host root on the host), THEN scrubbed.
- ⭐ **`W352/3` decided:** `RUN_ENVIRONMENT` carries `PYTHONDONTWRITEBYTECODE=1` in both modes,
  and a run of every unit leaves the tree byte-identical.
- ⭐ **Streaming is real for Python:** `RUN_ENVIRONMENT` also carries `PYTHONUNBUFFERED=1`, without
  which a Python program's first line waits for its last (asserted both ways).
- ⭐ **Killing reaches the whole tree in BOTH modes.** Host: the command's process group, TERM
  then KILL. Container: `docker exec` forwards no signal, so each run carries a random
  `STUDYFORGE_RUN` token that every child inherits, and a stop or timeout runs a fixed `sh`
  program inside the container that signals every process carrying it — then the local client.

## Decisions

- ⭐ **"Up" means running over THIS source root.** A container by the right name mounting another
  directory would grade files the reader is not editing; it is host mode.
- ⭐ **The token, not `docker exec` alone, is how a container run is killed.** The extraction source
  recorded that killing the client leaves the command running inside; the epic's clause is
  about the process GROUP, so a stop that orphaned it in the container would pass on the host
  and fail where it matters.
- ⭐ **`PYTHONUNBUFFERED=1` joins `PYTHONDONTWRITEBYTECODE=1`.** Both are environment decisions
  that reach Python only; a JVM or Node cache written into the tree is a corpus's ignore rules,
  not this package's.
- ⭐ **stderr is joined to stdout INSIDE the container**, by a fixed `sh` program that receives the
  argv as positional arguments and `exec`s it — verbatim, same process. ⛔ `docker exec -t` would
  also join the streams, and would change line endings, colour and width.
- ⭐ **A program that cannot start is a line and `exit 127`,** never an exception out of the
  stream: the stream's one promise is that it ends in one exit line.
- ⭐ **KILL follows TERM even when the leader obeyed TERM:** a child that ignores `TERM` outlives
  its parent, and the group outlives both.
- ⭐ **The container's name is `studyforge-runner-<source>`** (`container_for`), the name
  `code-server-toolchain`'s README gives the reader's run line — spelled once, here.
- ⛔ **The first line of the package contract no longer says "the only package that spawns a
  process"** — it is false today (`SF-20/4`); it says the only package that runs a corpus's
  commands, which is true.

## Surprises

- ⚠️ **The runner image cannot be built offline** (`SF-20/1`). `build.py --runtimes python` installs
  pytest from PyPI; the attempt, with the build's `RUN` steps cut off from the network, failed at
  exactly that step. ⭐ **So the real-container reading is of a STAND-IN**: the local
  `studyforge/dev` image — measured on the same pinned Python base digest and the same pytest set
  (versions) as the runner's `python` pins — committed OFFLINE with the runner image's idle
  command and working directory and with the dev image's own Python variables emptied, then
  started with the README's documented run line. ⛔ **It is a reading of the stand-in, not of
  `code-server-toolchain/runner:python-…`.** What it proves is the mechanism, which does not
  depend on the image: `docker exec` from outside, `/work`, `--network none`, the token kill, the
  identical output.
- ⚠️ **`docker exec` does not preserve the order between stdout and stderr.** The first
  real-container reading was RED on exactly one case: `out, err, out` arrived as `out, out, err`,
  because the exec protocol carries the two streams apart and the client writes each to its own
  descriptor. The host's single pipe never showed it — ⭐ which is what a real container is for.
  Fixed by joining them where the program runs (*Decisions*).
- ⚠️ **`stdin=DEVNULL` is a WRITE-mode open of `/dev/null`**, and the repository's emission census
  (`tests/test_emission.py`) refuses every write outside what its harness owns — the first host
  suite was RED on exactly the three launcher methods. ⭐ A child's stdin is now a pipe closed at
  once: the same end of input, and no file opened.
- ⚠️ **pytest's `-q` output is identical across the host's pytest and the image's**, once its
  wall-clock figure is masked — the one difference two honest runs have.
- ⚠️ **A `docker exec` client dies on `TERM` at once**, so a TERM-then-wait on the client alone
  never escalated to KILL inside the container; the unconditional KILL is what fixed it.
