# SF-21 — handoff

**Kind:** task handoff — SF-21

## Status

done. Self-certified on its own readings (no reviewer this wave). Branch
`feat/SF-21-progress-store`, from the release tip `f382a4a`.

## What landed

`studyforge.progress`, whose surface is its `__init__.py`: `Progress(root, depth)`
with `record_run`, `entry`, `unit_entries` and `read`; `practice_key` and
`parse_practice_key`; `is_pass`, `MODES`; `store_dir`; `RAISES = (ProgressError,
PersonalDataLeak)`. It has five modules: `store`, `document`, `keys`, `lock` and
`errors`. `progress_api` is registered in `version.CONTRACT_FIELDS`.

## Decisions

- **Where the record lives:** `<root>/.studyforge/progress/progress.json`. It is
  ignored by `.studyforge/progress/.gitignore` (`*`), which the store writes
  inside its own directory. That is R3's own remedy, so nothing that already
  existed is edited. An ignore file already there that ignores less is refused
  and left as it is.
- **The lock:** `fcntl.flock` on `progress.lock` beside the record. It excludes
  every writer that goes through this package, on Linux and macOS, across
  processes and threads. It is advisory, it is not promised on network
  filesystems, and on a platform without `fcntl` the store refuses to write
  rather than run unlocked. Reads take no lock, because the replace is atomic.
- **Key:** `Address.unit_key(n) + "/" + <section key>`, the extraction source's
  shape. The section is any slug, because an authored practice key need not
  start with `practice-`.
- **Version handling:** `check`, not `is_supported`. The record can only be
  re-earned by re-running graders, so an unknown version stops rather than
  resets.
- **Shape:** every key sorts (`sort_keys=True`), and `passed` is stored but must
  agree with `is_pass` when read back.

## Surprises

The epic says "one git-ignored JSON file" without saying who ignores it, and
R3 closes the obvious answer (the root ignore file). The nested ignore file is
the answer. It needs no declaration and no `permitted_edits` entry.

## Findings

- `[structural]` SF-21/1 — spec §R9's register of located contracts has no row for this record (file `.studyforge/progress/progress.json`, key `progress_api`, one writer `studyforge.progress`). The key is minted and registered in code; the transcription into the spec is not this row's surface.
- `[structural]` SF-21/2 — "never inside served content" is now a route obligation. `.studyforge/` also holds the `tree` profile's pages and the shared assets, so a static route over `.studyforge/` would serve `progress/`. The serving rows own this refusal.
- `[structural]` SF-21/3 — SK-06's "re-import merges" has no merge rule and no public API here. What two machines' `first_passed_at` and `runs` combine to is a decision, and this row did not invent one. `Progress._update(change)` is the locked seam a merge would use.
- `[local]` SF-21/4 — E05 SF-22 says "the page names a practice" without naming it by section key. This store keys by section key, so SF-22 must name practices through `practice_key` or the pass is recorded under a name the page never reads.

## For dependents

- **SF-19b (state route):** call `Progress(root, len(levels)).entry(...)` or
  `unit_entries(...)` on every request, with no cache. Catch
  `studyforge.progress.RAISES`. A `ProgressFormatError` is the reader's file
  being wrong, so report it and never reset it.
- **SF-22 (run route):** parse the URL's key to an `Address` first, then call
  `record_run(address, n, section, mode=..., exit_code=..., commands=...,
  when=...)`. Only `mode="test"` with exit `0` completes a practice.
- **SF-30:** a read mark is not this record. There is no mode that holds one, and
  a hand-written `"mode": "read"` is refused as malformed.
- **SK-06 / OPS-04:** write only through this package, never to the file
  directly, because the lock is advisory. A sharing export leaves out
  `.studyforge/progress/` whole.
