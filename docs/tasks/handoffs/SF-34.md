## Decisions

1. ⭐ **`SURFACE_HOOKS` stopped being a mapping of classes, so the class contract
   compares against `HOOK_CLASSES` instead.** Four of its seven entries are now a
   `data-*` attribute **name** or a `data-kind` **value**. ⛔ Left in the whole
   mapping, `published` would make the stylesheet owe a rule for `.data-readable`
   in one direction and let a template carry `class="data-readable"` in the other
   — so `_FORM_OF` says which form each hook takes and `HOOK_CLASSES` is the
   class-shaped subset. ⚠️ **The destination was ruled and I did not re-choose it**;
   only the *shape inside* it is mine, and it is the decision I would most like
   reviewed.
2. ⛔ **Every rule for a `data-kind` value names its element** —
   `span[data-kind="numbering"]`, never `[data-kind="numbering"]`. `data-kind` is
   **overloaded**: `section.html` carries a section's own kind in it, and a section
   kind is a corpus's word. An unscoped selector would style a section the day a
   corpus named one `numbering` — a page that changes because of its material (R1).
   `test_a_kind_hook_is_reached_through_its_element_and_never_on_its_own` pins it.
3. ⛔ **The column is bounded ONCE, on `body`, and that is a measurement.**
   `--measure` is `80ch` and `ch` resolves against the **element's own font**, so
   the same `max-width` on each region gave three columns — 800px, 715.7px and
   680.3px, measured. `body` carries the prose font the measure was chosen in.
4. ⛔ **`--page-max` is NOT painted, deliberately.** It is `96rem`, an outer edge
   for a rail-and-content layout; against a bounded single column it would never
   bite at any viewport. ⭐ **Painting a token only so a check can say it is
   painted is `QA-03/2` committed on purpose.** It stays unpainted with `--rail`
   and `--player-height` — all three are measures, so no ledger row is involved and
   nothing fails. See finding 5.
5. ⚠️ **The outline is a card above the content, not a sticky rail beside it.** A
   rail is the layout `--rail` was minted for and it is the one thing here I cannot
   verify in the pinned image. An unverifiable layout is a worse answer than a
   plain one.
6. ⛔ **`footer#player` is left entirely alone** and asserted unstyled. Laying out
   `SF-18`'s region — `--player-height`, `--panel`, `--shadow` all wait for it —
   would be deciding its design in a file its author does not read.
7. ⭐ **`AUTHORED_CSS` in `test_surface` is derived from `STYLE_PARTS`** rather than
   listed. See Acceptance row 4: the listed form silently excluded `chrome.css`.
8. ⛔ **The `data-readable="false"` row is told apart without colour too** — italic
   plus a `::before` mark, no pointer affordance. The state itself stays in the
   attribute, which is what assistive technology reads; the mark is `content`, so a
   screen reader skips it.
