## What landed

⭐ **(a) A tab is closed by whoever opened it.** `Browser.page()` now keeps the target id behind
each attached session, `Browser.close_page(session)` closes that target, and
`Browser.live_pages()` asks the browser which page targets it still holds. `OpenPage` grew a
`close()` and the context-manager pair, and `conftest.py`'s `open_page` closes in a `finally`
so the run whose tab must not leak — the one that raised — is the one that pays.

⛔ **Closing the TARGET and not merely detaching the session.** A detached tab keeps its
renderer, so a harness that only detached would accumulate exactly what this removes.

⭐ **(b) The protocol read carries the caller's deadline.** `call` and `wait` each computed a
deadline and looped on it, but the loop body blocked in `os.read` on a live pipe — so a browser
that was *up and silent* was waited on forever and the harness's own `"no answer in 30s"` was
unreachable code. `_receive(deadline, complaint)` now waits with `select` until the instant the
caller named and raises `BrowserError` there, carrying the caller's own sentence plus the
browser's last words. ⚠️ **The two halves are one symptom:** tabs accumulated until the image
could start no more renderers, and then the harness waited forever on the browser that could
not answer, which is why the directory HUNG rather than failed.

⭐ **(c) The fixture's teardown is measurable.** `one_tab_per_check` is a named generator and
`open_page` is one line over it, so `test_page_lifetime.py` drives the teardown and counts the
tabs instead of reading the fixture body and believing it. ⛔ A fixture body reachable only
through pytest is a teardown asserted by reading it, which is how this one came to close
nothing.

## Decisions

- **The target map lives in `Browser`, not in `OpenPage`.** `page()` is what learns the target
  id, and a tab opened through `page()` without an `OpenPage` around it — `test_browser.py` does
  exactly that — is then still closable and still counted.
- **`live_pages()` asks the BROWSER, never this package's own bookkeeping.** The row is about
  operating-system processes; a count of what the harness *intended* to close would have been
  green over the defect.
- **`close_page` returns quietly once the browser itself is closed.** A tab cannot outlive the
  process holding it, and a teardown that raised there would turn a browser that died mid-test
  into an error on top of the failure that already says what happened.
- **`test_contrast.py` was edited although it is a clause module.** Its module-scoped `readings`
  fixture builds its own `OpenPage` — it says in its own docstring why it cannot take
  `open_page` — so it is the one other place in this package that owns a tab, and leaving it
  would have leaked one tab per run past the fix.
- **The plant for clause 3 is the DEADLINE, not the hang.** ⚠️ A read with no deadline does not
  fail slowly, it does not return at all, so planting it against a silent browser would hang
  this module the way it hung the directory. ⭐ So `select` is wrapped in a recorder, the bounds
  it was handed are read back, and the plant is the old blocking `_receive` against a browser
  that answers at once — which reaches the recorder never and reddens the check in milliseconds.
- **`docker/dev/check`'s outer bound is untouched.** It catches a hang anywhere; this catches
  this one with a verdict attached, which is what the wrapper's own header asked for when it
  routed the deadlined read to this row.
- **`test_page_lifetime` is MACHINERY in `test_init.py`, not a clause in `ACCEPTANCE`.** It
  asserts nothing about any page this repository renders, which is what that map is a map of.

## Surprises

- ⚠️ **The two defects are one bug and neither alone explains the reading.** Tabs leaking alone
  would have made the directory slow and then loud; a read with no deadline alone would have
  needed something else to make the browser go quiet. Together the first produces the second,
  which is why the same modules passed ALONE in that image in seconds.
- ⚠️ **`docker/dev/check` had already diagnosed the deadlined read, in prose, in its own header,
  and correctly declined to fix it there.** Reading the wrapper before the harness saved the
  diagnosis entirely. ⭐ That header is now dated in one sentence; see the findings.

## What landed in stage 2 — `W397/3`, the flake stage 1 shipped

⛔ **Stage 1's own module was not decidable under load, and it refused another office's merge.**
The gate audits its scope selection every fifth merge and takes the FULL suite; that audit hit
`tests/visual/test_page_lifetime.py` on a branch whose surface is nowhere near it.

⭐ **The mechanism, measured rather than reasoned:** `Target.closeTarget` is answered when the
browser has **accepted** the close, not when the tab is destroyed. ⚠️ **MEASURED in the pinned
image: a closed target stays listed for 10-13 ms idle and 26-100 ms under 24 competing
processes.** ⛔ So `close_page` returned while the tab was still live, every count taken
afterwards was a guess, and a check that read its baseline inside a previous check's close
window read it wrong. ⚠️ **Reproduced: `assert 1 == 5`** — the launch tab plus the four tabs the
leak plant had just closed — at **2 of 6 runs** under contention.

⛔ **It was NOT the deadline.** The bound was never approached and no `BrowserError` was raised;
the hypothesis that a slow browser missed a bound chosen on an idle machine is **refuted** by
the lag measurement, which is two orders of magnitude inside every bound in this harness.

⭐ **The repair is a readiness condition in the HARNESS, not a retry in the check.** `page()`
turns on `Target.setDiscoverTargets` once, and `close_page` waits for the browser's own
`Target.targetDestroyed` for that target before returning. ⛔ **Every settling window in the
test module is therefore deleted** — `_live` reads once and believes it. A count that has to be
waited for is a count nobody can decide.

destruction is delivered by the test, so both directions are decided here and neither depends
on how busy the machine is. ⚠️ It is the FAKE arm in `test_browser.py`'s sense — additional,
never a substitute; the two real-browser checks above stand beside it.

## Findings

  unaffected and the bound stays: it is the outer bound against a hang anywhere. ⚠️ `docker/dev/`

  staleness predates this row and belongs to that growth, not to this one, so only the machinery
  entry this row owes was added. ⭐ The check itself is total either way — it reads `ACCEPTANCE`
  rather than a typed count.
- `[local]` `W397/3` — **this row's own defect, found after stage 1 merged and FIXED in stage

  through a five-second settling window, which is a guess about the machine rather than a fact
  about the browser; under load the guess was wrong and the check could not be decided. ⭐ The
  repair and both readings are in *What landed in stage 2*.
- `[structural]` `W397/4` — **a candidate common cause for `W388`'s parallel-only
  `test_rail_marks.py` failures, offered for measurement and NOT claimed.**
  [`tests/visual/test_rail_marks.py`](../../../tests/visual/test_rail_marks.py)'s `fresh`
  fixture says in its own docstring: ⚠️ *"Every `file://` page shares one storage origin and the
  browser outlives the test, so a mark left behind would be read by the next check."* ⛔ **Before
  stage 2, `open_page`'s teardown returned while the tab was still alive** — measured at 10-100
  ms — so a previous check's page could still be running script against that one shared store
  while the next check cleared it and asserted a fresh one. ⭐ That is parallel-only and
  load-dependent, which matches `W388`'s reading (0 of 13 at the release tip, 2 of 8 on that
  branch). ⚠️ **I could not reproduce it here** — it appears only on that branch, which is not
  my surface — so this is a hypothesis with a mechanism, not a finding of fact. ⭐ **The decisive
  test for whoever holds `W388`: re-take that reading on a tree carrying stage 2.** If it goes
  green, the two were one defect.
