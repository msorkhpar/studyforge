## Decisions

- ⛔ **The one hand-written module is `read.py`, and `expected_units` is in
  it.** It first sat in the generated `audit.py`, which quietly gave a scaffold
  **two** hand-written modules — and R19's promise is that a reader can name
  what is theirs in one breath. Counting the source is reading the source.
- ⭐ **`Layout` re-derives two constants and pins them behaviourally.**
  Ruling 101's second row: a name not on the owner's `__all__` is not shared.
  Exporting `ARCHIVE_DIR`/`ARCHIVE_ROOT_NAME` is outside this task's `Owns`, so
  they are re-derived, and `test_layout` proves the derivation by having
  `validate` read back what `Layout` wrote. ⛔ A literal against the same
  literal would agree with itself.
- ⭐ **A generated module's contract is composed, not pasted.** `parts.compose`
  assembles R17's three questions plus a summary and **raises** if one is
  missing — because a contract inside a string literal is a contract no rule
  reaches, and nothing lints a module that does not exist yet.
- ⭐ **`parts/reading.py` is a split, not a tidy-up.** With all five renderers
  in it, `parts/adapter.py` measured **428** lines, over R11. Ruling 100 makes the split the default; the
  seam it took is the one that already existed — generated versus hand-written —
  so the module boundary and R19's boundary are now the same boundary. Largest
  module after the split: **327**. No `Size exception:` claimed.
- ⭐ **The generated suite copies the corpus minus its archive.** A generated
  test whose first run rewrites the working tree is a test people learn not to
  run, and the archive is the one thing excluded: emitting over the last run's
  output would pass on a corpus this run can no longer produce.
- ⚠️ **`SKILL.md` says nothing about what is *material*.** That is
  reconnaissance's question and the manifest is its answer. A second skill
  re-opening it would give a corpus two places to say what it ingests — and it
  is also why this task was safe to author while `SF-35` was still in flight.

## Findings

### SK-02/1 `[structural]` — a corpus's adapter is not material, and nothing puts that in the manifest

**Measured 2026-09-10**, at `corpus_api: 1`: scaffolding into a clean corpus and
running `studyforge validate` gave `NOT valid: 8 finding(s), 1 unchecked
claim(s)` — one `unclassified` per generated file.

⛔ `content.exclude` cannot say it. **Measured:** it matches by *exact path
equality*, so `{"path": "ingest"}` classifies nothing at all — and `exclude`
means *material withheld*, which code is not.

⭐ `SF-35`'s `content.not_material` is the vocabulary, and this task now
**generates** the globs — `Scaffold.not_material`, two entries for eight files.
⛔ **It stays structural because nothing writes them into `corpus.json`:** today
a person copies two lines out of a report. That is `SK-07`'s, because onboarding
owns the manifest a new corpus starts from, and this is exactly R19's *"anything
a second source would have to retype"*.

### SK-02/2 `[structural]` — a second measured instance of `SF-31/3`

`ARCHIVE_DIR` and `ARCHIVE_ROOT_NAME` live in `validate.corpus` and are on no
package surface, so `skills/adapter/layout.py` is the **second** package to
re-derive them; `cli/plan` was the first.

⚠️ `SF-31/3` predicted this by construction — *"four more commands are planned
under `cli/`, and every one of them reads a corpus root"* — and a **skill** has
now joined the commands, which widens it past `cli/`.

⭐ The remedy is one line on `studyforge.validate.__all__`, or the archive root
becoming a real parameter (§6 permits a corpus to put its archive elsewhere, and
`Layout` already takes it as a field). Neither is inside this task's `Owns`.

### SK-02/3 `[structural]` — an installed `studyforge` ships the skills' code without their procedures

`pyproject.toml`'s `[tool.setuptools.package-data]` is
`["**/templates/*.html", "**/assets/*"]`, and `SKILL.md` matches neither.

⚠️ **Two skills are affected today** — reconnaissance and adapter — and every
future one will be, silently: the package imports fine and the procedure is
simply absent.

⛔ It matters more than a packaging detail because §9 makes the document the
deliverable and the modules the thing it calls, so shipping the callee without
the caller inverts the design. One glob fixes it; `pyproject.toml` is outside
this task's `Owns`.

### SK-02/4 `[local]` — E11's second acceptance clause names a state that cannot be entered from this side

*"E07's adapter package was produced by this skill — the scaffolding commit
precedes the source-reading commits"* is a claim about a repository the
framework agent does not own, and `git log` in the corpus is the only
instrument.

⚠️ The board routed that question to PO-Integration *before this task's review*.
It is still open; the other three clauses are met and evidenced above.
⛔ Per `agent-protocol.md`, the clause is **reported, never rewritten**.

### SK-02/5 `[local]` — could `.gitignore` classify the adapter instead of the manifest?

A NEGATIVE result. **It cannot, and it should not.**
`validate.source.source_files` consults the repository's own declaration of
*generated output*, and an adapter is committed source — so it is scanned
however the ignore file is written, and gitignoring it would make the corpus's
build unversioned in order to hide a classification problem. Recorded so the
next reader does not spend the round trying it.
