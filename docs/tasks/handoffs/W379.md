## What landed

⭐ **What the software does now that it did not:** every layer of the runner stage is cached
under the image's own tag. A build for one declared set, or one set of pins, can no longer be
served a layer recorded by a build for another. That holds whatever BuildKit does with the
selected stage's own cache key.

⭐ **The reason, stated structurally.** Each `COPY --from=<runtime> / /` in the runner is cached
on two inputs: the runner layer below it, and the selected stage (`java-yes` or `java-no`). The
second input is the one a warm cache has matched wrongly, in both directions: `W374` (a `-no`
build served the `-yes` record) and `TC-01/13` (a `-yes` build served the `-no` record). The
first input was the bare runner base, and it is the same for every selection on that base. The
fix makes the first input differ. The runner's first instruction is a `RUN` that reads
`CACHE_KEY`, and `plan.py` sets `CACHE_KEY` to the image tag: the sorted set, the architecture,
and the digest of every input. A `RUN`'s cache key carries its build arguments, so from that
layer up nothing matches across tags. The editor-shaped build can match only a record made by a
build with the same tag, which by construction has the same inputs and selection.

⭐ **Evidence the first input is keyed by definition only:** in the reproduction below, a no-op
`RUN` planted as the runner's first instruction made every runner `COPY` execute rather than
come back `CACHED`, even though records with identical sources on the same base existed.

⭐ **The static guard.** `plan.keyed_copy_findings` names every `COPY --from=<a stage selected
by FROM x-${…}>` that sits above a `RUN` reading `${CACHE_KEY}` in its own stage. It reads the
whole file. `maven-fetch` used to copy the selected `java` and `maven`, but it is reached only
when `maven` is declared. It now names `java-yes` and `maven-yes`, which makes it independent of
the selection by construction. The LLB is unchanged, because an alias resolves to the same
stage. `W374`'s two guards stay: `WORKDIR /opt` in each `-no` stage, and the build-time `/opt`
check.

## Decisions

- ⭐ **The key is the TAG, not only the declared set.** Keying on `DECLARED` alone would still
  let a changed pin for the same set be matched through the second input. The tag already names
  every input (R10), so an image is only ever assembled from records made for that tag. Cost: an
  edit under `docker/minimal/` or to `pins.json` rebuilds the runner stage's own steps. The
  download and unpack stages stay cached, but the pinned `pip` and snapshot `apt` steps run again.
- ⭐ **A no-op `RUN`, not a file or a label.** `LABEL` and `ENV` do not enter the COPY's cache
  key, and a written marker file would put something in the image that the set did not declare.
  A `RUN :` changes no file. The measurement: its layer in a probe image holds no tar entry.
  `docker history` shows the ordinary empty-layer size, the same as the `WITH_SQLITE=no` step.
- ⭐ **Not a cache flag.** `--no-cache-filter runner` works, but only where somebody passes it.
  It lives in the caller, and `build.py`, the tests and a reader's own `docker build` would each
  have to know about it.

## Surprises

## Findings

- `[local]` **`W379/1`: the editor's `--no-cache-filter runner` workaround in the sibling's
  `docker/editor/build.py` can go once this merges.** Every runner layer is now keyed per tag.
  Its docstring's rationale (`TC-01/13`) is then historical. This is `TC-02`'s file, so it was
  not edited. Dropping the flag also lets the editor's runner build reuse the runner's own records.
- `[structural]` **`W379/2`: the sibling's tags move.** The inputs digest covers
  `docker/minimal/`, so every runner tag changes with this merge. That includes
  `runner:python-amd64-cf1c00796308` on this host, and any pin that names a tag. Moving
  `workspace.json`'s pin to the sibling's new `main` is the register's job.
