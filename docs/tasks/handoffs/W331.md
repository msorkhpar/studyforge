### ⭐ The shape chosen, and why it is the plan and not a new record

⚠️ **The brief left two open**: the check consults `studyforge plan`'s
declaration, or a build writes a record of its own output the way onboarding
writes `.studyforge/installed.json`. ⭐ **Chosen: the plan.** Three reasons, in
order of weight:

1. ⛔ **The plan is already the framework's single authority on what a build
   writes into a corpus**, and two other instruments already read it: `OPS-05`
   compares a finished build against `Plan.paths`, and
   `validate.source.enumeration._generated_output` recognises a build's output
   by asking it (`W242`). ⭐ A new record would be a third answer to a question
   that already has one, and the two would then have to be kept in step.
2. ⛔ **A build record is code outside this row's surface.** The build would have
   to write it, and *"stay inside your surface"* is not a formality here — it is
   the reason parallel offices do not collide.
3. ⭐ **A record says what one run DID; the plan says what a build WILL DO.** R3
   is a question about the second, and only the second can be asked of a tree
   whose history has already been committed.

⚠️ **The dependency the brief asked to be judged: a generated check that calls
the framework.** ⭐ **It is not a new dependency.** `SK-02`'s generated
`tests/ingest/test_emit.py` already imports `studyforge.validate`, and the
generated `tests/test_framework_pin.py` refuses a corpus with no framework
checkout beside it. ⛔ The alternative was a generated copy of a 1599-path
enumeration, which ages the moment the corpus does — R19 with the sign flipped.

### ⭐ What the generated check now does

⛔ **Two readings, and the first is the one commit state cannot touch.**

- **The declaration.** `plan_for(root)` enumerates every path a build writes,
  and `manifest.edits.reads_as_content` — the ONE predicate for R3's third
  category (`W278`) — says which paths R3 reads as this corpus's content. A path
  in both that `permitted_edits` does not declare is the breach, **stated before
  anything runs, so it is RED whether the tree is clean, dirty or staged.**
- **The tree, through that same declaration.** Both status letters are read. ⭐
  **An addition is never a breach** — R3 forbids moving, renaming and rewriting
  and says nothing against adding — so `A` and `??` are alike and staging cannot
  fail the check. What is left (a rewrite, a removal, a rename's origin) must be
  named by the plan, by the install record (`W329`), or by `permitted_edits`.
- **A rename's origin is CONSUMED as a field, never indexed.** With `-z`, git
  emits `R  new\0old\0`; the old parser read `old` as a status record and
  reported `.txt` — a path that never existed — while the path that had actually
  MOVED went unnamed, on the first verb R3 names.
- **The framework's own directory at the corpus root is the framework's.**
  `validate.source.SKIP_DIRS` already declares `.studyforge/` this tool's and
  never the corpus's material, so what changes inside it — the narration record,
  the site cache, the pin — is the framework's own writing and not an R3 breach.
  ⛔ Taken from that declaration, never spelled here as a guess.
- **The baked `PERMITTED` list is checked against `plan.edits`**, so a manifest
  that grew an edit without a regenerate fails rather than silently checking a
  corpus that has moved on (R19).

⚠️ **A refusing plan is a hard failure, not a skip.** If the plan will not say
what a build writes, R3 cannot be checked against it, and a check that skipped
there would be silently vacuous in exactly the corpus that needed it. ⭐ Measured:
a freshly onboarded corpus that has not yet been ingested produces **no**
refusals, so the onboarding [`SKILL.md`](../../../src/studyforge/skills/onboarding/SKILL.md) step 4 is unaffected.

## Decisions

- ⭐ **`nondestructive.py` is a SPLIT at a named seam, not a trim** (Ruling 261).
  `artifacts` renders what a person reads and declares what this skill occupies;
  this renders what a machine checks. ⚠️ `pin` already keeps its own generated
  check beside the document that check is about, so this is that arrangement
  applied to the second one, and `artifacts` was within a few lines of R11's
  bound before the check grew.
- ⭐ **`TESTS_DIR` and `EDITS_TEST` went with the renderer**, so the check and the
  directory it lands in cannot be moved apart, and the dependency runs one way:
  `artifacts` imports `nondestructive` and never the reverse.
- ⭐ **The install record is read through `reconnaissance.installed.generated`**,
  `W329`'s one reader, rather than through a second parse of the same JSON. ⛔ No
  new way to recognise a generated file was invented — not a name, not a suffix,
  not a directory.
- ⚠️ **`archive/` is not special-cased** — measured: the plan already names it,
  and `.studyforge/assets/` and `.studyforge/site.json` with it. ⭐ **The
  framework's own DIRECTORY is**, from `validate.source.SKIP_DIRS`'s declaration
  rather than from a name typed here: the narration record and the pin live there
  and no plan path names them, so without it `studyforge narrate` re-run with a
  different voice would have reported an R3 breach against the framework's own
  record.
- ⭐ **A refusing plan fails rather than skips**, for the reason above. ⚠️ A
  missing `git` and a root that is not a working tree still skip, as before: R3
  is a question about a repository's history, and there is none.
- ⚠️ **`test_committed_output._onboarded` became public `onboarded`** rather than
  being copied into the new module. One fabricated corpus that a build writes
  into, in one place.
