## What landed

⭐ **What the software does now that it did not:** `python3 docker/minimal/build.py --runtimes
python` builds an image with an empty `/opt`, and no `-no` stage is a bare cache key. An image
whose `/opt` is not exactly what its declared set places there fails the build and names both.

⭐ **The cause.** Every `-no` stage was bare `FROM scratch`, and BuildKit (v0.31.1, engine
29.6.1, this host) served `COPY --from=<a bare scratch stage> / /` from a cache record that the
same instruction had made from the `-yes` stage on the same base. The `python` set is the only
one whose base (the python image) is also the base of the everything-set that `tests/test_image.py`
builds first, so it is the one set that read populated records. The `java,maven` and `shell`
sets sit on the Debian base and were never served one.

Three readings settle it:

1. **The register's image.** `runner:python-amd64-cfc3a251827c` has six populated `COPY / /`
   layers. Rebuilding that tag through `build.py` loaded metadata for the python image **only**:
   the Temurin stage was not in the build graph at all. Every `COPY --from=<runtime>` still came
   back `CACHED` with the runtime's bytes in it. Its content came from the cache, not from the
   graph.
2. **A probe with no image at all.** It had a `scratch` base holding one file, `a-no` bare
   scratch, `a-yes` holding one file, and `COPY --from=a-${W} / /`. It was built with
   `--output type=local` in the order `no`, `yes`, `no`. The first `no` was empty. The second
   `no` held `a-yes`'s file.
3. **The same probe with `WORKDIR /opt` in `a-no`.** It was correct in both orders, `no yes no
   yes` and `yes no yes no`.

⭐ **The fix.** Each `-no` stage carries `WORKDIR /opt`, so it has real bytes that the cache
addresses by content. Every base already has an empty `/opt`, so nothing visible is added.
Two refusals back the fix up so it does not rest on it alone:

- **At build time,** the check `RUN` compares `ls -A /opt` with `OPT_EXPECTED`. `plan.py`
  computes that value from `OPT_DIRS`.
- **Statically,** `plan.dockerfile_findings` refuses a `scratch` stage that has no instruction.

⭐ **`test_quiet_image`** reads the image's `org.studyforge.runner.runtimes` label. When the
label does not name `maven`, or is missing, every container case SKIPS with the label in the
reason. Read against the register's `python` tag, that is exactly what happens.

## Decisions

- ⭐ **Why not simply stop the everything-build from running first?** That would hide the
  defect, not remove it. The build cache belongs to the host, and any later build could leave
  a populated record behind. So `setUpClass` keeps the everything-set FIRST on purpose, with a
  comment, and builds every single after it.
- ⭐ **"The base's own tools named"** is `BASE_TOOLS = {"shell"}` in `tests/test_image.py`.
  `bash` is present in every image, declared or not. The absence assertion exempts that one
  name and no other, so no absence is claimed that the base makes impossible.
- ⭐ **Which image is built per runtime:** the runtime together with its `requires`. So there
  are eight sets: `gradle java`, `java`, `java kotlin`, `java maven`, `node`, `python`, `shell`,
  `sqlite`. `maven`, `gradle` and `kotlin` cannot be built without `java`, and `plan.py`
  refuses them otherwise.
- ⭐ **`OPT_DIRS` lives in `plan.py`, not `pins.json`.** It describes the Dockerfile's COPY
  destinations, not a version. A test holds the two equal in both directions.

## Surprises

- ⚠️ **The old instrument could not see this.** `tests/test_image.py` proved absence on the
  `shell` image only. That image sits on the Debian base, the one base the populated records
  never reached.
- ⚠️ **`test_a_wrong_checksum_stops_the_build…` removed the class's own `node` image.** Its
  "right checksum" copy has the tree's inputs, so it has the tree's tag. The first run of the
  new per-runtime case was RED on the `node` label for exactly that reason. The removal now
  skips a tag the class built.
- ⚠️ **The defect depends on the cache's history, and a plant does not reproduce it on
  demand.** The real Dockerfile with bare `-no` stages restored was built in two plants: the
  everything-set, then `python`. That python build came out correct both times, most likely because the
  cache served the record left by this branch's own correct builds. That is why the
  deterministic guards are the static finding and the build-time `/opt` check. The per-runtime
  inspection is the reading of the result.
