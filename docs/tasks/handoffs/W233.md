## What landed

- `tests.support.ProcessOutput`: the one reader of a child's `stdout` and `stderr`. It reads
  the raw descriptors with `os.read` under a `select` deadline and keeps every byte. `line()`
  hands out the next whole line, and `rest()` reads to end of file and returns everything,
  lines already handed out included. It never sleeps.
- `tests/studyforge/cli/test_serve_process.py`: `launched` yields a `Running` that owns the
  reader, and `Running.stopped()` reads through it. `printed()` asserts every line the verb
  prints: the listening line first, naming the port the caller read, then one request line
  per fetch in order, then `stopped`. In the root form, the `corpus` line must come straight
  after the listening line.

## Decisions

- ⭐ **The reader lives in `tests/support.py`**, not in the row's file. `running.py` holds no
  process reader: it runs the skill on a thread with a `StringIO`, so there is nothing there to
  share. The process tests that could adopt this reader are in two packages, so it goes in the
  module whose rule is "imported, never copied".

## Surprises

- The row names `running.py` as the harness that met this trap. It holds no process reader (`W233/1`).
- ⚠️ A sleep put in place of the reads passed every runtime test. Only the static guard turned it RED (`W233/5`).

## For dependents

- A test that starts a process and reads its output while it runs: `output = ProcessOutput(process)`
  right after `Popen`, with no `text=`. Read with `output.line(timeout)` and finish with
  `output.rest(timeout)`. ⛔ Never touch `process.stdout`, `process.stderr` or `communicate()`.
