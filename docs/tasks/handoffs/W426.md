## Decisions

**Plain `java`, no build tool, no dependency — the brief's recommendation, adopted, and here
is the reason rather than the assent.** The JDK's source-file launcher compiles in memory, so
a run writes **nothing** anywhere in the corpus — which is R3 held by construction rather than
by a `.gitignore`. jPOS is a dependency and a dependency is vendored or pinned by digest,
never downloaded loose; and it is not needed, because what this material teaches in §2 is the
*format* — four digits of MTI, sixty-four bits of bitmap, and the lengths that let a reader
walk a message — every bit of which is pure, deterministic and gradeable in the standard
library. ⭐ The graders are plain `main` methods that print one line per check and exit
non-zero: **no JUnit, so no jar, so nothing to fetch.**

**A fourth container rather than practices attached to existing units — and this was forced,
not preferred.** `validate.source.completeness.check_completeness` sums `counts.headings`
across **all** of a unit's archive documents and compares the total against the heading count
of the one file the unit's `origin` names. A practice added to a recorded unit therefore
raises that unit's total above its source file and reads as a `short-read` — **correctly**,
because the practice's prose is not in that file. The three additive shapes are: a new
container, new units with new origin files, or a practice document carrying **zero** headings.
⭐ The first is the only one that touches no existing record at all, so the practices bring
their own material, in their own files, under their own record, `src/Practice.md`.

**The starting code is read from the Java file, never retyped into the Markdown.** The
runnable fixture writes the fence in its `.md` *and* in `starting_code` *and* keeps a real
file, and holds the three together with a test of its own. ⛔ Nothing in `src/` does — see
`W426/5` — so for a real corpus that is three copies with no diff. The `.md` carries a bare
`## Starting code` heading and the adapter appends the code block it read from the file.
⚠️ This also keeps the heading arithmetic honest: a heading the adapter invented would break
`check_completeness`, and only a *block* may be appended.

**`provenance: bundled`, `trust: authoritative`.** These graders ship in the corpus
repository, beside the material, and are the corpus's own. ⚠️ R5 forbids a `generated` grader
that claim, which is a rule an authoring skill will meet on day one and this hand-authored
sample does not — see `W426/1`.

**`runtimes: ["java"]`, the honest minimum**, even though no prebuilt image on this host
carries exactly that set — see `W426/4`.

**The variant stays `prose`.** `variants` is a filing and presentation key and explicitly not
a capability (`corpus.manifest.document`'s own docstring), so a Java practice filed under
`prose` is correct rather than a compromise. ⚠️ It does mean the section key a reader's
progress is recorded under is `practice-prose` — see `W426/9`.

## Findings

**Twelve findings, and the first four are `M10`'s actual input.** ⛔ Every one of them is a
thing the framework could not do, met while doing this row; none of them was patched around
in the corpus.

`W426/1` `[structural]` — **There is no skill for authoring practices, and the consuming half
of a practice is hand-written.** `skills.adapter` scaffolds a reader and contract tests for a
**prose** corpus; nothing it generates knows about `exercise`, the lesson/practice split, the
`practices` count or the provenance pair. Every one of those had to be typed into
`ingest/practices.py` by hand. R19 says what a second source would have to retype is a hole in
the skills, and this is the whole of one. ⭐ It is also the target `M10`'s generator is
measured against: this handoff's corpus half is the worked example.

`W426/2` `[structural]` — **The heading-count check decides the SHAPE of every "add practices
to an existing corpus" row, and that is written down nowhere.** `check_completeness` compares a
per-unit heading total against one source file, so a graded practice cannot join an existing
prose unit without rewriting that unit's source — which R3 forbids. The three additive shapes
are named under *Decisions*. ⚠️ An `M10` row that assumes it can hang a practice off unit 7 of
an existing corpus will meet this as a red gate rather than as a design note.

`W426/3` `[structural]` — **`corpus.json` cannot declare a practice's workspace.**
`exercises` and `runtimes` are the only exercise-facing manifest keys; which file a practice
sets, what runs it and what grades it exist only inside the archive document, so they are the
*adapter's* to author in Python. A corpus cannot declare its practices as **data**. ⛔ That is
the single largest obstacle to a generated consuming half, and it is a framework decision
rather than a corpus one.

`W426/4` `[structural]` — **`runtimes` does nothing at serve time, and a wrong toolchain is
undiagnosed.** Measured on this branch at `347d71d8`: outside `execute/quiet.py`'s own
docstring, nothing under `serve/`, `execute/`, `generate/` or `render/` reads
`manifest.runtimes`. The runner is found by container **name** (`studyforge-runner-<source>`)
and the image is whatever the reader started; a corpus declaring `java` served against a
python-only runner gets the framework's "could not be started" line and no sentence anywhere
mentioning the declaration it broke. ⚠️ Compounding it: the prebuilt runner sets available on
this host are unions (`python`, `java-maven`, `gradle-java-maven`,
`gradle-java-kotlin-node-python`), so the honest minimal declaration `["java"]` corresponds to
**no** prebuilt image, and nothing says so either.

`W426/5` `[structural]` — **`starting_code` is inert and unchecked.** Measured at `347d71d8`:
the key is written by `archive.document` and read by nothing under `src/` — the page renders
the `code` **block**, and the runner executes the real file at `main_path`. The only check
that they agree is `tests/test_fixture_runnable.py`'s, over the fixture alone. So for a real
corpus the shown code and the run code can differ silently. ⭐ This corpus avoids it by
construction (one source, read from the file); the framework does not require that of anyone.

`W426/6` `[local]` — **A hand-written adapter module has no way into
`.studyforge/installed.json`.** That record carries `ingest/read.py` as `hand_written: true`,
so hand-written files *are* in its vocabulary; but editing it is a hand-edit to a generated
artifact (R19), so `ingest/practices.py` is now a module of this corpus's adapter that the
install record does not know exists. Onboarding would have to be re-run to say so.

`W426/7` `[local]` — **The generated non-destructive check reds on any uncommitted authored
edit**, because it reads `git status`. Correct for a generation run, surprising for an
authoring one, and worth one sentence in the generated docstring so the next office does not
spend the minute this one did.

`W426/8` `[local]` — **The serving process's `Sec-Fetch-Site` rule refuses an
extension-driven navigation**, so "read it in a browser" is not directly reachable by a
browser-automation harness. ⭐ Worked around here by navigating from a page already on the
origin; ⚠️ but every future acceptance clause that says *read in a browser* inherits this.

`W426/9` `[local]` — **The section key for a Java practice in a one-variant prose corpus is
`practice-prose`.** It is the manifest's own rule (a variant is filing, not capability) and it
is right, but it is what a reader's progress record and the run API path will carry forever.
Saying so now is cheaper than discovering it in a progress migration.

`W426/10` `[local]` — **`W425`'s remedy already exists in the tree.**
`.studyforge/progress/` ships its own `.gitignore` and therefore self-ignores;
`.studyforge/site.json` does not, which is the whole of `W425`. Corroborates that row and
names its fix.

`W426/11` `[local]` — **This row has no row file and is not on the board.** Dispatched by
brief only. Minting is the register's; recorded so the absence is a decision rather than an
oversight.

`W426/12` `[local]` — **The generated onboarding report went stale the moment the corpus
declared exercises.** The generated onboarding report at the corpus root now says *graded
practices: no* and *This corpus declares no graded practices, so nothing here is waiting on
one*, and both are false. ⛔ It is
a generated artifact, so editing it is a finding and not a fix (R19): it is regenerated by
re-running onboarding, which this office did not do because re-running it also rewrites the
pin, the install record and the generated tests, and the pin advance is the register's.
⚠️ **So a corpus that gains exercises has no way to refresh that one report alone.**
