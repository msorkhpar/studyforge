## Ruling 1 — `check-ignore` wins. My verdict was wrong; the branch stands.

⛔ **I tested both rather than weighing the arguments**, and the measurement is
not close:

```
repo: .gitignore has `.idea/`; three leaks planted

git ls-files sees            check-ignore approach sees
  .gitignore                   .gitignore
  src/committed.py             src/committed.py
  src/ok.py                    src/just_written.py   <-- LEAK-A
  src/staged.py                src/ok.py
                               src/staged.py
```

⭐ **`ls-files` misses the brand-new, never-added file — which is the whole case.**
An R7 gate exists to catch a leak *before it enters*, and `src/just_written.py`
is the only state in which the fix is free. By the time `ls-files` can see it,
it is staged at best and committed at worst, and committed is the state my own
rubric calls ⛔ REJECT-and-rewrite-history. The developer's sentence — *"catches
the leak one commit too late, which is the commit that then has to be
rewritten"* — is exactly right.

**The other three properties, verified rather than accepted:**

| Property | Measured |
|---|---|
| fails open | outside a repo, `check-ignore` exits **128** with an empty list, so the whole tree is swept — ⭐ an unanswerable question reports too much |
| exit 1 ≠ failure | a clean repo returns **1** meaning *no matches*, distinguishable from 128 — the subtlety a naive implementation gets wrong |
| `!tests/fixtures/**` honoured | `tests/fixtures/depth1/.studyforge/site.json` is **not** ignored; `.studyforge/site.json` at the root **is** |

⚠️ That last row matters more than it looks: it is the golden tree the sanctioned-
directory registry is *about*. A sweep that let it fall out would have disarmed
the check's most important target while reporting clean.

### ⛔ Why I got it wrong, because the shape will recur

I wrote that both `FND-06` defects were **scope, not patterns** — and that was
right. Then, in the same breath, I proposed **a third scope error in the opposite
direction**.

⭐ **The mistake was picking the noun that matched the symptom instead of the
one that matches the purpose.** The failing file (`.idea/workspace.xml`) was
untracked, so "tracked content" looked like the answer. But the subject of an
*entry* gate is content **about to enter** — and `ls-files` is a definition of
what has *already* entered. ⚠️ **A reviewer proposing a fix is doing design with
less context than the developer had**, and I should have said *"the scope is
wrong, here is the case it must cover"* and left the mechanism to them.

**Amended, not the branch.** `FND-06` as merged is correct.

### The sub-shape you named is real — ruled prospectively

⚠️ It did not happen here, but it will, so: ⭐ **the C5 rule is about any input to
a gate that can differ between two runs, not only about a rule that is new.** The
unifying form:

> ⛔ **A gate's verdict must be a function of the tree alone.** A new check, a
> changed configuration and a changed tool version are the same defect wearing
> three faces.

The trial merge removes the **tree** variable. ⛔ It does nothing about the other
two, and pinning is what removes them — which `FND-03` has already done for the
image. ⚠️ **A config change is therefore a `[structural]` finding on the commit
that makes it**, and it carries the same-commit obligation as a new rule:
reformat the tree in the commit that changes the formatter.

## Ruling 3 — the process error, and why a promise is not the fix

⭐ **I am not asking for a stricter promise.** Two branches were merged ahead of
their verdict in one round, both in good faith and both to unblock a critical
path — which is precisely the pressure under which *"I will not do it again"*
fails. This project has twice ruled that a rule living only in someone's
intention erodes: once for the module ceiling, once for the R7 sweep.

**So the verdict is recorded in the merge, not remembered:**

```
Merge <branch>: <one line> (CTO: APPROVE)
```

```bash
git log --merges --format='%s' "$REVIEW_BASE" | grep -vE '\(CTO: (APPROVE|APPROVE after changes)\)'
```

⛔ **The point is not to prevent an urgent merge.** It is that an un-reviewed
merge should be **visible in the log afterwards** rather than depending on
whoever did it to remember. ⭐ A gate that leaves no trace when skipped is a gate
that will be skipped again.

⚠️ **And I applied my own round-5 rule to it rather than repeating that
mistake.** Every existing merge predates the clause and none carries a verdict.
⛔ They are **not** back-filled — rewriting merge messages on a branch other
agents have built on costs more than the record is worth, and the verdicts are on
record in the `CTO-*` handoffs. The rule binds from here, and the check is scoped
to say so, **in the document**.
