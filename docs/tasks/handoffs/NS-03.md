#### ⛔ Where the CPU proof STOPS, named rather than left to be assumed

## Decisions

**1. ⛔ THE CPU AND GPU PROFILES ARE NOT TWO ADAPTERS, AND THAT IS THE ANSWER
RATHER THAN A SHORTCUT.** Kokoro's CPU and GPU images speak one request shape,
so both profiles run `KokoroEngine` unchanged. ⭐ **That is the strongest
available form of *"switching profiles is not a code change"*: there is no code
that could have changed.** ⚠️ **The alternative — a `CpuEngine` and a
`GpuEngine` — would have satisfied a reading of the row's word *"profiles"* and
broken the clause underneath it.**

**2. The GPU profile is a SECOND FILE, not a `profiles:` key.** A compose
profile is selected by `COMPOSE_PROFILES` as readily as by a flag, so a machine
with no GPU is one stale shell export away from trying to start a device
reservation it cannot satisfy. ⛔ **A second file cannot be selected by
accident**, and `docker compose up` — the command in every README and every
script that has never heard of this file — is always the CPU deployment.

**3. ⛔ `engine_profile` is a DECLARATION and the documents say so in four
places.** The service is on the far side of HTTP from its engine and cannot see
that engine's hardware; a claim that it could would be a claim about somebody
else's container. ⭐ **The default is `unknown`, not `cpu`** — a service run by
hand against an arbitrary engine must not report a hardware fact it did not
check, and `test_the_default_profile_is_not_a_hardware_claim` pins that. ⚠️ **The
default *deployment* is `cpu` and the default *label* is `unknown`; they are
different statements and conflating them is how a lie gets a test.**

**4. A registry with one entry, and it is the `SUPPORTED_FORMATS` argument.**
`NS-01` declined a lookup table for one implementation and was right to. What
changed is that engine choice is now a **setting**, and a setting must be
validated: an unknown `NARRATE_ENGINE` has to be refused at startup naming what
is permitted. ⛔ **The closure is the feature.** There is no entry-point scan and
no import-by-name, because that would turn an environment variable into an
instruction to import an arbitrary module.

**5. A runtime gate rather than an ABC.** The object that reaches the server can
come from the registry, from a test, or from `build_server(config, engine=…)`,
which is public. An ABC is enforced at subclass definition, which is the wrong
moment. `check_engine` runs on whatever object it actually is, so a missing
member is a refusal to start rather than a `500` on somebody's first request.

**6. ⛔ I did NOT invent a second speech engine to justify the seam.** A
`SilenceEngine` or a shim around a CLI would be a harness standing in for an
engine, and describing it as evidence of engine-independence would be exactly
what the brief forbids. ⭐ **What the suite asserts instead is narrow and true:
no module above `narrate/engine/` names `KokoroEngine` at all** (swept, not
claimed), and an adapter of another family satisfying only the contract is
served by every route. ⚠️ **The second real implementation is still owed and its
absence is stated in `narrate/engine/__init__.py` rather than papered over.**

**7. `consuming.json` names its own gap.** `voices` is `NS-04`'s half, so the
key is absent and `not_yet_declared: ["voices"]` says so. ⛔ **A consumer that
found no `voices` key and no marker could not tell *"this service has no
voices"* from *"nobody has written that part yet"*** — which is the same failure
`docs/api.md`'s *What is not here yet* table exists to prevent. `provides` is
minted at `1`: this is the first promise this component has published.

**8. The declaration cannot drift from the compose files or from the code
silently.** The suite asserts each declared engine image appears in the compose
file the declaration names, that the default deployment contains no device
reservation, and that every declared default and closed set is the module
constant the service enforces. ⚠️ **The compose files are read as text with
whole-line comments stripped, because this repository has no YAML parser and is
not acquiring one** — the limitation is written into the test module's own
docstring, and the comment stripping is load-bearing since `compose.yaml`'s
comments say `nvidia` and `devices` while explaining why the body must not.

**9. ⛔ `python3 -m tools.workspace record` was NOT run**, for the reason
`NS-01` measured: it rewrites the commit of **every** `present` row, which would
advance the `ISO-8583-jPOS-tutorial` pin that the board holds `pending` and
`docs/conventions/workspace.md` forbids advancing. ⭐ **One row was edited by
hand; `git diff --stat` says `1 file changed, 1 insertion(+), 1 deletion(-)`.**

**10. The CPU engine image was PULLED from `ghcr.io` over the network.** ⚠️
**Disclosed because `NS-01` recorded that its build needed no network at all and
this one did.** ⛔ **Nothing identifying the user was sent**: an anonymous
registry token and `docker pull`'s own user agent, no header, query string or
payload of mine. The image is pinned by digest in `compose.yaml`, so the pull is
reproducible and the next run of it is offline.

## Surprises

- ⭐ **A CPU build of the same engine at the same upstream version exists and
  works.** `NS-01`'s hand-off warned *"a CPU profile will need a different
  engine image; I did not pull one, so nothing about a CPU path is proven"* —
  `ghcr.io/remsky/kokoro-fastapi-cpu:v0.8.2` matches the GPU pin's version
  exactly, which is what let the overlay change the image and nothing else. ⚠️
  **Had the versions not matched, the overlay would also have had to change the
  request shape's assumptions, and *"switching profiles is not a code change"*
  would have been a much weaker claim.**
- ⚠️ **The CPU path is far less slow than the row's framing implies.** ~0.14
  real-time factor here. The row and the spec both treat CPU as the concession;
  on this hardware it is a perfectly usable default, and the corpus-sized
  question is throughput rather than feasibility.
- ⭐ **`docker compose config` turned out to be the right instrument for clause
  3.** It renders both deployments without starting either, so the *"not a code
  change"* claim is discharged by a diff of three lines rather than by reading
  two files and asserting they agree.
- ⚠️ **The context budget (~30k) was adequate but only because `NS-01`'s handoff
  is as good as it is.** Reading `E13`, R15, §8.2, `NS-01` and the component's
  own source came to roughly that; without the handoff naming the seam and the
  eight decisions it would not have.
