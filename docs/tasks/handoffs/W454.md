## Decisions

1. ⭐ **Deleting the modules is NOT enough, and that was measured, not assumed.** On a scratch layer
   of the current image with only the three `@github/copilot*` directories removed, the first
   workbench still made the server fork `bootstrap-fork --type=agentHost`. The fork logged
   `[IPC Library: Agent Host] Uncaught Exception: Error [ERR_MODULE_NOT_FOUND]: Cannot find package
   '@github/copilot-sdk' imported from …/agentHost/node/agentHostMain.js` to the server log. It then
   **stayed resident for the whole 40 s window without restarting**, and the workbench's console
   stopped at `Connecting to remote agent host...` with no `Connected`. So the answer to the row's
   question is: it neither crashes into a retry loop nor goes away. It lingers as a dead process,
   and one error goes to the server log. That is why the fork is switched off as well.
2. ⭐ **The server switch is the one that matters, and it had to be a bundle patch.** In 4.137.0 the
   server has three branches. It forks eagerly with `--agent-host-port/--agent-host-path`. It
   registers a bridge, or an *unavailable* channel, when any `--agent-host-bridge-*` flag is given.
   Otherwise it forks **lazily**, on the first client `connect`. ⛔ **No setting reaches that
   choice.** A code-server flag could (`--vscode-option agent-host-bridge-host=…` lands in the
   middle branch), but it would not reach the reader. The consuming contract's compose `command:`
   **replaces** the image's `CMD`, and the reader's compose does exactly that. Changing the
   entrypoint to append an argument would break its documented promise to pass arguments through
   untouched. So the middle branch's condition is prefixed with `!0||`. The server then runs
   upstream's own code path and logs `Registered unavailable IPC channel 'agentHostProxy'`, and
   every `connect` is refused with `Agent host proxy is not available because no upstream agent
   host endpoint was configured.` ⭐ **This holds whatever a client sends**, including a browser
   still holding a cached old workbench bundle (see *For dependents*, step 4).
3. ⭐ **The workbench switch removes the retry noise, and nothing else.** With the server switch
   alone, no process ran, but each window's workbench retried the refused connect at 1, 2, 4, 8, 16
   and 30 s. Each retry wrote a `WARN [RemoteAgentHostProtocol] Reconnect attempt failed …` line to
   the reader's console. The enablement for the web (`remoteAuthority && !chat.disableAIFeatures`)
   is now `!1&&…` in both bundles, so the workbench never calls `startAgentHost`. ⚠️ **Not the
   setting `chat.disableAIFeatures`.** It would do the same, but the seed only reaches a fresh
   volume and the reader's settings are theirs to edit. A workspace setting would be a framework
   change outside this row's surface.
4. ⭐ **`@vscode/copilot-api` goes too.** The build's own guard found it on the first build. It is
   the "module used for interacting with the GitHub Copilot API" (68 KB). Measured on the image,
   the only file that imports it is `agentHostMain.js`, and so do the three `@github` modules. The
   `copilotVersions` lookups in `ptyHostMain.js`, `extensionHostProcess.js` and the workbench read
   `package.json` metadata only, never the modules, so the terminal and the extension host are
   unaffected. The two-practice sessions below exercised the extension host.
5. ⚠️ **"Not in the image" means not in its filesystem.** The bytes are still in the code-server
   base layer, which this image builds on and cannot rewrite. A deletion in a later layer is a
   whiteout. The image even grows (`2.09 GB` → `2.14 GB`), because the step rewrites three bundles
   into a new layer. Reclaiming the bytes would need a squashed or rebuilt base. The ruling was
   about what the product carries and can run, and it can run neither.

## Surprises

- ⚠️ **`W449/1` said the agent host is forked "eagerly and before any browser connects". It is
  not.** In 4.137.0's default branch it is lazy. The server logs `Registered lazy IPC channel
  'agentHostProxy'` at start. `ps` inside a freshly started editor, before any browser, shows only
  code-server's two processes on BOTH images. The fork appears about 2 s after the first workbench
  connects. The practical conclusion does not change, because every practice window is a workbench.
  It is recorded as `W454/1`.
- ⚠️ **`tests.test_editor_image` cannot pass on this host, and not because of this row.** Its build
  is the DEFAULT set, and that build is refused by the confinement gate at `a34a93e` too (see
  `W454/2`).
