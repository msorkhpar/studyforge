#### 1. The manifest key — `runtimes`

```json
{ "corpus_api": 4,
  "exercises": true,
  "runtimes": ["java", "maven"],
  "…": "the other keys as today" }
```

| property | proposed | why |
|---|---|---|
| name | `runtimes` | the user's word, and it names *what runs the corpus's commands*, not an editor's toolchain |
| shape | a JSON array of names, no duplicates; order carries no meaning and `Manifest.runtimes` holds it **sorted** | a set is what the image builds; sorting makes two equal declarations one value (R10) |
| vocabulary | **closed**: `gradle`, `java`, `kotlin`, `maven`, `node`, `python`, `shell`, `sqlite` | the user's list — Java, Kotlin, Python, Node.js, shell, SQL in-memory — with the build tools named separately, because `mvn` and `gradle` are what an exercise's `test_command` actually invokes |
| names only, **never versions** | a corpus says *which*, the pin file says *which version* | a version in a corpus manifest would be a second place a version is chosen, which the epic forbids |
| dependencies | `maven`, `gradle` and `kotlin` each **require** `java` in the same list; a set missing it is refused by name | nothing is inferred, the same rule `corpus_api` follows: a declaration says what it means |
| `runtimes` with `exercises: false` | **refused** | it declares a runner for nothing to run; §7 has no graded or runnable unit without `exercises` |
| `exercises: true` without `runtimes` | **permitted** | an ungraded corpus (SPARQL's shape) needs no runner |
| **absent** | exactly `[]`: **no runner.** The framework neither builds, probes nor starts a container for it, and `buildserve`'s `NO_TOOLCHAIN` state is the honest report | ⛔ **a corpus that declares none is complete at the reading floor** (§7, C5, §11.0), and a corpus with no runtimes writes nothing, as with `media` |
| version | **`corpus_api: 4`**; `runtimes` under `1`–`3` is refused naming both numbers | R9: a manifest using the key is unreadable to an older build, which would otherwise blame the corpus |
| where it is parsed | a new module beside `media.py`, `corpus/manifest/runtimes.py`, which spells the vocabulary **once** as its constant | `document.py` is at its R11 bound (`TC-00/3`) |

⚠️ **`sql` is spelled `sqlite`, deliberately.** *"SQL"* names a language, not something an image can
carry; a runtime is an engine. ⭐ A second engine is a second vocabulary entry and a `corpus_api` bump,
exactly as `variants` was kept from answering *"is this runnable?"* (§4).

⚠️ **`shell` adds nothing to the image** — the base carries `bash` — and it is still declarable,
because the declaration is what lets the build **assert** it is present rather than assume it.

#### 2. Where each version is pinned — ONCE, in `code-server-toolchain/pins.json`

⭐ **One file at the ROOT of the component, never under `docker/minimal/`,** so `TC-02`'s editor image
at `M7` reads the same file and *selects* from it. ⛔ **No `ARG` in any Dockerfile carries a default
version or checksum**: the build script reads `pins.json` and passes every one, so a build that
bypasses the file fails on an empty argument instead of quietly choosing.

```json
{ "pins_api": 1,
  "base":     { "image": "debian:trixie-slim", "digest": "sha256:…" },
  "runtimes": {
    "java":  { "version": "…", "arrives": "image",   "image": "eclipse-temurin:…-jdk", "digest": "sha256:…" },
    "maven": { "version": "…", "arrives": "archive", "url": "https://archive.apache.org/…", "sha512": "…",
               "checksum_source": "…" },
    "node":  { "version": "…", "arrives": "archive", "per_arch": { "amd64": { "sha256": "…" }, "arm64": { "sha256": "…" } } } } }
```

⭐ **The two one-way checks, and neither is an equality** (the shape Ruling 30 gave `MANIFEST_KEYS`):
a name the framework's vocabulary admits and `pins.json` does not pin is **refused by the build, by
name, listing what is pinned**; a pin no vocabulary names is harmless (undeclarable). ⭐ Stage 2 lands
a pin for **every** vocabulary entry, so the refusal is green on the day it lands.

⚠️ **A pin is one version per runtime.** A corpus needing a *different* JDK major is a new decision,
not a manifest value — recorded as deliberate. Measured: the Java corpus's POM declares release `21`
and `CodeSignal`'s Gradle toolchain declares `26`; one JDK `26` compiles both, since `--release`
targets downward.

#### 3. How each runtime ARRIVES, pinned

⭐ **The rule: a checksum is a pin when it is RECORDED IN THE REPOSITORY and the build checks against
the recorded value, fetching no checksum at all.** ⛔ **`CodeSignal`'s build fetches each checksum from
the same host as its archive at build time** — measured in its Dockerfile, for Gradle, Kotlin and Node
— which proves only that the host agrees with itself. ⭐ **The recorded value's PROVENANCE is taken
once, at pin time, from a source independent of the download host** (a signature, or a second
official host) and written into `checksum_source`, so the register can re-check it.

| runtime | arrives as | pinned by | provenance to record at pin time |
|---|---|---|---|
| base | `debian:trixie-slim` | image digest (multi-arch index) | the registry |
| `java` | `COPY --from` an official `eclipse-temurin` JDK image into `/opt/java/openjdk` | image digest | the registry |
| `maven` | the Apache binary tarball, from `archive.apache.org` (a URL that never moves) | recorded SHA-512 | Apache's detached signature against its `KEYS`, or the same artifact's checksum on Maven Central |
| `gradle` | the official distribution zip | recorded SHA-256 | a second Gradle host — **question S5** |
| `kotlin` | the JetBrains compiler zip | recorded SHA-256 | **question S4**: an independent second source may not exist |
| `node` | the official tarball, per architecture | recorded SHA-256, per `TARGETARCH` | `SHASUMS256.txt` verified by its release-key signature |
| `python` | **question S7**: the official image's `/usr/local` onto the same Debian release, or a standalone build | image digest, or recorded SHA-256 | the registry, or the publisher |
| `sqlite` | the official precompiled CLI | recorded SHA-256, per architecture | **question S8** |
| `shell` | the base's `bash` | the base digest | — |

⭐ **Architectures:** `amd64` and `arm64` are recorded; any other `TARGETARCH` fails loudly naming
itself — the prior art is this repository's own [`docker/dev/Dockerfile`](../../../docker/dev/Dockerfile),
whose Node block does exactly that.

⛔ **A runtime's TEST RUNNER is part of the runtime only where it is not built in**, and that matters
at once: `node:test` needs nothing; `python` needs `pytest`, pinned by hash (`--require-hashes`); and
**`maven` needs a local repository holding the compiler and surefire plugins and JUnit before
`mvn -o test` can run at all** (`TC-00/4`). ⭐ Stage 2 warms **one generic set** for its own smoke
project, each artifact pinned by a recorded checksum (**question S3**); ⛔ **per-corpus warming stays
`TC-03`'s** at `M7`.

⭐ **Prior art taken from `CodeSignal`, in these words and not by reference (R20):** the JDK arrives as a
whole tree copied from the official image, with `JAVA_HOME` at its root; `PATH` is set by `ENV` **and** by
a `profile.d` script, because a login shell rebuilds `PATH` from `/etc/profile` and drops `/opt`; an
architecture outside the recorded set fails the build rather than downloading something unverified.

⛔ **Refused from it:** its `:latest` inputs, its build-time checksum fetches, its unpinned
`npm install -g` and `uv pip install`, its editor base, and **building FROM its local image at all.**
⛔ **That image is not a pin.** Its `RepoDigest` is a local content id with no registry behind it, so

## Decisions

- ⭐ **The runtime set is per corpus, declared once in the manifest, and never per exercise.** One
  container, one cache, one image per corpus; a set derived by scanning exercises would be inferred,
  not declared.
- ⭐ **Build tools are vocabulary entries of their own** rather than bundled into `java`: a Gradle-only
  corpus and a Maven-only corpus are both real, and bundling would put an unused toolchain in each —
  against the Acceptance's *"contains no toolchain EX-00 does not use."*
- ⭐ **`gradle` is in the vocabulary although no `M5` consumer needs it**, because `TC-02` must
  *select* from these pins and never add one; leaving it out would make `TC-02` a second place a
  version is chosen.
- ⭐ **The base image is `debian:trixie-slim`, not a runtime's image** (stage 1; stage 2 refines it for `python`, below), so a corpus declaring no
  `python` gets no Python: basing on `python:3.14-slim` would ship a toolchain the corpus did not
  declare.
- ⭐ **Stage 2: `python` arrives AS THE BASE, only when declared.** The official image is Debian
  trixie-slim plus Python, so a set with `python` gets exactly that and a set without it gets the plain
  base. ⚠️ Copying `/usr/local` out of it onto the plain base was the alternative, and it would have
  dropped the shared libraries the image installs beside Python. ⚠️ The cost, recorded: a set with
  `python` sits on the Python image's Debian layer, which is not byte-identical to the pinned base.
- ⭐ **Stage 2: the Python image is also the UNPACKING tool** (standard-library `zipfile` and `tar`),
  in build stages only; nothing from it reaches an image that did not declare `python`.
- ⭐ **Stage 2: the Maven smoke project names no plugin version.** Maven's default bindings decide
  them, so the pinned Maven decides them and the smoke's POM chooses only JUnit.
- ⭐ **Stage 2: no `JAVA_HOME`.** It would point at nothing in an image built without `java`; every
  launcher finds `java` on `PATH`. `HOME` is `/tmp`, so no tool writes caches into the mounted sources.

## Surprises

- ⚠️ **The row's surface is narrower than its proposal.** `TC-00` owns `TC/`; the key it must propose
  lands in `src/studyforge/corpus/manifest/`, the spec's §4 table, and the reconnaissance skill that
  drafts manifests (R19) — none of which the row owns (`TC-00/1`).
- ⚠️ **`mvn -o test` is not a property of a JDK and a Maven.** It needs a warm local repository, which
  the epic places in `TC-03` at `M7` (`TC-00/4`).
- ⚠️ **Stage 2: the local image IDs on this host ARE multi-arch index digests** — the stage-1
  question `S1` asked whether they were. Measured: the registry's index digest for
  `python:3.14-slim-trixie` is `cad9a2c8…`, which is the local image's ID and the digest
  `studyforge`'s own contributor image already pins.
- ⚠️ **Stage 2: the Maven warm for one tiny project is hundreds of files** (every artifact beside its
  `.sha1`), so `pins.json` is mostly the warm's list. That is the honest size of *"pinned artifact by
  artifact"*, and it is what `TC-03` will face per corpus.
