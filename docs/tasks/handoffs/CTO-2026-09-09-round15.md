# ⛔ The `label` seam: the reported defect is a symptom

**Reported:** `fields.LABEL_FORBIDDEN` is `"/\\ \t\n\r"`; `names.py` re-spells
it as `"/\\ \t\n"`, so a carriage return passes placement. ⭐ **Correct, live,
and found by a sequencing instruction rather than a gate.**

⛔ **I ran the wider probe on the merged tree and it is not one character.**

| `label` | container map | `label_of` | filename it writes |
|---|---|---|---|
| `a/b` | refuses | refuses | — |
| `a\r b` | refuses | ⛔ **accepts** | `a\r b-t.unit.html` |
| vertical tab | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| form feed | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| non-breaking space | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| Unicode line separator | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| a double quote | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| a colon | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |
| an asterisk | ⛔ **accepts** | ⛔ **accepts** | ⛔ **both** |

⛔ **Seven shapes pass both gates into a filename**, and the colon and the quote
break the `file://` floor (R8) on a platform this project promises to run on.
⚠️ **Fixing the CR and stopping would have left every one of them**, and the
next report would have read like this one.

## ⛔ Ruling 8 — a filename component is validated by what is permitted

⛔ **A forbidden list is an open set and cannot be finished.** Every character
nobody thought of is permitted by default, so the list is wrong the moment it is
written and stays wrong silently — which is exactly what happened, in duplicate,
in two packages, past two reviews and a gate.

⭐ **State the permitted class.** One predicate, closed: what a slug accepts,
plus `.` so `4.4.1` passes. A character nobody thought of is then refused by
default, and the rule is one line that cannot rot.

⚠️ **This project already applies closed sets everywhere else** — an unknown
contract version is refused rather than migrated (R9); an unknown profile name
is refused *listing the ones there are*; an unknown document key is refused
rather than ignored. ⛔ **The character blacklist was the one open set left**,
and it survived because it looked like a filename question rather than a
contract question. It is a contract question: `label` is only ever a filename
component, and that is the whole reason the field exists.

⭐ **One implementation, in `fields.py`, imported by `names.py`.** SF-05
exported `LABEL_FORBIDDEN` precisely so placement could use it; placement
re-typed it instead. ⛔ **A constant that is exported and then re-typed is a
finding on sight** — before anyone checks whether the copies agree.

## ⛔ And §1f survived both of my reviews, two lines from the defect I caught

`names.py:112` is `f"unit label becomes part of a filename, got {label!r}"`.
⛔ **That is rubric §1f — the clause I wrote in round 14 — and a label is read
straight out of a file somebody else authored**, so it can be an absolute path.

⚠️ **SF-05 refused to echo for exactly this reason and named the character class
instead.** The right answer was in the other half of the seam, in the tree,
while I reviewed the half that got it wrong.

⛔ **Why I missed it, and it is not "I was in a hurry".** I found the echo in
`relative_href`, wrote it up, and moved to the next function. **I read the
function under discussion instead of the module.** A rule applied at one site
and not its neighbour is the shape *both* of §1f's misses have had — SF-03's own
author did the same thing between `origin_directory` and `relative_href`.

⭐ **Rubric §1f now says so:** when one branch is corrected for echoing a value,
read **every other raise in the same file** before moving on. ⚠️ And diff two
enforcements of one rule whenever two modules enforce it.

⭐ **Recorded as the fifth vantage-point instance, and the first found by a
prediction.** "No test today spans that seam" was a guess in a handoff; running
once with both is what made it a measurement. ⛔ That is worth more than the
finding: **an untestable claim about a seam becomes testable the moment the two
halves are in one tree**, and the instruction to put them there costs nothing.

## ⛔ Ruling 9 — `CONTRACT_FIELDS` is a guaranteed conflict, and that is a design fact

⚠️ **Three consecutive contract tasks have edited one tuple; the third
collided.** SF-03 already put it one name per line to reduce this, and it
collided anyway, because every task appends at the same place.

⛔ **Sorting it does not fix this** — it moves the collision, it does not remove
it. ⭐ **Two honest options, and I am ruling the first:**

1. ⭐ **Keep the explicit tuple and accept the conflict as the cost of the
   guard.** A one-hunk conflict that git shows you both sides of is cheap, and
   the alternative — discovering fields by scanning — is a guard that cannot
   tell a contract field from a variable that happens to end in `_api`. ⛔ **The
   explicitness is the mechanism**; a registry a task must *deliberately* join
   is the thing that makes "or the guard cannot see it" true.
2. A per-package registration call. Rejected: it puts the list back where the
   guard cannot read it without importing every package, which is the coupling
   `version.py` exists to avoid.

⚠️ **So the ruling is: this conflict is expected, and the task documents it.**
`version.py`'s comment already says a task registers its field in the same
commit; it should also say **that this line is a known conflict point and the
resolution is always "keep both, in the order they merged"**. ⛔ A conflict
nobody warned you about gets resolved by picking a side.

# The four questions

## 1. R9's sentence → a pointer. ⭐ Agreed, and edited

The spec listed five fields; the constant holds seven. ⛔ **A list written twice
is a list that disagrees with itself, and this one already did.** R9 now states
the *rule* and points at `CONTRACT_FIELDS` for the *list*; the register says
which contract, the constant says which field name.

⭐ **SF-09's diagnosis is the part I kept**, because it explains the drift rather
than patching it: the five originally listed are every document the framework
**writes**. The overlay is the one it only ever **reads**, so it fell out of an
enumeration built — without anyone deciding it — around authorship. ⛔ **A
contract is versioned because somebody reads it, not because we wrote it.**

**Applied:** spec §R9, and the R21 register's overlay row now reads `content_api`.

## 2. "Name the type, not the value" in eight modules. ⭐ Ruling 10 — extract it, as a task

⚠️ **Measured: 10 sites, 8 modules, 5 packages, and three named functions** —
`version._said`, `container.said`, `unit.describe`.

⛔ **They have already drifted, which is the argument.** Two quote integers, on
the stated grounds that an integer cannot carry an identifier and a refusal that
will not say `unit 4` is unactionable. The third returns *"an int"*. ⚠️ Nobody
chose that difference; it is what a third copy does.

⭐ **One implementation, in its own module — `src/studyforge/describe.py`** —
depending on nothing, importable by everything, with integer-quoting as the
behaviour, because two of three chose it and stated why. ⛔ **Not inside
`version.py`.** Round 12 ruled one concept, one home; a value-describer filed
under versioning is the same misfiling `trust.py` correctly avoided this round.

⭐ **SF-09 was right to leave it, and right about why.** This touches eight
modules in five packages: it is a task, not something slipped into a diff about
overlays. ⚠️ It is also **not** a refactor to do while three branches are in
flight — it is FND-06's follow-up batch, after M1 step 1.3 lands.

⭐ **And the shape of the finding is the good part**: the `Measured` field caught
its own author drafting "written three times" when it is eight. ⛔ A finding
about verification, corrected by verification, inside the round where a CTO
ruling was overruled for the same reason. Keep it in the handoff.

## 3. `VARIANT_KINDS` — renamed, not narrowed. ⭐ Endorsed, and it is now precedent

**A check narrowed by the first task it inconveniences stops being believed.**
⛔ That is the whole doctrine and a developer under deadline applied it against
their own interest. ⚠️ **This is the standard for every tripwire in this
repository**: when a tripwire fires on your own work, the burden is on you to
show the tripwire is *wrong*, not that you are *in a hurry*. Round 8's rubric
change came from me failing this test; SF-09 passed it unprompted.

## 4. The `contact@example.com` gate test. ⛔ Ruling 11 — the third instance is a rule

⚠️ **Three times a test of a gate would have passed with no gate.** This one used
the documented placeholder the personal-data gate **deliberately allows** — so it
asserted a refusal that was never going to happen. ⭐ Caught by its author; the
two before it were not.

⛔ **An assertion that a mechanism refuses something is worthless until you have
watched it pass without the mechanism.** ⭐ **Delete the call, run the test, see
it fail, put the call back.** Thirty seconds, and it is the only thing separating
a test of a gate from a test of a fixture.

⚠️ **The tell, so it can be caught in review:** a negative fixture built from a
**documented placeholder or a sanctioned exception**. Those are exactly the
values the mechanism exists to let through. ⛔ Round 14's §1f and this are the
same failure seen twice — a check whose input cannot reach the branch it claims
to test.
