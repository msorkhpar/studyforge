## Ruling 1 — the rubric's review base · ⛔ my defect, and a bad one

**Confirmed by measurement**, and worse on the branch that found it: `merge-base
HEAD main` gives **106 changed files** where `merge-base HEAD
release/m0-foundations` gives **14**.

⭐ **The failure mode is why this matters more than the arithmetic.** It is silent
and it *flatters*: the reviewer sees more work, not less, and every downstream
check then runs over three other tasks' code attributed to one author. A rubric
that appears to be working harder is not one anybody questions. ⚠️ My own first
two reviews escaped only because they hardcoded a SHA that happened to be right
that day.

**Fixed:** the base is `${REVIEW_BASE:-release/m0-foundations}` — ⭐ *the branch
the change will merge into, never `main` by reflex* — and §0 now **prints the
base and the file count** with the instruction to read them before running
anything. ⛔ **The count is the guard:** if it does not match the task's `Owns`,
the base is wrong, stop.

⚠️ **The four Python checkers had the identical bug** and none of my reviews
would have caught it, because they each re-derived the base internally where
nobody was looking. All four now read `REVIEW_BASE`. ⭐ **A rubric with two
definitions of its own range is the same defect it exists to find in other
people's code** — one visible, one buried, disagreeing silently.

## Ruling 2 — `FND-05a` under "nothing is ever pushed"

⭐ **The workflow survives. The composition does not. `FND-05b` is cancelled
outright, not deferred.**

**Submodules have no legal form here, and all three roads are closed:**

| Form | Why it fails |
|---|---|
| absolute local path in `.gitmodules` | writes a home directory into a **tracked** file — ⛔ direct R7 violation |
| relative URL | R7-clean, but git resolves it against the **parent's own remote**, which does not exist |
| a real remote URL | names a commit **nobody pushed**, so it resolves to nothing anywhere, ⛔ **including here** |

⭐ **What replaces R18's guarantee — and the answer is that most of it never
depended on pushing.** A submodule is exactly two things: a **URL** and a
**commit**. Only the URL half needed a remote. So the parent records each
component's verified commit in a **tracked pin file** and **verifies it against
the local checkout** — which is mechanically checkable, in the way this project
checks everything else, rather than documented as folklore.

⚠️ **The honest claim shrinks and is now stated rather than implied.** This
reproduces a configuration **on this machine and across time** — which is exactly
what R9's cross-repository versioning needs. ⛔ It does **not** reproduce one
across machines, and no document in the workspace may say it does. R18 previously
claimed the stronger thing; it has been amended rather than left to be
discovered.

⭐ **`studyforge` goes into the pin file too.** The whole reason it was excluded
was that it had no remote — and with nothing being fetched, that reason is gone.
So `FND-05b`'s content evaporates rather than moving: `TC/` and `NS/` become rows
added by E12 and E13 as they create those repositories. **No task is needed.**

⚠️ **The silent first-run failure has changed shape, not disappeared.** It is no
longer "a plain clone yields empty submodule directories" — nobody clones this.
It is now **a component sitting at a commit the parent never recorded**: the same
surprise (your change is not part of the configuration) with no symptom at all.
⛔ That is why verification is a command with an exit code and not a paragraph.

⚠️ **One consequence beyond FND-05, and E11 owns it.** §9 said a consumer obtains
the skills by pinning the framework **as a submodule**. That is now a sibling
checkout at a recorded commit. ⭐ The load-bearing half is untouched — never
vendored, never copied, never forked, and a drifted stub is still a build failure
— but `SK-07` must not be written against `git submodule add`.

## Ruling 3 — an account name in the material · ⛔ unblocks E07

`FND-02` finding 3: the Java corpus carries its owner's account name in **345
file paths, in every `import`, and in a code block on every generated page**.

⭐ **X2's reasoning reaches it, but X2's *wording* does not — and the wording was
mine, so this is a correction rather than an extension.** X2 said R7 governs
identifiers that are not *the material's subject matter*. A test PAN is what an
ISO lesson teaches; an account name in a package path is incidental to what a
Java lesson teaches. The underlying test is the one that generalises:

> ⭐ **The gate's question is not "is this string identifying?" but "did this
> build put it there?"**

That name reached the document because the corpus owner chose it years ago and
committed it. The build environment contributed nothing, and rendering
`import com.github.<account>.Foo;` on a local page discloses nothing the source
the reader already has did not.

⛔ **Scrubbing it would be worse than useless.** It rewrites the material's own
source into a placeholder — the failure `SF-08`'s task text already names — and
it emits Java that does not compile, breaking Run and Submit for the whole
corpus.

⭐ **But the decisive argument is that the pattern cannot exist, and it is
general.** To match *"this is the user's username"* the gate must **hold the
username** — which means the framework stores the exact personal datum R7 forbids
it to hold. The only alternative is an unanchored identifier pattern, which
matches every symbol in every codebase. ⛔ **A gate that must contain the secret
to detect the secret is self-defeating.** So `SF-08` never grows a username
pattern, and the reason is not convenience.

⚠️ **What this does not license.** An **email address** in a lesson comment is
still refused — an email is an environmental shape wherever it appears, and its
pattern needs no stored value. The exemption is for shapes with **no structural
anchor**, not for identifiers the gate can already recognise. That is also why
CodeSignal's `/learn/profile/<name>` pattern is legitimate: the URL path is the
anchor, and it never has to know the name.

## Ruling 4 — R14's qualification reaches the spec

⭐ **Yes, it belongs in the ruling and not only in the convention**, and `FND-02`
was right to surface it rather than bury it.

`explain` and `path` hold unconditionally — sub-second, a few hundred tokens,
against ~20k tokens of equivalent reading. `query` holds **only when phrased as
distinctive nouns**; asked as an English sentence it returns confidently wrong
material.

⛔ **The reason it cannot stay in the convention alone is that every task's
context budget is set from R14.** A budget premised on a tool that answers
*slowly* produces late work. A budget premised on a tool that answers *wrongly*
produces wrong work, **and the agent gets no signal that it did**. Those are not
the same risk and the ruling was silently claiming the first.

R14 also now says it binds on a repository **when it enters the working set** —
the edit I owed from the M0 audit, which `FND-02` correctly carried into the
convention and correctly refused to make in the spec on its own authority.

## Ruling 5 — the R11 / formatter conflict (`FND-03`)

⭐ **`FND-03`'s exclusion stands as an interim. The resolution is the split, and
it belongs to `FND-04`'s already-open follow-up.**

`tests/test_fixture_consistency.py` is 554 lines; the formatter's magic-trailing-
comma handling explodes its hand-packed key tuples to **606**, over R11's 600.

- ⛔ **Authoring a `Size exception:` is wrong on principle.** The rubric says an
  exception states *why splitting would be worse* — and splitting is not worse
  here: the module has five natural seams its own handoff already named (shape ·
  digests · addresses · media · personal data). ⛔ **And a third party cannot
  author one anyway**, because the exception turns on the isolation question,
  which only somebody who understands the module's internals can answer.
- ⭐ **The split is not optional, because the file is going over 600 regardless.**
  `FND-04`'s open follow-up — the `disclosure` fixture change — *adds* to
  `BLOCK_FIELDS` and `COUNT_KEYS`. Formatting is not what pushes it over; it is
  what pushed it over first.
- ⭐ **The one-entry assertion is the right mechanism and I want it kept until the
  split lands.** An exclusion list that cannot grow without a test failing is
  what stops it becoming where difficult files go.

**So `FND-04`'s follow-up gains a fifth step:** split the module along its five
seams, then delete the formatter exclusion and its assertion together.
