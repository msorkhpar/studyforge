## What landed

⭐ **What the software does now that it did not:**
`python3 docker/minimal/build.py --runtimes gradle,java,maven --prime <dir>` builds a runner
that already holds that corpus's practice dependencies. Inside it, `docker exec … mvn -o test`
and `docker exec … gradle build --offline` succeed with **no network and no cache flag of their
own** — the image points `MAVEN_ARGS` and `GRADLE_USER_HOME` at the seeds it warmed. Before, the
runner carried only the generic Maven warm for its own smoke project, so a graded run of a
corpus's practice would have tried to download and, under `--network none`, simply failed.

- The prime is **read and guarded before Docker starts**: a prime whose build tool the declared
  set does not hold, or which names a Gradle, Maven, Kotlin, toolchain or Java release other
  than the pins, exits 2 naming the file and both versions. That is `prime/prime.py`'s existing
  guard, called from the runner's `planned()` exactly as the editor calls it from its `plan()`.
- The image is **tagged only after the warm is proved**: the last thing the build does with the
  seed is run a fresh copy of the prime against a copy of it under `RUN --network=none`.
- **A corpus that declares none is untouched**: no `--prime`, no warm, no `/opt/prime`, an empty
  `MAVEN_ARGS` and Gradle's own default under `HOME` — which is what the image already had.

## Decisions

- ⭐ **The seeds live under `/opt/prime`, not under `HOME`.** `/work` and `/tmp` are where a
  mount contract puts things (`TC-05`'s), and a seed under either could be shadowed by a volume
  or a tmpfs without a word. `/opt` is where this image already keeps what it built, and the
  build's own `/opt` check names `prime` when, and only when, the image was primed.
- ⭐ **No entrypoint, and no copy at start.** The editor copies its seed into `$HOME` because a
  named volume shadows the image there; the runner mounts only the source at `/work`, so the
  seed is simply used where it lies. ⛔ **That makes it writable by any uid a `--user` may
  bring** (`chmod -R a+rwX`): the documented run line passes the reader's own uid, both tools
  write into their cache, and a root-owned seed would fail for every reader. The container has
  no network and belongs to one reader.
- ⭐ **`ENV GRADLE_USER_HOME` / `ENV MAVEN_ARGS` are set after the version checks**, so
  `gradle --version` writes its scratch into `HOME` and never into a seed a reader is about to
  use. `HOME` itself now comes from `plan.RUNNER_HOME`, so the path is chosen in one place.
- ⭐ **No `PRIME_KEY` of its own, unlike the editor.** `CACHE_KEY` is this image's tag, the tag
  folds the prime's digest, and the runner stage's first RUN reads it (`W379`) — so every layer
  the warmers write is already cached per prime. An extra argument would have pinned nothing.
- ⛔ **The warmers are folded into a PRIMED build's digest only.** Putting `prime/` in
  `INPUT_ROOTS` would move every unprimed runner tag when a warmer changed, and the editor's
  own test holds Ruling 2 — an editor-only change moves no runner tag — with `prime/warm-maven.sh`
  as its example. A warmer runs only in a primed build, so that is the only digest it enters.
- ⭐ **`inputs_digest` skips `__pycache__`, and now takes its roots.** `prime/__pycache__`
  exists on any checkout that has imported the contract; hashing it would have given one image
  two tags depending on whether a module had been imported.
- ⭐ **Every build names the `consumer-prime` context**, an empty `.work/no-prime` when there is
  no prime: a `RUN --mount` is not conditional, so the flag cannot be optional. `.work/` is
  git-ignored and `.dockerignore`d already.

## Surprises

- ⚠️ **The `prime/` directory is an input of BOTH images now, and the editor's test says a
  change to it must not move a runner tag.** That test (`tests/test_editor_plan.py`, `TC-03`'s)
  is what settled the digest decision above; it passes unchanged.
- ⚠️ **A tag change costs a full re-warm.** Any edit to `docker/minimal/`, `pins.json` or
  `prime/` moves `CACHE_KEY`, and every layer of the runner stage above it — the warm included —
  is then a cache miss. Worth knowing before a one-character edit between two image runs.

## Findings

- `[structural]` **`W390/1`: every runner tag moves, and so does every editor tag.**
  `docker/minimal/plan.py` and the Dockerfile are inputs to the runner's digest, and the editor
  folds the runner's digest into its own. Moving `workspace.json`'s pin to the sibling's new
  `main` is the register's job, as it was for `W387`.
- `[local]` **`W390/2`: the runner has no equivalent of the editor's "leave a reader's cache
  alone" rule.** The editor's entrypoint seeds only an empty directory; the runner's seed is the
  image's, and a reader's writes into it live only for that container's life. Nothing is lost —
  the runner is not where a reader keeps anything — but a later mount contract that puts a
  volume on `/opt/prime` would need the editor's emptiness check, which does not exist here.
- `[local]` **`W390/3`: `/opt/prime` must stay writable.** A compose contract that mounted `/opt`
  read-only, or ran the container with a read-only root filesystem, would break every graded
  Gradle run: Gradle writes into its user home on every build. `TC-05` should mount neither.
- `[structural]` **`W390/4`: nothing in the framework passes a prime yet.** The image can be
  warmed; choosing a corpus's prime directory, declaring its practice dependencies and naming
  the primed tag is `M10`'s, and it is the only step left between this and a graded run.

## For dependents

- ⭐ **`M10` / `E14`:** the seam is `docker/minimal/build.py --prime DIR`, where `DIR` holds
  `gradle/` and/or `maven/` exactly as `prime/prime.py` defines them (the editor's contract,
  unchanged). The tag it prints already names the prime. A graded run then needs **no cache
  flag**: `docker exec <container> sh -c 'cd <dir> && mvn -o test'` resolves offline.
- ⭐ **`TC-05`:** see `W390/3`. Also, an image built with no prime is byte-identical in this
  respect to what you have been mounting: no `/opt/prime`, empty `MAVEN_ARGS`.
- ⭐ **Anyone adding a third warmer:** add it to `prime/prime.py`'s `TOOLS`, to
  `plan.PRIME_SEEDS`, and to both RUNs in the Dockerfile. A test holds the first two equal and
  reads the Dockerfile for each seed's warm and prove line, so forgetting one is RED.

## Measured

On this host (linux/amd64), the sibling branch, the host's `python3`, and a Docker CLI with
BuildKit. ⭐ **The reading the row asks for** — a run under `--network none` — is
`tests/test_runner_prime_image.py`, which builds the `gradle,java,maven` runner twice, warmed
from `tests/fixtures/prime/` and not warmed, starts each container with `--network none` and
`--user 4242:4242` (an arbitrary uid with no passwd entry, because the documented run line
passes the reader's own), and runs the graded commands with `docker exec`.

⭐ **Both ways, in the same module:** the primed image's Gradle build and `mvn -o test` succeed
and every compile and test task runs; the same two commands in the **unprimed** image fail, and
in the primed image they also fail when pointed at an empty cache — so it is the seed, and not
something else in the image, that made them work.

⭐ **Both ways on the host:** a prime the declared set cannot build is refused with exit 2
before Docker is touched, and the same prime with `maven` declared plans; a primed tag, a
gradle-only primed tag and an unprimed tag are three different tags, and appending a byte to
`prime/warm-maven.sh` moves the primed one and leaves the unprimed one where it was.
