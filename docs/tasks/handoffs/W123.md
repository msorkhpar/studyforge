## 1. ⛔ The defect, confirmed a third time by reading the code

⭐ **RECEIVED as `W36/2`, confirmed by the CTO, and CONFIRMED AGAIN by me at
`tests/visual/browser.py:172-181`:** `call()` sets `deadline = time.monotonic() +
CALL_TIMEOUT` and loops `while time.monotonic() < deadline`, but the loop body is
`self._receive()`, which blocks in `os.read` on a live pipe with no deadline. ⛔ **So
`BrowserError(f"{method}: no answer in {CALL_TIMEOUT:.0f}s")` at `:181` is unreachable for a
browser that is UP AND SILENT; it fires only if the pipe CLOSES.**

⛔ **I DID NOT TOUCH IT.** ⭐ **Ruling 235(a)'s ground and it is better than ownership:
`select`-ing on the fd is a different I/O path, so fixing it inside the harness would change
what every one of the 57 first readings was taken against. That stays with `QA-03`'s
successor.**

## 3. ⛔ WHY THE BOUND IS INSIDE THE CONTAINER — three measurements, not a preference

⭐ **The row and the ruling both say "an outer `timeout` around the suite" without saying on
which side of the boundary. ⛔ I measured, and the readings put it inside:**

1. ⛔ **THE HOST'S `timeout` IS NOT THE SAME PROGRAM.** **[MEASURED]**: `uutils coreutils
   0.8.0` on this host, `GNU coreutils 9.7` in the pinned image. ⚠️ **And on macOS there is no
   `timeout` at all.** ⭐ **A bound whose implementation depends on the host is an UNPINNED
   bound — Ruling 238's own reasoning applied one level down, to the instrument rather than to
   the environment.**
2. ⛔ **`docker/dev/check` CLAIMS, IN ITS OWN HEADER, that it uses only `docker`, `id` and
   shell builtins** — *"the whole claim of this task is that a contributor needs Docker and
   nothing else"*. ⚠️ **A host-side `timeout` would falsify that claim in the same file that
   makes it, which is Ruling 239's shape.**
3. ⭐ **Inside, it bounds the COMMAND and not the image BUILD.** ⚠️ `--build` runs on every
   invocation and can legitimately take minutes on a cold cache and a slow link; ⛔ **the thing
   that hangs is a read inside the suite.** ⭐ **Bounding the right one is what keeps the
   default figure small enough to mean something.**

⭐ **MEASURED that the status propagates unchanged out through `docker compose run --rm`:
that is the whole of the table in §2, every row of which was taken through `check` itself.**
⭐ **And no container leaked: `docker ps -a --filter name=studyforge-dev` is empty after the
wedge.**

## 5. ⭐ The default figure, and Ruling 236 applies to it

⛔ **`STUDYFORGE_CHECK_TIMEOUT` defaults to `1800` seconds and the file SAYS it is loose,
because Ruling 236's second half binds any threshold chosen to be loose.** ⭐ **MEASURED at
`af31fd7` in the pinned image: the whole suite runs in **57.66 s** and `tests/visual/` alone
in **8.44 s**, so the margin is about **31×**.**

⚠️ **It is that loose deliberately and the reason is printed beside it: with
`STUDYFORGE_DOCKER_TESTS=1` the command itself builds images and runs the suite inside them,
and a contributor's hardware is not this hardware.** ⛔ **A bound that fires on a healthy run
is a bound somebody deletes** — ⭐ and `STUDYFORGE_CHECK_TIMEOUT=0` is GNU `timeout`'s own
"no limit", documented rather than invented, so the escape is to raise or disable it rather
than to edit the script.

## 6. ⛔ The no-argument case is a CHECKED copy of the image's `CMD`

⚠️ **`timeout` needs a command, so the no-argument path has to name one — and naming it is a
SECOND COPY of the Dockerfile's `CMD`, which is precisely the host/container divergence this
wrapper exists to prevent.** ⭐ **So it is a checked copy:
`test_the_no_argument_case_names_the_image_s_own_command` parses the Dockerfile's `CMD` as
JSON and asserts `check`'s `set --` line is the same argv.** ⛔ **Planted and confirmed to
fire: changing the fallback to `python3 -m unittest` reds it.** ⚠️ **This is the idiom
`test_dev_image_browser.py` already states for `CANDIDATE_NAMES` — *imported in spirit rather
than by reference, so the check can notice the two disagreeing*.**

## What landed

- ⭐ **`docker/dev/check`** — an outer bound **inside the container**:
  `timeout --kill-after=30s "$STUDYFORGE_CHECK_TIMEOUT" <command>` as the Compose service's
  command. ⛔ **`exec`'d, with nothing left to rewrite the status.** ⭐ **Overridable via
  `STUDYFORGE_CHECK_TIMEOUT` (default `1800`, `0` disables), read on the host and NOT crossing
  into the container.** ⚠️ **A no-argument invocation now names the image's `CMD` explicitly,
  and a test keeps the two identical.**
- ⭐ **`tests/docker/test_dev_check_timeout.py`** — a new module, 275 lines, 10 checks. ⛔ **Six
  static**: the bound exists; it is inside the container and not on the host; it is overridable
  with a default; the default is loose and says so; the no-argument command equals the
  Dockerfile's `CMD`; and nothing can rewrite the status. ⛔ **Four that WEDGE A REAL RUN** —
  an overrun, a SIGTERM-ignoring overrun, a real failure passing its own status through, and a
  healthy run staying clean.
- ⭐ **`OVERRUN = (124, 137)`** — the set, encoded rather than left in prose (`W123/4`).

## Decisions

1. ⛔ **THE BOUND GOES INSIDE THE CONTAINER.** ⭐ **Neither the row nor Ruling 235(d) said which
   side of the boundary; three measurements put it inside** (§3) — the host's `timeout` is a
   different program, `check`'s own header claims it needs only `docker` and `id`, and inside it
   bounds the COMMAND rather than the image BUILD.
2. ⛔ **`--kill-after=30s`, accepting `137` as a second overrun code.** ⭐ **A bare `timeout` is
   advisory against a SIGTERM-ignoring command** (§2.2). ⛔ **The two codes are NOT collapsed:
   both are outside pytest's range, and `137` is the one that tells you a process is ignoring
   signals.**
3. ⭐ **`1800` s, about **31×** a measured healthy run, and the file SAYS it is loose** (§5,
   Ruling 236's second half). ⚠️ **Sized for the `STUDYFORGE_DOCKER_TESTS=1` path, where the
   command itself builds images.**
4. ⛔ **The no-argument fallback is a CHECKED copy of the Dockerfile's `CMD`** (§6) rather than
   an uncheckable second copy.
5. ⛔ **The harness was NOT touched** — the deadlined read stays with `QA-03`'s successor
   (Ruling 235(a)), and §4 states precisely which half of Ruling 235(c) this retires.

## Surprises

- ⛔ **The row's framing — *"an outer `timeout` around the suite"* — is under-specified in the
  one way that matters.** ⭐ **A host-side bound would have been an UNPINNED bound and would
  have falsified `check`'s own header claim; neither hazard is named in the row or the ruling.**
- ⛔ **A SIGTERM-ignoring command yields `137`, not `124`.** ⚠️ **Round 56's measurement that
  `124` survives is true and incomplete — a wrapper asserting `== 124` would have called a
  correctly-killed wedge a failure of the bound.**
- ⚠️ **One of my own plants red-lined the CORRECT implementation** (`W123/1`): the host-side
  guard matched the backslash continuation of the Compose command. ⭐ **The third instance of
  one root cause on this branch.**
- ⭐ **`STUDYFORGE_DOCKER_TESTS=1` runs cannot be bounded end-to-end by this** (`W123/3`), and
  that is structural rather than fixable here.
