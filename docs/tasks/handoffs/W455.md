## Decisions

1. ⭐ **The bases are `Visual Studio Light` and `Visual Studio Dark`, and this was measured.** I tried
   the `2026` pair first, because it is the image's default. In a real session, Java's `int` and `void`
   stayed teal (`rgb(78, 201, 176)`) next to the page's keyword violet. The reason: those themes include
   `Dark+`, which has a rule for `storage.type.primitive.java`. That scope is more specific than a
   customization's `storage.type`, so the theme's rule wins. The Visual Studio pair is the theme the other
   defaults include, and it has the fewest token rules of the four default pairs. It keeps three Java rules
   (an import's path, a package's path, and `*`), and the language server's `namespace` tokens repaint
   them. Its workbench greys are older, but a practice frame shows only the editor, and every surface
   that frame shows is overridden. ⛔ Solarized, Quiet Light and Kimbie are warm, and Tomorrow Night Blue
   and Abyss are saturated navy.
2. ⭐ **Every rule states its weight and slant, even when the page declares none.** This was also
   measured. A type reference (`ISOMsg`, which Java's grammar scopes as `storage.type`) came out bold,
   because it inherited the keyword rule's `bold` under a semantic colour that set no style.
3. ⭐ **Light and dark are handled by `window.autoDetectColorScheme`, and nothing on the page tells the
   editor anything.** Measured with the host's Chrome 149: inside an iframe, `prefers-color-scheme`
   follows the iframe element's `color-scheme`, and the page's `:root` sets that from the reader's choice.
   So all three states work: no choice (follows the system), light, and dark. A change made while the
   editor is open repaints it within seconds. The old code, by contrast, ignored the frame's scheme.
4. ⭐ **The readings are split from the mapping** (`page_colours` and `editor_theme`). One module would
   have been over the line ceiling, and the two halves change for different reasons: a stylesheet's shape
   versus the editor's vocabulary.
5. ⚠️ **A colour that cannot be read refuses the editor.** It is never silently left stock, because a stock
   editor is exactly the defect this row fixes. The refusal names the file and the selector.
6. ⚠️ **Bracket-pair colouring is off.** The page paints every bracket with the punctuation ink, and
   per-depth hues were the loudest clash in the old frame.
7. ⚠️ **Only palette hex values reach the editor, and the `#` is the one read from the stylesheet.** The
   full suite caught two things at my first commit. `tests/test_emission.py` found that a refusal repeated
   the value it refused (R7). `test_fragment` read a composed `f"#{…}"` as a page anchor built outside
   `render/markup`. The fix: `colour()` now keeps the `#` it read, and it refuses an `rgba` value. The
   current-line tint is therefore the accent with an alpha stated in `SURFACES`, and that alpha is `.12`
   in both themes, where the page's light theme uses `.14` (`W455/6`).

## Surprises

- ⚠️ **A workbench customization loses to a theme rule with a more specific scope.** This is why the base
  is a design choice and not a detail (Decision 1). For the same reason, the plainest base matters more
  than the newest one.
- ⭐ **Chrome derives an iframe's `prefers-color-scheme` from the embedding element's `color-scheme`.** The
  reader's explicit choice therefore reaches a cross-origin frame without any message. ⚠️ **CDP's
  `Emulation.setEmulatedMedia` overrides that for every frame on the page**, so a browser test of the
  reader's choice must not emulate the scheme. My first probe did, and it read the wrong thing.

### ⭐ What the register must do to put this live on `:8770`

1. **Merge this branch.**
2. **Restart the `:8770` serve on the merged framework.** The colours are written by the serve process
   when a page asks for a practice's editor, and Python reads the modules once, at start. ⭐ **Nothing
   else is needed.** There is no corpus regeneration (no page asset changed), no image rebuild, and the
   editor container does not need to be recreated.
3. **The reader reloads the unit page.** Loading the page asks for the practice editor, which rewrites
   that practice's `.vscode/settings.json` (it is the framework's own file, recognised by `MARKER`). The
   workbench reads that file. ⚠️ An editor tab that stays open across the restart and is not reloaded
   keeps its old settings until the page asks again.

⭐ **For whoever changes the palette next:** nothing to do. The editor follows `palette.css` and
`code-highlight.css`. ⛔ A new Prism class in `code-highlight.css` is not in the editor until a row of
`TOKENS` says where it goes. A new workbench surface that clashes is one row of `SURFACES`.
