## What landed

- `cli/serve.py`'s `--site` branch builds one `serve.routes.runs.Runs` over the corpus at the
  root it is given. It uses a `ServedCorpus` with relative path `.` and a one-corpus
  `Discovered`, and passes the same `CorpusContent` that the content namespace reads. It
  registers `run.route` over that `Runs`, and `writers` is the set of namespaces that
  `_execution` returned, which is just `run`.
- The run's command comes from the corpus's unit documents, and its outcome is recorded in the
  corpus's own progress store. The site is never written to.
- The skill needed no logic change: `exercise_states` already reads `server.namespaces`, so
  the state follows what the served process actually offers.

## Decisions

- ⭐ **`--site` registers `run`; the skill still serves `--site`.** `SF-22/2` offered both
  options. The root form serves the corpus root as its static mount, but the skill builds
  into `--out`, a separate directory, so switching the skill to the root form would stop it
  serving the site it just built.
- ⛔ **No discovery cache is judged or written.** `serve.discovery.discover` would write
  `site.json` into the corpus root. The skill serves the repository's own fixtures as corpus
  roots, and `--site` may serve a corpus it must not touch. So `_execution` calls
  `corpus.discovery.assemble(root, depths)` with no `cache`, which scans and writes nothing.
  The scan only fills `ServedCorpus.startup`, which `Runs` never reads.
- ⭐ **The wiring lives in `cli/serve.py`, not in `serve/instance.py`,** because the row's
  surface is the verb or the site path. That leaves two places that construct `Runs` (see
  `W371/1`).
- `writers=tuple(execution)` rather than a second spelling of `run.NAMESPACE`. The planted
  "no execution" state in the skill test (below) relies on this, because a writer that is not
  registered is refused by `app`.

## Surprises

- The first version of the skill's negative test returned an empty `_execution` while still
  passing `writers=(run.NAMESPACE,)`, and `app` refused to bind (*"only a registered namespace
  may answer POST"*). That refusal is correct. It is why the writers are now derived from the
  namespaces.
- With no runner container present, a run from the served site executes in host mode. The
  tests rely on this (as `SF-22`'s do). See `W371/3`.

## For dependents

- ⭐ **`W370` (how a page loads the run client):** on a `--site` origin, `/api/v1/run/client.js`
  and `/api/v1/run/` now answer 200, the same as on a root origin. The start path is the same

  planting an empty `_execution`.
