# SF-40 — handoff

**Kind:** task handoff — SF-40

**Status:** ⭐ **Done. `studyforge` is an installed command and it builds a site

`--out` is REQUIRED with no default, a rebuild's behaviour is whatever

## What landed

⭐ **`[project.scripts]` registers `studyforge = "studyforge.cli:main"`** — one
script name, not one per verb, so the subcommand structure lives in one place.

⭐ **`studyforge.cli.dispatch`** holds `VERBS`: `validate`, `plan`, `build`.
It reads the first argument as a verb and forwards every remaining argument to
that stage's own `cli.main` unparsed, so the dispatcher cannot come to disagree
with a stage about a flag. `serve` and `reconcile` are named in the package
contract and deliberately NOT registered — `SF-39` and `OPS-07` build them, and
a verb registered against a callable that does not exist fails on first use.

⭐ **`studyforge.cli.site` is the `build` verb**, the CLI stage over
`generate.write_site`: parser, report, exit code, `__main__`. ⛔ **The package
is `site`, not `build`, because `.gitignore`'s bare `build/` matches at every
depth** — `git check-ignore -v src/studyforge/cli/build/x.py` returns
`.gitignore:10:build/` at this ref, so that package would have been untracked
from the moment it was written. `tests/studyforge/cli/site/test_init.py` pins
the reason.

⭐ **R3 is SURFACED, not swallowed.** A second build over the same output root
prints one `refuse <path>  a file is already there; nothing was overwritten`
line per path, writes nothing, and exits `1`. Exit codes are `plan`'s and
`validate`'s: `0` wrote it all, `1` something was refused, `2` could not run —
`UNUSABLE` imported from `validate.cli`, never respelled.

⭐ **Ruling 157's check was CONVERTED, not deleted.**
`test_no_fence_anywhere_offers_a_console_script_that_does_not_exist` keeps its
name (Ruling 106) and its population (`commanded_pages()`), and its blanket
refusal became a derivation: `[project.scripts]` → the target module → its
`VERBS`. Three checks were added beside it — the population is non-empty, a
planted fence naming `frobnicate` raises, and the derivation reads the table
rather than a list.

⛔ **The pass condition is the MOVED exit code (Rulings 124, 348), run rather
than asserted, in BOTH directions.** A fence reading `studyforge frobnicate .`
planted into `docs/authoring/validate.md` took the converted check RED naming
the verb; deleting `[project.scripts]` from `pyproject.toml` took it RED again
on *"the derivation has no ground"* rather than passing over an empty
population. Both plants reverted; the tree is clean at the tip below.

⭐ **The eleven-file caveat sweep is done.** Both skills' fences now read
`studyforge validate …`; `tests/studyforge/skills/adapter/test_init.py` derives
that spelling from `cli.PROGRAM` and `cli.VERBS` instead of from the module
name.

## Decisions

⛔ **`--out` is required and has no default, and that is the row refusing an
open decision rather than answering it.** `W202` Q1 is the user's. Requiring
the flag defers where a build writes to the person running the command, which
is the only shape "unanswered" can take in a command that has to write
somewhere. The help text says why.

⛔ **`build` was registered as a verb even though no row names its CLI stage.**
`SF-28`'s split table gives SF-40 `[project.scripts]` and says SF-40 "is where
the verbs that make it observable are registered"; `W195`'s pass condition is a
command a user can invoke. Registering `validate` and `plan` alone would have
left `write_site` reachable only from a test. If the register wants the stage
homed on its own row, the module moves without the table changing.

⭐ **The refusal message for a bad `--out` is printed bare, with no path
prefix**, because prefixing it with the corpus root misattributes a refusal
about the output directory to the corpus.

## Surprises

⛔ **The row's first acceptance grep CANNOT print nothing, by construction** —
see `SF-40/1`. Its pattern includes the literal `\[project\.scripts\]`, and
that string is the TOML section header this row was minted to add.

⭐ **Hazard 1 did not fire, measured two ways.** After a full suite run in the
pinned container at the tip below, `git status --porcelain` printed nothing.
And `census("studyforge.cli")`, run from an empty scratch directory, left that
directory empty and reported no echo.

⚠️ **One callable of mine carries the trap SHAPE without the trap.**
`site.report.lines(written, root, into)` has the two-string signature the
coordinator names, but `root` and `into` are report LABELS printed back to the
caller — the module opens no file and imports no filesystem name. ⛔ **The
writer is `generate.write_site`, and the CLI gates it twice**: the corpus root
must be an existing directory before it is called, and `write_site` itself
refuses an output root that does not already exist. Any future stage should
keep `main(argv=None, out=None)` and gate the same way.

## For dependents

- ⭐ **`SF-39` (`serve`) and `OPS-07` (`reconcile`) each add one `Verb(...)`
  entry to `studyforge.cli.dispatch.VERBS` and one line to

  The dispatcher calls `run(rest, out=out)`, and the signature is also what
  keeps the stage out of `tests/emission`'s write hazard.

  verb**, and gets a named failure for any other.
  `tests/authoring/support.py`'s `registered_verbs()` is the derivation; do not
  copy the verb list anywhere.
- ⚠️ **`docs/authoring/` deliberately keeps the `python3 -m …` spelling**, so
  every command there works from a checkout nobody installed; the skills use
