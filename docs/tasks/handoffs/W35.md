## What landed

⭐ **`_check` asks whether git ignores the target BEFORE it asks whether the target
exists**, and the new branch returns a `pointer` finding whose message names the cause:

```text
points at '../graphify-out/GRAPH_REPORT.md', which git IGNORES. It is present on the
machine that generated it and absent from a fresh clone, so resolving it by existence
makes this verdict depend on untracked state (Ruling 80). …
```

⛔ **The ORDER is the row, not a detail.** ⚠️ Asking existence first would give a stable
verdict and two different MESSAGES — *"no such file"* on a fresh clone and *"git ignores
it"* on the machine that built it — which is the same defect one layer down.

⭐ **ONE `git check-ignore` call per scan and never one per pointer.** `scan` now reads the
whole population, resolves every target into one frame, asks once, and only then judges —
which is why the findings are gathered after the read rather than during it.

## Decisions

### ⛔ A finding, and not a silent exclusion

⭐ Two shapes would have made the floor quiet: dropping an ignored target from the walk, or
resolving it anyway. ⛔ **Both leave a reader following a link that a fresh clone does not
have.** ⚠️ The verdict has to be the same in both checkouts, and the only value that is
the same in both is *"this does not resolve"*.

### ⛔ The IGNORE declaration, and NOT the index

⭐ **`W148`, on the same branch, narrows the document POPULATION to `git ls-files`.**
⛔ **`W35` deliberately does not use that question for RESOLUTION.** ⚠️ A file written and
not yet added is not ignored, has not been declared out of the repository, and a link to
it must still resolve — otherwise every author would red the floor on their own
in-progress work, which is the shape that gets a check switched off.
⭐ `test_an_untracked_but_not_ignored_target_still_resolves` pins it.
