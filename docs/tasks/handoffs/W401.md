## Decisions

1. ⭐ **The block is in the root `consuming.json`, not under `docker/minimal/`,
   and the reason is measured.** `plan.INPUT_ROOTS` hashes everything under
   `docker/minimal/` into the runner's tag (`plan.inputs_digest`), so a
   declaration there would move every consumer's tag whenever its prose was
   corrected. ⚠️ The row's surface line reads *"the sibling's `docker/minimal/`
   declaration"*; the declaration OF `docker/minimal` is what landed, at the
   component root, which is also what `TC-05`'s handoff told a second block to
   do.
2. ⭐ **The split is at the BLOCK, not at the ruling**, as `TC-05` asked. Three
   of the editor's five finding groups — the published port, the named volumes,
   the health check — do not apply to an image that listens on nothing, mounts
   one bind and answers no request, so threading "unless it is the runner"
   through each of them would have made every editor check read as a pair of
   exceptions.
3. ⭐ **This branch MERGES the sibling's `task/TC-05-compose-and-mount`**, which
   is not on the sibling's `main`. There was otherwise no `consuming.json` to
   add a sibling block to, and `task/TC-06-versioning-and-pinning` — the other
   office on these files this wave — did exactly the same thing for the same
   reason. The merge's one conflict was two README test lines that both belong,
   and both were kept.
4. ⭐ **The README keeps its `docker run` line.** What `TC-05/3` named as the
   defect is not the sentence, it is the sentence being the ONLY copy. The line
   now says it is a rendering, names the block as the authority, and a test
   asserts it is what `--run-line` prints — the same arrangement `TC-05` used
   for `docs/compose.reference.yaml`.
5. ⛔ **The framework renders the run itself and imports nothing from the
   component** (R18). `run_argv` is a short function of the framework's own,
   reading the same JSON; `consuming/runner.py` exists to demonstrate the block
   is sufficient, not to be a library the framework links.
6. ⛔ **`run_argv` fills a real uid:gid and never passes `runs_as.run_value`
   through.** That value is `$(id -u):$(id -g)` — what a PERSON types into a
   shell. A `subprocess.run` list has no shell, so shipping it would have run
   the container as a user literally named `$(id -u)`, or as root.
7. ⭐ **`PROMISE = 2` and a lesser sibling is refused, not migrated** (R9),
   recorded the way `skills.buildserve.narration.PROMISE` records
   `narrate-service`'s. A sibling that promises MORE is accepted: `provides`
   versions the promise, and a promise kept is still kept.

## Surprises

⛔ **THE RUNNER IMAGE DECLARES NO `USER`, WHICH MAKES ITS `--user` FLAG A
DIFFERENT KIND OF THING FROM THE EDITOR'S.** The editor image has `USER 1000`
and `fixuid`, so its `runs_as.uid` is a real default and the compose `user:`
adapts it. The runner has neither: measured against the Dockerfile, there is no
`USER` line at all, so a run without `--user` is **root**, and every file a
graded run writes into the reader's own sources is root-owned. So the block
declares `uid: null`, `required: true`, and `runs_as.how` says why no `fixuid`
is needed here — nothing under `HOME` is seeded and the only directory the run
writes is the bind. `runner._user_findings` refuses a block that makes the flag
optional, and a test asserts the Dockerfile still has no `USER` line, so the
day one is added this reads red rather than going quietly stale.

⚠️ **A smaller one.** The README's line quotes the uid substitution in **double**
quotes, and it has to: single quotes would hand `$(id -u)` to docker literally.
`runs_as.quote_in_shell` now carries that as data and two tests assert it — one
that the rendered prose keeps the double quotes, one that the framework's argv
carries no `$` at all.
