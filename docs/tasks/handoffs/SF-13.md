## Decisions

### ⛔ The stable half is built from what a corpus DECLARES, never from a scan

⚠️ **`W32`'s defect, arriving in this task's own vocabulary.** A contents
document sourced from `corpus.discovery` would list the pages that exist; a unit
declared in a container map and not yet generated would simply not appear, the
document would be internally consistent, and **nothing would raise**. ⭐ So
`build` reads container maps and opens no file at all, `status` says which of the
declared units this machine has, and `missing` names the rest (R6).

⭐ **This is also why the task's two dependencies are both used**: `SF-05`'s
container maps are the stable half, `SF-04`'s scan is the local half, and
`found(site, corpus)` is the one line that maps a scan's artifacts onto the keys
the local document is written in — by **identity**, never by path (R4).

### ⛔ Sibling order is a function of the ADDRESS, and it is alphabetical

⚠️ **Three orders were available and two of them are wrong.** The order a caller
enumerated the maps in is not a committed input; the order the maps sit in on
disk is not one either (R4). ⭐ What is committed is the address, so siblings are
ordered by their segment, compared as **text by code point** — plain `sorted`,
never a locale collation, so the build does not depend on `LANG`.

⛔ **The consequence is stated rather than hidden: a corpus gets alphabetical
order unless it puts the order into its segments.** Real material does —
`01-getting-started` before `02-going-further` — and the `depth2` fixture's
*first* level does not, so it reads `advanced` before `basics`. ⚠️ That is
`SF-13/6`, and inferring an order from anything else would be the framework
knowing something about a source (R1).

⭐ **Units are not a second orderer.** The container reader has already refused
any map whose ordinals are not contiguous from 1, so the declared order *is* the
ordinal order and `tree._entries` uses it as given.

### ⛔ The reading order is DERIVED and never stored beside the tree

⚠️ This task is the first thing in the project that computes one, so it is also
the first chance to store one twice. ⭐ The tree already states the order; a flat
list written into the document next to it would be a second copy the day's first
edit puts out of step, with nothing comparing them. `test_order` asserts by `ast`
that `order.py` and `entries.py` contain **no `sorted` at all** and `tree.py`
contains exactly **one**.

### ⛔ No href is stored, because there is no single correct one

`relative_href` answers *"how does the page at A address B"*. Under `sibling`
placement two units of one container share a directory and two units of different
containers do not, so the same target has a different href from each asking page.
⭐ Storing one would be correct under `tree`, wrong under `sibling`, and wrong
**silently** — `UnitLocations.href`'s *ask, never compose* rule, one layer up.

### ⛔ `links` returns plain strings, so `contents` never imports `render`

⭐ R13 and the E03 layering in one decision. The mapping onto
`navigation.Links(previous=Link(**slot), …)` is one line and it lives with the
caller; `test_order` asserts that no module of this package contains the text
`studyforge.render`. ⚠️ **Which caller does that mapping is `SF-12`/`SF-14`'s
row, not mine** — see *For dependents*.

### ⛔ One `toc_api` versions BOTH documents

⚠️ The spec's register calls it *"the TOC schema version"* for `toc.json` and
`status.json` alike. They are two halves of one schema, and a build that spoke
one half and not the other could join a pair it does not understand. ⭐ The local
document carries `toc_sha256` — the digest of the stable document's **bytes**,
which is the thing a consumer actually holds — and `join` refuses a mismatched
pair naming both digests, rather than joining on ids that have been re-minted.

⛔ **An unknown `toc_api` RAISES, unlike `site_api`.** Ruling 95 lets the
discovery cache be discarded and rebuilt because a scan can simply be re-run.
This document is not that: a consumer holding a `toc.json` it cannot read has no
scan to fall back on. So `version.check`, not `version.is_supported`.

### ⛔ The R7 gate runs on the WRITE path too, before the `mkdir`

⭐ **Found by a check, not by taste.** `tests/test_emission.py` probes every
public callable with a poisoned value; `writing.write(path, text)` took a poisoned
`text` and **wrote it into the checkout**, leaving `alpha` at the repository root
and poisoning three later assertions. ⚠️ The conventions' own rule for a defence
whose legal set cannot be enumerated is *every layer asserted, because no layer is
sufficient* — and the read gate is not sufficient here, because a `Contents` can
be built in memory and written out without ever having been decoded.

### ⭐ The mixed-form fixture is material, not a description of material

⛔ **`W32`'s clause says the fixture is built by this task, and it is.** 38
entries, 36 list items, 2 headings, and the 38 files it points at. ⚠️ **It is not
markdown in a fenced block**: the repository-wide pointer walk reads markdown
under `tests/fixtures/`, so an index whose links resolved to nothing would have
been 38 new unresolved pointers.

## Surprises

### ⛔ `W32` was re-routed to a task that has no parser, and the clause still lands

⚠️ **The re-route's premise is that `SF-13` is *"the task that first needs"* a
parser.** It is not: `build` reads container maps and `toc.json`, and neither is a
markdown index. ⭐ **The parser the clause guards already exists and is already
form-agnostic** — `skills.reconnaissance.record.read` reads by **link target**
and reports the shape spread through `forms()`.

⭐ **So the clause is met the only way it honestly can be:** the fixture is built
here, `record.read` is asserted to see all **38**, and the negative control — a
list-only reader built out of `record.LIST_MARKER` itself — is asserted to see
**36**, which is the short parse the donation records. ⚠️ The fixture's exposure
therefore sits in `skills.reconnaissance`, not in `contents`, and `SF-13/5` says
so.

### ⚠️ `tuple(to_document(x)) == TOC_KEYS` is not R10, and a mutant proved it

⛔ **The object's key order is not the document's key order.** `sort_keys=True`
in `json.dumps` re-sorts every key on the way out and leaves that assertion
passing — it survived as `M5` in the first sweep. ⭐ The bytes are what a consumer
reads, so the bytes are what is pinned now, in both documents.

### ⚠️ A mutant that WRITES dirties the tree for the next row of the sweep

⛔ **My first sweep's closing baseline failed**, and it failed because the `M9`
row (the R7 write gate removed) left `alpha` in the checkout and every later run
inherited it. ⭐ Fixed in the harness with a `git clean` between rows; recorded as
`SF-13/4` because the protocol's sweep recipe does not mention it.

### ⭐ The census asked for one `Reader` and needed two

`tests/test_document_emission.py`'s derived guard reported `contents/document.py`
and said nothing about `contents/status.py`, because it looks for `from_document`
by name and the local half's reader is `from_status_document`. ⚠️ **A derived
guard that names a convention is a guard with a blind spot exactly the width of
that convention** — `SF-13/3`.

## Findings

### SF-13/1 `[structural]` — ⛔ the between-units bar loses its *next* link under `sibling` placement, silently

⛔ **`render/page/text.py`'s `SAFE_SCHEMES` is a closed set of prefixes —
`http://`, `https://`, `mailto:`, `#`, `/`, `./`, `../` — with no entry for a
relative href that names a file in the SAME directory.** `navigation._link` drops
a link whose scheme is refused rather than rendering dead text, so the slot
vanishes from the page with nothing raised.

⚠️ **Under `sibling` placement two units of one container share a directory**, so
`relative_href` answers `unit-02-fields-and-constructors.unit.html` and that is
precisely the shape refused. ⭐ **Under `tree` every unit has its own directory,
the href begins `../`, and all three slots render** — which is why the acceptance
clause is met and the hole is next to it rather than in it (Ruling 56: *a
guarantee does not extend to what sits beside it*).

- **Measured**, `docker/dev/check`, `4c868f4`, 2026-09-10:
  `links(depth2, "basics/01-getting-started/unit-01")["next"]["href"]` is
  `unit-02-fields-and-constructors.unit.html`, and `safe_href` of it is `None`.
  The composed page carries `rel="prev"` and `rel="up"` and no `rel="next"`.
- **Measured:** the `depth1` (`tree`) page carries all three.
- **Received** from `E03-rendering.md`: the bar's *rules* are `SF-34`'s and its
  *content* is this task's.
- ⛔ **Not fixed here: `render/page/text.py` is outside this task's `Owns`.** The
  behaviour is pinned by a test in my own tree that names this finding, so the
  day somebody widens the set the test says so.
- ⭐ **Why it is structural rather than local:** every corpus using `sibling`
  placement loses every same-container *next* and *previous* link, and the
  measured designed shapes include two that would. The fix is a decision about
  what a permitted href is, which is the owner's to make.

### SF-13/2 `[structural]` — ⚠️ `SF-31/3` recurs, now with its third and fourth consumer

⛔ **Reading a corpus's container maps is `sorted((root / ARCHIVE_DIR).rglob(CONTAINER_FILENAME))`
in `validate/corpus.py` and again in `cli/plan/derive.py`, and `ARCHIVE_DIR` is on

- **Measured**, 2026-09-10: `grep -rn 'CONTAINER_FILENAME' src/` finds the walk
  in those two modules; `ARCHIVE_DIR` appears in `validate/corpus.py` and is not
  in `studyforge.validate.__all__`.
- **Measured:** `contents` needs it and cannot have it, so `build` takes the maps
  as a parameter and `tests/studyforge/contents/corpora.py` carries a **third**
  copy of the walk, declared as a finding in its own docstring rather than
  smuggled in.
- **Received** from `E03-rendering.md`: `SF-14` reads *only* the two contents
  documents, so it needs the walk to produce them — a **fourth** consumer.
- ⭐ **The shape of the fix is Ruling 101's producer half**, and the larger
  question — §6 permits a corpus to put its archive elsewhere, so the root is a
  parameter and not a constant — is still the one `SF-31/3` named.

### SF-13/3 `[local]` — ⚠️ the document-emission guard is blind to a reader not called `from_document`

⛔ **`tests/test_document_emission.py`'s `modules_with_a_reader` reported

### SF-13/4 `[local]` — ⚠️ a mutant that writes to the checkout poisons the rest of the sweep

### SF-13/5 `[local]` — ⚠️ `W32`'s exposure is `skills.reconnaissance`'s, not `contents`'

⛔ **The round-25 re-route reasoned from `contents/` being a 20-line stub with no

- ⭐ **The clause is discharged**, and the fixture is where a future reader would

### SF-13/6 `[structural]` — ⛔ a corpus whose top-level segments are unnumbered reads in the wrong order, and nothing can say so

⛔ **Sibling order is alphabetical by address segment, because that is the only
committed input available. Nothing in `corpus.container` or `corpus.manifest`
declares a reading order.**

- **Measured**, 2026-09-10: the `depth2` fixture reads
  `advanced/02-going-further` before `basics/01-getting-started`, which is
  alphabetically right and pedagogically backwards. Its **second** level is
  numbered and orders correctly; its first is not.
- **Measured — a NEGATIVE result, recorded so it is not re-raised:** I looked for
  an existing declared order and there is none. `Container` carries `address`,
  `titles`, `variant`, `ingested`, `units`, `origin`, `note`; `Unit` carries
  `label` and `url_slug`, and `label`'s own docstring forbids reading it back as
  an ordinal.
- ⛔ **Not fixed here.** An ordering field is a `container_api` bump, every map
  written under the old version is refused rather than migrated (R9), and
  `corpus/container/` is outside this task's `Owns`.
- ⭐ **Why structural:** it is a property of every corpus whose top level is a
  word rather than a number, and the remedy the framework can offer today —
  *number your segments* — is advice a corpus's own layout may refuse (R3).
  Whoever integrates the first such corpus pays for it, and `contents` is where
  the decision would land.

## For dependents

### ⭐ `SF-14` — root index renderer

- ⛔ **Your only inputs are the two documents, and both have readers**:
  `toc.load(path)` and `toc.load_status(path)`. `toc.join(built, local)` gives
  you `{unit key: UnitStatus}` and **raises** if the pair does not belong
  together — call it rather than zipping the two yourself.
- ⭐ **The hierarchy is already arbitrary-depth**: `Contents.groups` nests
  `len(levels)` deep, every `Group` carries `level` (the corpus's own word for
  that depth), `segment`, `key` and `title`, and holds `groups` **or** `entries`,
  never both. Your subtask (a)'s disclosure elements map onto that directly.
- ⚠️ **You will need the container-map walk to produce a `toc.json` at all**, and
  it is `SF-13/2`. Take the archive root as a parameter.
- ⛔ **`status.json`'s producer.** The spec's register says `SF-14` writes it;
  everything you need is `toc.status(built, present, read=…)` and
  `toc.write_status(path, local)`. `toc.found(site, corpus)` turns `SF-04`'s scan
  into the `present` set.

### ⭐ `SF-12` / `SF-34` — the unit page and the between-units bar

- ⛔ **The bar's content is one line**, and this is it:

  ```text
  navigation.Links(**{
      field: navigation.Link(**slot)
      for field, slot in contents.links(built, key).items()
  })
  ```

  `contents.links` returns at most three slots keyed `previous`, `next`, `index`
  — the same three words `navigation.Links` uses — each `{"href", "label"}`, and
  an absent slot is **missing** rather than present and empty.
- ⛔ **Read `SF-13/1` before you judge a rendered bar.** Under `sibling`
  placement the *next* slot is present in the data and dropped by
  `safe_href`. A page that looks short is not necessarily short.
- ⭐ **`neighbours(built, key)` also gives `position` and `total`**, both counted
  over what the corpus declares, so *"3 of 38"* needs no second walk.
- ⚠️ **`positions(built)` exists for the whole-site render.** `neighbours` is a
  linear scan; asking it once per page over 1,290 pages is quadratic.

`toc_api` is `CONTRACT_FIELDS`' ninth entry, and the tuple's comment predicting a

meaning anything.
