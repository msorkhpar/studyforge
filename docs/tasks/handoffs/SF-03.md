## ⭐ The derivation SF-31's golden was deferred for — answered

**A page's name is derived from identity, never from the source filename.**

`unit_page_name(ordinal, title, label=None)` → `<label>-<title-slug>.unit.html`,
and the default label is the unit's own ordinal: `unit-07-…`.

⚠️ §5's worked example shows `4.4.1-introduction-to-the-streams-api.unit.html`
beside `README_4.4.1.md`, and reading `4.4.1` out of that filename is the
tempting answer. It is the wrong one, for three reasons and one measurement:

- **R1.** `README_<numbering>.md` is *one corpus's* convention. See finding 1:
  the four designed shapes use four different ones, and two of them differ only
  in zero-padding — so a filename parser would have to know which corpus it was
  reading to know whether `1.md` and `01.md` mean the same unit.
- **R4.** Inferring what an artifact should be *called* from what a source file
  is *named* is inferring meaning from a path, pointed the other way.
- **R10.** `origin` is optional, so a name derived from it needs a fallback, and
  a corpus would then use two naming schemes at once.

⭐ **`label=` is the seam, and it costs nothing to leave open.** A corpus's own
display numbering is *data*. The day an adapter records it, it is passed here
and §5's example is reproduced **character for character, with no change to
this package** — asserted now by
`test_the_worked_example_from_the_spec_is_reproduced_exactly`:

```text
label="4.4.1"  →  16-streams-api/4.4.1-introduction-to-the-streams-api.unit.html
                  16-streams-api/4.4.1-introduction-to-the-streams-api.audio
                  16-streams-api/4.4.1-introduction-to-the-streams-api.practice
```

⛔ **So SF-31's golden can be written today**, against the ordinal form, and it
does not have to move when the numbering field lands. The field is routed in
finding 2.

## Decisions

1. ⭐ **The name comes from identity, and `label=` is the seam.** Above.
2. ⭐ **`SURFACE`-style contract for media: ask, never compose.**
   `where.href(kind, filename)` — because `audio/<clip>.mp3` is the **`tree`**
   shape. Under `sibling` twenty units share one directory, so the same clip is
   `<stem>.audio/<clip>.mp3`. ⛔ The invariant that survives every profile is
   *"relative to the page"*, not the literal string, and a renderer that
   hardcoded the string would be correct under one profile and silently wrong
   under the other. §5's *"every page still addressed a clip as plain
   `audio/<clip>.mp3`"* is a statement about `tree`, and reading it as
   universal is the mistake this API prevents.
3. ⭐ **The two profiles differ only in where *pages* land.** Assets, archive
   and the discovery cache are identical under both, in `.studyforge/`.
   `sibling` exists so the reader's own directories gain a page beside the file
   they know — not so a corpus's archive is scattered through them. Dot-prefixed
   so it sorts out of the way in a repository whose directories *are* the
   material.
4. ⛔ **`origin` is required by `sibling` and refused when absent** (R6).
   "Beside the source file" has no answer for a unit with no source file, and
   inventing a directory writes generated output somewhere the corpus owner
   never agreed to (R3). ⚠️ `tree` needs none, which is what makes it the
   profile for material with no layout worth preserving.
5. ⭐ **Sibling media directories are dot-suffixed**, `<stem>.audio/` rather
   than `audio/`. Many units share a directory here; a shared `audio/` would
   collide twenty ways and no clip could be told from another. The dot-suffix
   also makes every artifact of one unit sort contiguously beside its page and
   its source, so deleting a unit is deleting one run of names.
6. ⭐ **The identity block is defined here, with both halves and the round-trip
   tested now** — a milestone before SF-04 reads it, because SF-12 writes it in
   M1. A definition arriving after its first writer is a definition two tasks
   each guess at differently.
7. ⛔ **The identity marker is a contract, not presentation.** The element, its
   `type` and its `id` are fixed in `identity.py`, not chosen by a renderer,
   because a scan must find it in thousands of files without parsing HTML. ⚠️
   This is the one place R13's "markup lives in template files" gives way, and
   it gives way because this markup is **machine-read, never shown** — it is an
   inline wrapper around JSON, and a template file for it would put the scan's
   own contract somewhere the scanner cannot see.
8. ⛔ **`identity_api` is versioned through the shared guard** and was added to
   `version.CONTRACT_FIELDS` **in the same commit**, which is what that
   constant's own docstring asks for. Without the registration the guard cannot
   see the new contract, and the one-line edit to another task's file is the
   convention rather than an intrusion.
9. ⭐ **The registry is the acceptance.** `profile_for(name)` and
   `register(profile)`; nothing downstream names a profile, asserted by an AST
   scan of all of `src/` rather than promised.
10. ⚠️ **`SF-02.PLACEMENT_PROFILES` and this registry are two answers to two
    questions**, as the CTO ruled — a manifest must be able to refuse an
    unknown name without importing a placement engine. ⛔ But they must not
    drift, so `test_the_registry_and_the_manifests_accepted_names_are_the_same_set`
    fails a profile registered here that a manifest may not name. That is the
    seam drawn, and it is the whole of the coupling.

## Surprises

1. ⛔ **`tree` cannot reproduce the extraction source's page filename, and the
   task document says it must.** See finding 3 — the numbers are there.
2. ⚠️ **The Java corpus's directories are flat, and its address is two levels.**
   `16-streams-api/` sits at the repository root; the address is
   `basics/16-streams-api`. So under `sibling` the directory comes from
   `origin` and the address is *only* identity. A profile that used the address
   for both would have created `basics/16-streams-api/` beside the material and
   restructured nothing into it. Pinned by
   `test_the_page_is_beside_the_source_and_not_under_the_address`.
3. ⛔ **My first refusal for a bad `origin` echoed the path, and R7 caught it —
   through my own test.** An origin is corpus data, and the one shape being
   refused there (an absolute path) is exactly the shape that carries a home
   directory. So a refusal that quoted it would copy personal data into a build
   log *from the check that exists to catch it*. It now **describes** the fault
   and names the address, following `version._said`'s precedent.
4. ⚠️ **Two of my own tests tripped the repository's R7 sweep** with fabricated
   absolute-home-path literals — the shape a refusal test necessarily contains.
   Split across a concatenation, which is what `tests/studyforge/test_version.py`
   already does. See finding 5 — I do not think that technique should stay
   unremarked.
5. ⭐ **`test_two_containers_sharing_a_directory_would_collide` is a test that
   asserts a collision.** Two containers whose units land in one directory with
   the same ordinal produce the same page path. The Java corpus does not do it —
   one module directory per container — and nothing in the profile prevents it.
   Rather than pretend otherwise, the shape is pinned so SF-25 knows what to
   look for.

## Findings

### 1. `[structural]` Four corpora, four source-filename conventions — two differing only by padding

**Measured 2026-09-09**, in the workspace:

```text
$ ls ISO-8583-jPOS-tutorial/src/*.md | head -3 ; ls .../src/*.md | wc -l
  src/1.md  src/10.md  src/11.md                       41 files
$ ls Claude-SPARQL-tutorial/src/*.md | head -3
  src/04.md  src/11.md  src/13.md
$ ls Claude-senior-java-engineer/01-java-basics/README_*.md | head -2
  README_1.1.1.md  README_1.1.2.md
$ (fixture) tests/fixtures/depth1 origins
  depth-one/01-what-a-triple-is.md
```

⛔ ISO spells unit one `1.md`; SPARQL spells it `04.md`. **A filename parser
would have to know which corpus it was reading to know whether `1` and `01` are
the same unit** — which is R1 exactly. This is the evidence behind the naming
decision, and it is why the decision is not a preference.

### 2. `[structural]` The archive carries no field for a corpus's own display numbering

⭐ **Proposed:** the container map's unit entry gains an optional
`label` — the numbering the material itself uses (`4.4.1`, `s7`, `2.4`) —
written by the adapter, which is the only party that knows the source's
convention. Placement already accepts it; nothing else changes.

**Measured 2026-09-09:** `tests/fixtures/depth2/archive/basics/01-getting-started/container.json`
unit entries carry `n`, `title`, `practices`, `origin`, `note` — and no
numbering. §5's worked example cannot be reproduced from the archive as it
stands, only from a filename.

⚠️ **Owner:** SF-06 (archive document) and SF-05 (container map) share it; the
adapter side is E07. ⛔ Needs routing before SF-05 freezes the container map,
because adding a field after an adapter has written a thousand of them is not
the same cost as adding it now.

### 3. `[structural]` "`tree` reproduces CodeSignal's paths byte-identically" cannot be true of the page filename

**Measured 2026-09-09**, in the extraction source:

```text
$ find study -name index.html -path "*/units/*" | wc -l
1290
$ find study -name "*.unit.html" | wc -l
0
$ grep -n 'UNIT_PAGE_FILENAME' .pipeline/tools/study/layout.py
91:UNIT_PAGE_FILENAME = "index.html"
```

⛔ §5 rules that every generated page carries a real name, **because a scan
reads names** — and `index.html` is neither unique in a listing nor
distinguishable from the root index. Discovery globs `*.unit.html`; a `tree`
profile emitting `index.html` would be **found by nothing**.

⭐ **Resolved in favour of the spec, and the cost is one file per unit.** The
directory shape below the container is preserved segment for segment —
`units/unit-NN/` with `audio/`, `images/`, `video/` — so every href a page holds
to its own media is unchanged and a migration moves a tree rather than
re-deriving one. Only the page is renamed.

⚠️ **`docs/tasks/E01-core-contracts.md` should be corrected**: "reproduced
byte-identically" is true of the directories and false of that one filename. I
did not edit it — it is the PO's document, and a task quietly rewriting its own
acceptance is worse than a task reporting that it cannot meet it as written.

### 4. `[local]` The `sibling` profile can collide across containers, and only a corpus-wide check can see it

Two containers whose units land in one directory with the same ordinal produce
the same page path. ⭐ **Routing:** SF-25 already gains *"no two containers claim
the same address"* from SF-01; this adds *"no two artifacts claim the same
path"*, which is a different check because addresses can differ while origins
do not.

**Measured 2026-09-09:** the Java corpus does not collide — 45 module
directories carrying `README_*.md`, 166 units, one container per directory,
`test_no_two_units_in_the_java_corpus_produce_the_same_artifact_name` green
against the real tree. The risk is real and unexercised, which is the worst
combination to leave undocumented.

### 5. `[local]` A split string literal defeats the repository's own R7 sweep

An absolute home path written as two adjacent string literals joined by `+`
passes `tools.quality.personal_data` and reaches the file intact.

**Measured 2026-09-09:** `tests/studyforge/corpus/placement/test_errors.py` and
`test_identity.py` each hold one such value, deliberately, and:

```text
$ python3 -m tools.quality
quality floor: clean
```

⛔ Before the split, the same two lines were reported — so the sweep sees the
literal and not the value.

⚠️ It is the established technique — `tests/studyforge/test_version.py:119`
already does it, in an approved file — and both uses are legitimate: a test of a
refusal needs the shape it refuses. ⛔ But the sweep cannot tell a legitimate
split from an evasive one, and the fixture registry
(`SANCTIONED_PERSONAL_DATA_DIRS`) exists precisely so such exceptions are
*bounded by a test rather than by a reviewer's memory*. **Proposed:** either the
registry gains these test modules, or the sweep learns to see a concatenation.
Not fixed here — `tools/quality/` is not SF-03's, and a commit that adds a check
must bring the whole tree into compliance in the same commit.
