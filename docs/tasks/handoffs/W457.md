## The design

- ⭐ **The build's own join, not a second one.** Per declared unit, the check builds the served
  document and asks `generate.narration.heard`, exactly as a build does: the same audio
  directory (`W222`) and the same `playable_of`, with the disk probed. `Playable.stale` is the
  population, so validate and the page cannot disagree about which clip is stale. The
  `generate` import is deferred inside the check, because `generate` imports the renderer and
  `validate`'s package contract keeps `render` out of the other checks.
- ⭐ **One finding per stale speech unit**, filed at the unit's archive directory. It names the
  speech id, which carries the section, block and item, and says to run
  `studyforge narrate <corpus-root> --voice <the record's voice>`. ⛔ No text is quoted. The
  voice is read from the record's top-level conditions (`State.voice`) and gated by
  `archive.scrub` before it is printed. With no usable voice, the finding says `<voice>`.
- ⭐ **No record: quiet** (C5). ⛔ **An unreadable record is a `narration-record` finding**,
  because the build refuses the same record (`generate.narration.recorded`). A corpus that does
  not read the way a build reads it, or a unit that does not build, is an `Unchecked`, never
  clean.
- ⚠️ **Only `WORDS_MOVED` is reported.** `NOT_ON_DISK`, `MISFILED` and `NOT_PLACED` already
  show on the page as the renderer's third state, and are not this row's.

## Decisions

### ⛔ The page keeps playing a stale clip, and `validate` goes RED

1. **The renderer's third state means *a clip was promised and is not on disk*, and its notice
   says so.** A stale clip is on disk. Marking it there would print a false sentence, and
   `Narration.of` refuses a position that is both playable and missing, so marking it means
   taking its audio away. Every edit, a comma included, would silence a paragraph until
   someone re-narrates.
2. **The defect was that nobody was told, not that it played.** `validate` is the definition of
   done that an author and the build-and-serve skill already run. RED there means a stale
   corpus is not built through the skill without re-narrating.
3. **Never silent on both:** the page plays and `validate` reports, and the skill stops on the
   report unless it is about to narrate.

⚠️ What stays open: a bare `studyforge build` does not run `validate`, so it still builds a
stale corpus without a word. See `W457/1`.

### ⭐ `narration_on` lives in `narrate`, and the per-run answer is `--no-narration`

`narrate` is the package every narration stage already imports, and the predicate needs
nothing. `--no-narration` is an explicit off switch: a run that says nothing has not turned
narration off. `validate`'s rule ids stay `narration-*`, beside `ledger-*`.

### W457/1 `[structural]`: a bare `studyforge build` still builds a stale corpus without a word

`build` does not run `validate`, and it prints nothing about `Playable.stale`. The skill path
is covered. The bare verb could print one line counting the stale clips. That is outside this
row's surface.

### W457/2 `[local]`: a stale corpus is a RED `validate`, so an adapter's generated suite goes RED too

The adapter skill's generated suite calls `validate(root)`. A corpus whose text moved after
narration now fails it until it is re-narrated, or until narration is off for it (`W460`).
That is intended. It is written here so it does not read as a regression.

## For dependents

### W460: where narration-off hooks in

⭐ **One predicate: `studyforge.narrate.enabled.narration_on(root, *, asked=None)`.** `asked` is
the run's own answer (`None` when the run was not asked). It wins either way. Otherwise the
predicate returns ON.

1. ⛔ **The corpus's recorded choice is read INSIDE `narration_on`, from `root`**, in the marked
   place in its docstring. Then `validate` honours it with no further edit.
2. ⭐ **`validate` already takes the per-run answer**: `validate(root, narration=False)` and the
   CLI's `--no-narration`. If `build` and `serve` take a flag, spell it the same, or rename it
   here in the same diff.
3. ⭐ **`build` and `serve` should ask the same predicate** before `generate.narration.recorded`
   is read. Narration off is then `SILENT`, the first of the renderer's three states, and no
   clip is judged, linked or served.
4. ⚠️ The build-and-serve skill already passes `narration=False` to `validate` when it is about
   to narrate. When narration is off for the run, it should pass `False` too.

### A corpus

⭐ **Run `studyforge validate`.** Every `narration-stale` line names a paragraph whose clip says
old words. The line's own command re-makes them: `studyforge narrate <corpus-root> --voice
<voice>`. A re-run with nothing moved requests nothing.
