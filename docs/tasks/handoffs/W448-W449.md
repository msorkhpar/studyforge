## Decisions

1. ⭐ **W448: the workbench's DEFAULT, because no setting reaches it.** The primary side bar's
   visibility is workbench layout STATE. It is kept per workspace in the browser's own storage
   (`sideBar.hidden`), so neither the server nor the image can seed it. With nothing stored, the
   workbench falls back to `SIDEBAR_HIDDEN.defaultValue = (workbench is empty) || forceMaximized`.
   That was read in the 4.137.0 bundle, and it is why every fresh practice folder, which W446
   made per practice, started with the Explorer open. ⛔ `workbench.*` settings, the frame URL
   (`payload` carries no layout) and the web construction options (code-server's server does not
   pass `defaultLayout`) were each checked, and none can express it. ⚠️ The payload key
   `isSessionsWindow` would hide it as a side effect, but it turns the window into the agent
   Sessions window, so it was rejected.
2. ⭐ **W449: the page answers the steal, and the frame is not delayed.** Two platform levers
   were measured and found not to work: `inert` on the iframe does not reach the framed document,
   and `allow="focus-without-user-activation 'none'"` is not honoured by Chrome 149. The two
   `focus()` calls are in the workbench bundle (`restoreParts()` → `activeGroup.focus()`, then the
   editor that opens the payload's file). Patching those would put the page's integrity in a
   third party's minified code. ⭐ The order that makes a page-side answer possible was
   measured: the page's `blur` is dispatched INSIDE the frame's `focus()`, at `scrollY` 0, before
   the glide starts. ⛔ **Delaying the frame until the reader scrolls to it or clicks was not
   needed, so it was not done.**
3. ⚠️ **A task, not a microtask, and not inside the `blur`.** Both were measured. Moving focus
   inside the `blur` is ignored, and so is moving it in a microtask: `activeElement` stayed the
   frame and the page glided on.
4. ⚠️ **The glide is cancelled by a 1px nudge and back.** An instant `scrollTo` to where the page
   already is does not cancel a glide that has not started yet (measured: the page crept 3px and
   stayed). The next two frames are checked again, because a compositor step can still land after
   the nudge (measured about once in six).
5. ⭐ **What counts as the reader's hand.** Pointer over that frame plus
   `navigator.userActivation.isActive` covers a click, because a click inside a frame activates
   every ancestor. A Tab keydown on the page less than 500 ms earlier covers the keyboard. When a
   browser lacks `userActivation`, the pointer alone decides. ⚠️ The pointer is read from
   `pointerenter`/`pointerleave` on the iframe element, which the parent does receive (measured:
   the click was accepted).
6. ⭐ **Where focus goes back to:** the page element that last had it, with `preventScroll`,
   or, after a Tests-tab click, that tab. Otherwise the frame is blurred and focus goes to the
   document. If the reader had given focus to one frame, focus goes back to that frame.
7. ⚠️ **The watch never stops once a frame exists.** It is one comparison every 100 ms. Two steals
   raise no `blur` at all: a frame taking focus from another frame, and any steal while the
   browser window is unfocused. Measured on the host: with the watch planted out, an unfocused
   window glided to the editor.

## Surprises

- ⛔ **The session scratchpad was deleted underneath this office at about 11:33 host time** by
  the W450 office's cleanup (`rm -rf` over the whole scratchpad). The scratch clone, the probe
  scripts and one plant's saved copy went with it, and the working file was briefly left with two
  plants applied. It was restored by hand and verified by grep and by the green run below. Every
  reading in *Measured* was re-taken afterwards in a directory of this office's own, with the
  editor recreated (`down -v`, then up). See `W449/3`.
- ⚠️ **The two defects share one cause.** Each `closeSidebar` the lockdown ran moved focus to the
  editor (`setSideBarHidden` → `focusPanelOrEditor`), and each of those focuses was another steal.
  With the side bar starting closed, the frame's own focus calls fell from 3–4 to 2.
- ⚠️ **The visual harness cannot stage a steal that raises no `blur`.** Every tab it opens
  reports `document.hasFocus()` true, whether or not focus emulation is on. A backgrounded tab
  stops painting and hangs the harness's settle. So the watch is held by a text test, and its
  effect was read on the host (*Measured*).
- ⚠️ **One 3px step can still be painted** before the page is put back. It was seen in about one
  load in three of the two-practice page, when both workbenches take focus in the same few
  milliseconds on one renderer thread. It always settles at 0.
