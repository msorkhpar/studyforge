## What landed

⭐ **What the software does now that it did not:** a built site reads as an
exercise book (light) or a blackboard (dark). It is set in Charis and Andika,
two SIL faces drawn for people learning to read, with code in JetBrains Mono.
Every page tells the reader where they are and what comes next:
- the root index opens with what the site is and how to use it, then
  `n of N units read`, then a strip sized by each group's units that also
  links to each group, then the **Up next** slip, which is the one filled
  area of saturated colour;
- ticked units show a solid ink box in the lists;
- a unit page ends with the next unit on the same slip.

⭐ **The stylesheet's size is the subject (the register's D3):** the built
`page.css` is **2,419,289 bytes**. The embedded faces are 2,325,721 of that and
the authored parts 93,568. It is written once per site and linked by every page,
so a reader's browser loads it once. The script `page.js` is 199,337 bytes.
Measured on this branch's tree with `bundle.stylesheet()`.

## Decisions

- ⭐ **The Up next slip on a UNIT page names the next unit in the author's
  order, not the first unread one.** A unit page carries no other unit's key,
  so it cannot know what else is read. On the index and on a container page,
  every row carries its key, so there the slip is computed from the reader's
  own marks and never names a read unit. With no script, every slip names what
  the renderer wrote.
- ⭐ **The rail shows no ticks and does not mark the next unit.** Its rows
  carry no key (`render/page/rail.py`, outside this surface, rules that out
  on purpose so a container page never holds two elements under one id). A
  second "next" marker would also compete with the slip. The current unit
  keeps the accent's wash.
- ⭐ **Andika's heaviest shipped weight is 700** and there is no 800. The scale
  gets its contrast from weight and family together (Andika 700 over
  Charis 400), with bigger jumps (2.5, 1.6 and 1.2rem).
- ⭐ **No mono italic is vendored.** A code comment keeps the browser's
  synthesised slant and is told apart by its pencil colour first. Seven faces,
  each with a stated reason (`faces.py` docstring).
- ⭐ **`chrome.css` is split into four parts at seams named by job:**
  - `chrome.css`: where things are;
  - `lists.css`: what the reader navigates;
  - `onward.css`: where they go next, and the only fill of `--sign`;
  - `notes.css`: what the page tells them.

  Every part is under 400 lines, and the census tests read the four as one
  part.
- ⭐ **The narration highlight at rest is a short mark in the margin, and the
  wash appears only while playing.** `:root:has(#play [data-state="playing"]…)`
  does this with no change to `narration.js`.
- ⭐ **`--practice-soft` stays painted**, as the practices note's pale band. It
  has no stripe and no radius.

## Findings

- `[structural]` **W362/1** (outside this surface): the rail cannot show read ticks, because
  `render/page/rail.py` emits no unit key on its rows by design. A row that
  wants them would need a key attribute other than `id` (the collision
  `rail.py` avoids). R6 in the plan stays open.
- `[structural]` **W362/2** (corpus data, `W363`): the ISO corpus's unit masthead reads
  `prose`. That is its own variant word, which R1 keeps from the framework.
  `W363`'s manifest data is where a corpus could say not to show it.
- `[local]` **W362/3** (recorded, not reopened): the index keeps the one-column cap that
  `W333` and the census tests pin, so a wide window leaves space to the right
  of the index. Widening it would reopen `W333`'s decision, which is not this
  row's.
- **W362-plan/1** is the register's (the size gate reads `*.py` only), and
  **W362-plan/2** and **W362-plan/3** are settled in this row.
