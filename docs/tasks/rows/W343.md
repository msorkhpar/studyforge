⛔ **`INT-19/7`: the procedure PINS A COMMIT and then runs against a MOVING WORKING TREE, and nothing notices.**

⭐ **MEASURED during the first corpus's regeneration:** the framework's sibling checkout moved from `aa4e256` to `19eea9a` **while the round was running**, because this register merged a round into it. ⚠️ **`git diff aa4e256 19eea9a -- src/` is EMPTY, so no reading of that round needs re-taking** — ⛔ **but that is LUCK, not a property.**

⚠️ **The mechanism:** the corpus records a framework commit in its pin, and then every command it runs uses `PYTHONPATH=<sibling>/src` — ⛔ **which reads whatever the sibling's working tree holds RIGHT NOW, not what the pin names.** ⭐ **Had that round touched `src/`, the corpus would have been built against code its own pin does not name, and the round would have reported a clean build.**

⛔ **THE GENERATED PIN CHECK DOES NOT CLOSE THIS:** it asks whether the sibling checkout **HOLDS** the pinned commit, ⚠️ **not whether it is AT it.** ⭐ **A checkout holds every commit of its history, so the check is satisfied by a tree arbitrarily far ahead of the pin.**

⭐ **Why it matters more now than it did:** ⛔ **the user will run this themselves**, and a coordinator merging framework work while an ingestion runs is not an exotic case — ⚠️ **it is what happened the first time anybody tried.**

### ⛔ WHAT SETTLES IT

1. ⛔ **A build reads the source the pin NAMES**, or it refuses — ⭐ **being at the pin, exporting it, or reading it out of git are all open; say which and why.**
2. ⛔ **The generated check asks whether the checkout is AT the pin**, not merely whether it holds it — ⚠️ **or, if a moving tree is deliberately allowed, it SAYS SO and says what that costs.**
3. ⛔ **Asserted both ways (R12):** a sibling advanced past the pin with a real `src/` change is CAUGHT, and a sibling exactly at the pin passes.
4. ⚠️ **R18 — nothing is pushed and the components are siblings on disk** — ⛔ **so the remedy may not assume a remote or a fetch.**
